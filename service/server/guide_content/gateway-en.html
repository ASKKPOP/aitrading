Complete Guide to the Live Trading Gateway

2026-07-19 · prod = main@8c2248f (image 20260719-orderui) · Written after 3-agent QA verification · English subtitles per section

The full path from automated trading rules to simulator → shadow → live: This single document explains what needs to be configured, what gates an order passes through, and what the system will never do.

01The three execution modes / The three execution modes

A single account setting on the rule (automation page) determines where the execution lands. No other setting can change this.

ModeExecution locationReal fundsRequirementsPurpose
simulator Platform simulated ledger onlyNoneNone (default) Strategy validation, learning the platform
shadow Simulated ledger (baseline) + broker sandbox comparison ordersNone Gateway connection (optional — pure simulation without it) Comparing real slippage/fill rates risk-free
live Via connected gateway to real brokerYes Gateway connection + credentials + agreement to live trading terms Real automated trading
Figure 1 — After a rule passes through the gate chain, it is routed to one of three paths according to account_type.
What never happens: A live rule without a gateway being silently downgraded to simulator. live is rejected with an explicit reason, and that reason is recorded in the execution log — because a fake fill that looks real is the worst outcome.

Live orders on a new venue are refused with an explicit message (never a silent simulation) until Sooppiy enables it after its rollout soak, and newly enabled venues carry a $1,000 per-order limit at first ($1,500 for Webull) (over-limit orders are refused, never resized). Each broker has a step-by-step connection guide on the Accounts page — pick the broker and press the 📖 button.

STEP 2 — Connect the gateway on the Accounts page Connect on the Accounts page

  • Accounts page → Trading Gateway card, select the broker. The list is loaded from the server (GET /api/execution/brokers).
  • Alpaca/Binance: Enter key + secret. IBKR: Enter gateway URL + account number (option for self-signed certificate on local gateway). OKX/KuCoin additionally need the API passphrase.
  • Keys are encrypted and stored on the server using AES-GCM, never remain in the browser's localStorage, and are cleared from the input field immediately after saving, never to be displayed again.

STEP 3 — Agree to the live-trading terms / Accept the live-trading terms

  • The checkbox above the Connect button is the consent step. Without consent, the connection itself will not proceed.
  • Consent is recorded as an immutable log per broker (broker_live_optins) — even if you consented for Alpaca, Binance live requires separate consent.

STEP 4 — Check the health banner / Check the health banner

  • After connecting, a green (healthy)/red (unavailable) banner appears at the top of the account page (GET /api/execution/health).
  • For IBKR, session status (expired/contended) is also shown. Alpaca/Binance have no session concept, so only the presence of credentials is checked.

STEP 5 — Validate in shadow first / Validate in shadow first

  • Automation page (Expert Mode) → set the rule's account = shadow + Auto-Execute ON.
  • While the simulated ledger remains the baseline, the same order is also sent to the broker's sandbox, and the fill differences accumulate in the drift log. This lets you see slippage and fill rates without real funds.

STEP 6 — Flip to live / Flip to live

  • Set the rule's account = live. Live rules with Auto-Execute turned on display a red REAL MONEY badge in the list.
  • From this point on, only decisions that have passed the entire gate chain are sent to the actual broker. The platform ledger is recorded only after the broker accepts.

STEP 7 — Monitor / Monitor

  • Automation page execution log: Every tick's decision, fill, or skip reason.
  • Account page broker order history: Requested quantity vs. broker-confirmed filled quantity, color-coded by status.
  • Drift log (red cards): When the ledger and broker diverge — see §5.
  • Notifications: trade_executed, gateway_down, order_drift — follow the email/SMS channels set in your notification settings.

03The 12 gates an order passes through / The 12-step gate chain

For every tick of a rule with Auto-Execute turned on, a decision (buy/sell) must pass all of the following gates in order for it to actually be filled. If any gate blocks it, the reason is recorded in the execution log and the order is not sent.

Figure 2 — Execution gate chain (evaluate_execution_gates). ⑫ Flows from the bottom of the left column to the top of the right column, and all gates must pass for execution to occur. Test runs (▶) perform analysis only and do not go through this chain.
Order matters: rules with auto-execution disabled are logged as "auto-execution off," not as gateway errors. Reading the skip reason immediately tells you at which gate it stopped.

04The life of a live order / Life of a live order

If the broker does not immediately confirm execution (SUBMITTED) Order reconciler queries the broker every 2 minutes for the result to finalize the status.

Figure 3 — Submit → (immediate or via reconciler) confirm → alert loudly if mismatched. Since requested quantity (quantity) and broker-confirmed quantity (filled_qty) are separate columns, differences remain visible.
Design principle — detect only, humans correct: The reconciler never touches positions or cash. Having a background job fix money calculations would double the ways the ledger can break, so mismatches are prominently flagged with a red card and alert, and corrections are made by the user directly after checking the broker account.

05IBKR session keepalive / IBKR session keepalive

An IBKR Client Portal session disconnects after just a few minutes of idleness. The worker tickles the session every 60 seconds, attempts reauthentication if disconnected, and alerts once a day if recovery fails.

Figure 4 — Session state machine. A competing session is also treated as dead (since another login occupying the account causes orders to be rejected).
shadow safeguard: Unlike Alpaca/Binance, IBKR has no separate sandbox host, and the account determines whether it's real funds. So in shadow mode, if the account number does not have the paper account (D prefix), the adapter rejects without sending the request at all.

07Things the system absolutely never does / Safety invariants (test-pinned)

InvariantReasonHow it is guaranteed
Never silently downgrades live to simulatedA fake fill that looks real is the worst caseExplicit refusal + reason logged at Gate ②
Shadow orders never reach the real exchangeA "simulated execution" must never spend real moneyRule mode pins the endpoint (ignores stored account mode); IBKR is forced to paper account
No position is created when the broker rejectsPrevents phantom positions for orders that never reached the marketLive is only recorded to the ledger after broker acceptance
The reconciler never modifies the ledgerFixing money calculations in the background = risk of double corruptionOnly detect, log, and alert — humans make corrections
Broker keys never go back to the clientMinimize leak surfaceStored with AES-GCM; the lookup API returns only metadata
The encryption key (EXECUTION_ENCRYPTION_KEY) is write-onceRotating it permanently invalidates all stored credentialsOperational procedure + password manager backup
Live failures are never silentA dead gateway is indistinguishable from a quiet marketgateway_down/order_drift alerts (deduplicated hourly/daily)
The invariants above are pinned by automated tests (about 100 of the 1,386 total tests run this stack), and re-verified by 3-agent QA (backend adversarial verification · frontend flow · production status).
