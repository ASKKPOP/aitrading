Plan 20 — 트레이딩 스킬: 작동 방식

30기본 스킬(유지되며, 수정 가능하나 삭제는 불가)
4주입되는 의사결정 프롬프트
0스킬 선택에 소요되는 LLM 호출
28,000프롬프트당 문자 예산
30s워커 캐시 TTL

1. 전체 구조 — 스킬이 존재하는 위치와 작동하는 위치

점선 박스는 이 설계가 깨야 했던 기존의 가정을 나타냅니다: 저장소 skills/는 외부 에이전트를 위한 게시 표면으로, Docker 이미지에서 제외됩니다 — 그래서 스킬 본문은 DB에 저장되고, 기본 카탈로그는 코드로 배포되며 자체적으로 시드됩니다.

2. 의사결정 주기 흐름 — 스킬이 실제 트레이딩 주기에 진입하는 지점

💡 네 개의 주입 지점을 표시합니다. E1 라우터 프롬프트는 의도적으로 절대 커지지 않습니다 — 여섯 번의 비용이 큰 호출을 피하기 위해 존재하는 것이므로, 일곱 번째가 되어서는 안 됩니다.

3. 선택 & 예산 — 블록이 구성되는 방식 (zero-LLM)

어느 단계에서든 레지스트리 오류가 발생하면 빈 블록으로 저하됩니다 — 손상된 스킬 테이블이 트레이딩 사이클을 망가뜨릴 수는 없습니다.

5. 스킬 생명주기 — 기본 vs 커스텀

카탈로그 동기화 (2026-08-02): 카탈로그에서 원본 기본 스킬이 업데이트되면, 카탈로그가 마지막으로 작성한 그대로인 모든 운영 행은 다음 레지스트리 읽기 시 자동으로 업그레이드된다 — 핑거프린트(catalog_hash)가 이 둘을 구분한다. 관리자가 수정한 행은 매칭이 중단되며 명시적인 재설정 전까지 수정 내용을 유지하고, 재설정 시 자동 업그레이드가 다시 활성화된다. 스킬 비활성화는 수정이 아니라 운영자 상태이다: 수정되지 않은 비활성화 스킬도 본문 업그레이드는 계속 받지만 비활성 상태는 유지된다.

6. 안전 계층 — 프롬프트 텍스트가 주문에 직접 도달할 수 없는 이유

스킬 본문은 v1에서 관리자만 작성할 수 있으며 크기가 두 번 제한된다(라우트에서 본문당 4,000, 빌더에서 프롬프트당 28,000). 악의적인 본문이라도 계층 2–4를 우회할 수 없다 — 이들은 프롬프트 외부에서 실행된다.

모든 쓰기 작업은 admin_audit_log (skill.create / update / reset / delete) API 프로세스의 캐시를 즉시 무효화합니다. 워커는 별도의 프로세스입니다**: it converges through the registry's 30-second TTL — an edit reaches the next decision cycle within ~30 s, and a running fleet picks it up on its next cycle (v1 deliberately does not freeze skills per run; see the design doc's non-goals).**
