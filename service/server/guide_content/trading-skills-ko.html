22기본 스킬 (유지됨, 편집 가능, 삭제 불가)

1. 큰 그림 — 스킬이 존재하는 곳과 작동하는 곳

점선 상자는 이 설계가 깨야 했던 기존 가정입니다: 저장소 skills/는 외부 에이전트를 위한 게시 표면이며 Docker 이미지에서 제외됩니다 — 따라서 스킬 본문은 DB에 존재하고, 기본 카탈로그는 코드에 포함되어 배포되며 스스로 시드됩니다.

2. 결정 주기 흐름 — 스킬이 실시간 트레이딩 주기에 진입하는 지점

💡 네 개의 주입 지점을 표시합니다. E1 라우터 프롬프트는 의도적으로 절대 커지지 않습니다 — 이는 여섯 번의 비용이 큰 호출을 피하기 위해 존재하는 것이므로, 일곱 번째가 되어서는 안 됩니다.

3. 선택 & 예산 — 블록이 만들어지는 방식 (제로-LLM)

어느 단계에서든 레지스트리 오류가 발생하면 빈 블록으로 저하됩니다 — 손상된 스킬 테이블이 트레이딩 사이클을 망가뜨릴 수는 없습니다.

5. 스킬 수명 주기 — 기본 대 커스텀

카탈로그 동기화 (2026-08-02): 카탈로그의 원본 기본 스킬이 업데이트되면, 카탈로그가 마지막으로 기록한 그대로인 모든 운영 행은 다음 레지스트리 읽기 시 자동으로 업그레이드된다 — 지문(catalog_hash)이 둘을 구분한다. 관리자가 편집한 행은 더 이상 일치하지 않게 되며, 명시적으로 재설정할 때까지 편집 내용이 유지되고, 재설정 시 자동 업그레이드도 다시 활성화된다. 스킬 비활성화는 편집이 아니라 운영자 상태이다: 비활성화되었지만 변경되지 않은 스킬은 여전히 본문 업그레이드를 받으며 비활성 상태를 유지한다.

6. 안전 계층 — 프롬프트 텍스트가 주문에 직접 도달할 수 없는 이유

스킬 본문은 v1에서 관리자만 작성할 수 있으며 두 곳에서 크기가 제한된다 (라우트에서 본문당 4,000, 빌더에서 프롬프트당 14,000). 악의적인 본문이라도 2–4 계층을 우회할 수 없다 — 이들은 프롬프트 외부에서 실행되기 때문이다.

7. 운영하기 — 관리자 API + 전파 타이밍

호출동작비고
GET /api/admin/skills모든 스킬 나열 (기본 + 커스텀)신선한 읽기, 캐시를 우회함
POST /api/admin/skills커스텀 스킬 생성슬러그 [a-z0-9-] ≤48 · body ≤4,000 · prompts ⊆ {light, trader, verifier, planner} · 중복 시 409
PATCH /api/admin/skills/{slug}name/description/body/prompts/markets/priority/enabled 편집기본 스킬은 편집 가능; 슬러그는 변경 불가
POST /api/admin/skills/{slug}/reset카탈로그 기본값으로 복원 + 재활성화기본 전용 — 커스텀은 400
DELETE /api/admin/skills/{slug}커스텀 스킬 제거기본 → 400 "비활성화하거나 초기화하세요"

모든 쓰기는 admin_audit_log (skill.create / update / reset / delete에 기록되며 즉시 API 프로세스의 캐시를 무효화합니다. worker는 별도의 프로세스입니다: 레지스트리의 30초 TTL을 통해 수렴합니다 — 편집은 ~30초 이내에 다음 결정 주기에 반영되고, 실행 중인 fleet은 다음 주기에 이를 적용합니다(v1은 의도적으로 실행별로 스킬을 고정하지 않습니다; 설계 문서의 비목표를 참고하세요).
