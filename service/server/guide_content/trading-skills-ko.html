플랜 20 — 트레이딩 스킬: 작동 원리

16기본 스킬 (유지됨, 편집 가능, 삭제 불가)
4주입된 결정 프롬프트
0스킬 선택에 사용된 LLM 호출
10,000프롬프트당 문자 예산
30초워커 캐시 TTL

1. 큰 그림 — 스킬이 존재하는 위치와 작동하는 위치

점선 상자는 이 설계가 깨야 했던 기존 가정입니다: 저장소 skills/는 외부 에이전트를 위한 게시 표면이며 Docker 이미지에서 제외됩니다 — 따라서 스킬 본문은 DB에 저장되고, 기본 카탈로그는 코드에 포함되어 배포되며 스스로 시드됩니다.

2. 결정 주기 흐름 — 스킬이 실제 트레이딩 주기에 개입하는 지점

💡 네 개의 주입 지점을 표시합니다. E1 라우터 프롬프트는 의도적으로 절대 커지지 않습니다 — 이는 여섯 번의 비용이 큰 호출을 피하기 위해 존재하는 것이므로, 그 자체가 일곱 번째가 되어서는 안 됩니다.

3. 선택 & 예산 — 블록이 만들어지는 방식 (zero-LLM)

어느 단계에서든 레지스트리 오류가 발생하면 빈 블록으로 저하됩니다 — 손상된 스킬 테이블이 트레이딩 사이클을 망가뜨릴 수는 없습니다.

5. 스킬 생명주기 — 기본 vs 커스텀

Seeding은 없는 경우에만 삽입되는(insert-if-missing) 방식입니다 — 재시작이나 재배포가 관리자의 수정 사항을 덮어쓸 수 없습니다. 이것이 바로 "기본 스킬은 유지되지만 수정할 수 있다"는 것이 양방향으로 성립하는 이유입니다.

6. 안전 계층 — 프롬프트 텍스트가 주문에 직접 도달할 수 없는 이유

스킬 본문은 v1에서 관리자만 작성할 수 있으며 두 번 크기 제한이 있습니다(라우트에서 본문당 4,000자, 빌더에서 프롬프트당 10,000자). 심지어 악의적인 본문이라도 계층 2–4를 우회할 수 없습니다 — 이들은 프롬프트 바깥에서 실행됩니다.

7. 운영하기 — 관리자 API + 전파 타이밍

호출동작비고
GET /api/admin/skills모든 스킬 목록 조회(기본 + 커스텀)새로 읽기, 캐시 우회
POST /api/admin/skills커스텀 스킬 생성slug [a-z0-9-] ≤48 · 본문 ≤4,000 · prompts ⊆ {light, trader, verifier, planner} · 중복 시 409
PATCH /api/admin/skills/{slug}이름/설명/본문/prompts/markets/priority/enabled 수정기본 스킬은 수정 가능; slug는 불변
POST /api/admin/skills/{slug}/reset카탈로그 기본값 복원 + 재활성화기본 스킬 전용 — 커스텀은 400
DELETE /api/admin/skills/{slug}커스텀 스킬 제거기본 스킬 → 400 "비활성화하거나 초기화하세요"

모든 쓰기 작업은 admin_audit_log (skill.create / update / reset / delete에 기록되며 즉시 API 프로세스의 캐시를 무효화합니다. worker는 별도 프로세스입니다: 레지스트리의 30초 TTL을 통해 수렴합니다 — 수정 사항은 다음 결정 주기 내(~30초)에 반영되며, 실행 중인 fleet는 다음 주기에 이를 적용합니다(v1은 의도적으로 실행 단위로 스킬을 고정하지 않습니다; 설계 문서의 non-goals 참조).
