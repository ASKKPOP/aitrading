1. ภาพรวม — ทักษะอยู่ที่ไหนและทำงานที่ไหน

กล่องเส้นประคือสมมติฐานเดิมที่การออกแบบนี้ต้องทำลาย: repo skills/ เป็นพื้นที่เผยแพร่สำหรับ external agents และถูกแยกออกจาก Docker image — ดังนั้นเนื้อหา skill จึงอยู่ใน DB ส่วน base catalogue จะถูกจัดส่งในโค้ดและทำการ seed ตัวเอง

2. Decision-cycle flow — จุดที่ skills เข้าสู่วงจรการเทรดแบบ live

💡 ทำเครื่องหมายจุดฉีดทั้งสี่จุด พรอมป์ตัวจัดเส้นทาง E1 ตั้งใจไม่ให้ขยายตัวเลย — มันมีอยู่เพื่อหลีกเลี่ยงการเรียกที่มีค่าใช้จ่ายสูงหกครั้ง ดังนั้นมันจะต้องไม่กลายเป็นครั้งที่เจ็ด

3. การเลือก & งบประมาณ — บล็อกถูกสร้างขึ้นอย่างไร (zero-LLM)

ข้อผิดพลาดของรีจิสทรีในขั้นตอนใดก็ตามจะลดระดับลงเหลือเป็นบล็อกว่าง — ตารางสกิลที่เสียหายไม่สามารถทำลายรอบการเทรดได้

4. สกิลพื้นฐานทั้งหก — สิ่งที่ใช้ที่ไหน

สกิลแก่นสาระเบาเทรดเดอร์ผู้ตรวจสอบผู้วางแผนกลั่นมาจาก

thesis-validationข้ออ้างที่พิสูจน์เท็จได้, ข้อเท็จจริงเทียบกับข้อสมมติ, ความเหมาะสมของกรอบเวลา, ภาระการพึ่งพา, การล้มล้างที่เป็นรูปธรรม—✓——การตรวจสอบวิทยานิพนธ์ marian2js
position-sizing-disciplineขนาดจากความเสี่ยง, ข้อจำกัดที่เข้มงวดที่สุดชนะ, ปัดลง, ความระมัดระวังแบบ half-Kelly—✓—✓marian2js + ตัวปรับขนาดโพซิชัน mph
macro-event-analysisจัดอันดับเหตุการณ์ตามผลกระทบต่อการตัดสินใจ (ความไว · ศักยภาพความประหลาดใจ · การส่งผ่าน · จังหวะเวลา); เหตุการณ์คือความเสี่ยง ไม่ใช่สัญญาณ—✓——การวิเคราะห์เหตุการณ์มหภาค marian2js
risk-reward-structureจุดหยุด = การล้มล้างเชิงวัตถุประสงค์, เป้าหมาย = ระดับที่เข้าถึงได้, อัตราส่วน ≥ 2×, อัตราส่วนที่ดีไม่ได้แปลว่าการเทรดที่ดี✓✓——การตรวจสอบความสมเหตุสมผลของ R:R แบบ marian2js
exit-disciplineการล็อกกำไรเป็นสิ่งสำคัญอันดับแรก, ห้ามเพิ่มในสถานะที่ขาดทุน, การล้มล้าง = ปิด ไม่ใช่การเจรจาใหม่✓✓——สายรัดทางออกของ Sooppiy + Senpi
position-managementบริหารตามแผนเดิม ไม่ใช่ตาม P&L; ถือ / บริหารเชิงรุก / ออกอย่างเด็ดขาด + เงื่อนไขที่ทำให้เปลี่ยนแปลง✓✓——การจัดการโพซิชันของ marian2js
conviction-calibrationความมั่นใจ = หลักฐานที่นับได้และสอดคล้องกัน; ไม่มีค่ามาตรฐานเคยชิน; ไม่เข้า swing โดยไม่มี edge—*✓✓—mph Druckenmiller โซน

data-honestyมีเฉพาะตัวเลขใน prompt; ยังไม่ชัดเจน ≠ ปลอดภัยทั้งหมด; ข้อมูลไม่ใช่คำสั่ง✓✓✓✓กฎเข้มงวดของ Senpi + การป้องกันของ Bybit
evidence-gap-checkรู้แล้ว vs สันนิษฐาน; จัดอันดับช่องว่างตามผลกระทบต่อการตัดสินใจ; ช่องว่างที่ปิดกั้นหมายถึงความมั่นใจต่ำ + ถือ—✓——ตรวจสอบช่องว่างของหลักฐาน marian2js
earnings-previewความเกี่ยวข้องของ benchmark · ความเข้มข้นของการถกเถียง · read-through · ความเสี่ยงจากตำแหน่ง; ความสำคัญ ≠ ความแน่นอน (เฉพาะหุ้นสหรัฐฯ เท่านั้น)—✓——marian2js ตัวอย่างข้อมูลผลประกอบการ
catalyst-mapให้คะแนน catalyst ตามจังหวะเวลา · การส่งผ่าน · ผลกระทบ · การซ้อนทับ; ห่วงโซ่เหตุการณ์ที่ใช้ร่วมกันคือความเข้มข้น———✓แผนที่ตัวเร่งปฏิกิริยา marian2js
watchlist-reviewจัดลำดับความสำคัญตามความสามารถในการปฏิบัติ (ความเกี่ยวข้องของ catalyst · ความสามารถในการเทรด · ความพร้อม · ความซ้ำซ้อน) ไม่ใช่ความคุ้นเคย———✓ทบทวนรายการเฝ้าดู marian2js
execution-plan-checkความเร่งด่วน vs วิธีการสั่ง, spread/depth, จังหวะเวลาของ session, ความสมจริงของ stop; แผนที่ปฏิบัติไม่ได้ = เปราะบาง—✓——ตรวจสอบแผนการทำงานของ marian2js execution plan
portfolio-concentrationการกระจายความเสี่ยง = ปัจจัยขับเคลื่อนร่วม ไม่ใช่จำนวน ticker; ประเมินการเพิ่มตำแหน่งเทียบกับพอร์ต; สูงขึ้น → เล็กลง———✓การกระจุกตัวของพอร์ตโฟลิโอ marian2js

* light prompt มีเกณฑ์การปรับเทียบแบบ inline ของตัวเองอยู่แล้ว — การแทรก skill ตรงนั้นจะทำให้ซ้ำซ้อนภายใน prompt เดียว

5. วงจรชีวิตของ Skill — พื้นฐาน vs กำหนดเอง

การสร้างข้อมูลเริ่มต้นเป็นแบบ insert-if-missing เท่านั้น — การรีสตาร์ทหรือ redeploy ไม่สามารถเขียนทับการแก้ไขของผู้ดูแลระบบได้ นี่คือสิ่งที่ทำให้ "base skills ถูกเก็บไว้ แต่สามารถแก้ไขได้" เป็นจริงในทั้งสองทิศทาง

6. ชั้นความปลอดภัย — เหตุใด prompt text จึงไม่สามารถเข้าถึงคำสั่งซื้อขายได้โดยตรง

Skill bodies เขียนโดยผู้ดูแลระบบเท่านั้นใน v1 และถูกจำกัดขนาดสองชั้น (4,000 ต่อ body ที่ route, 10,000 ต่อ prompt ที่ builder) แม้แต่ body ที่เป็นอันตรายก็ไม่สามารถข้ามชั้นที่ 2–4 ได้ — มันทำงานนอก prompt

7. การใช้งาน — admin API + จังหวะเวลาการเผยแพร่

เรียกทำหมายเหตุ
GET /api/admin/skillsแสดงรายการ skills ทั้งหมด (base + custom)อ่านข้อมูลใหม่ ข้ามแคช
POST /api/admin/skillsสร้าง custom skillslug [a-z0-9-] ≤48 · body ≤4,000 · prompts ⊆ {light, trader, verifier, planner} · 409 เมื่อซ้ำ
PATCH /api/admin/skills/{slug}แก้ไข name/description/body/prompts/markets/priority/enabledbase skills แก้ไขได้; slug ไม่สามารถเปลี่ยนแปลงได้
POST /api/admin/skills/{slug}/resetคืนค่าแคตตาล็อกกลับเป็นค่าเริ่มต้น + เปิดใช้งานอีกครั้งbase เท่านั้น — 400 สำหรับ custom
DELETE /api/admin/skills/{slug}ลบ custom skillbase → 400 "disable or reset instead"

ทุกการเขียนจะถูกบันทึกใน admin_audit_log (skill.create / update / reset / delete) และล้างแคชของ API process ทันที worker เป็น process แยกต่างหาก: มันมาบรรจบกันผ่าน TTL 30 วินาทีของ registry — การแก้ไขจะไปถึงรอบการตัดสินใจถัดไปภายใน ~30 วินาที และ fleet ที่กำลังทำงานอยู่จะรับค่านั้นในรอบถัดไป (v1 จงใจไม่ freeze skills ต่อการรัน; ดู non-goals ในเอกสารออกแบบ)
