5. วงจรชีวิตของ Skill — พื้นฐาน vs กำหนดเอง

การซิงค์ Catalogue (2026-08-02): เมื่อ base skill ต้นฉบับถูกอัปเดตใน catalogue แต่ละแถวใน prod ที่ยังคงเหมือนกับที่ catalogue เขียนไว้ล่าสุดจะอัปเกรดโดยอัตโนมัติในการอ่าน registry ครั้งต่อไป — fingerprint (catalog_hash) ใช้แยกความแตกต่างระหว่างสองกรณีนี้ แถวที่ admin แก้ไขแล้วจะหยุดตรงกันและคงการแก้ไขไว้จนกว่าจะมีการ reset อย่างชัดเจน ซึ่งจะเปิดใช้ auto-upgrade อีกครั้งด้วย การปิดใช้งาน skill ถือเป็นสถานะของผู้ดำเนินการ ไม่ใช่การแก้ไข: skill ที่ถูกปิดใช้งานโดยไม่ถูกแก้ไขจะยังคงได้รับการอัปเกรดเนื้อหาแต่ยังคงปิดอยู่

6. เลเยอร์ความปลอดภัย — เหตุใดข้อความในพรอมต์จึงไม่สามารถส่งคำสั่งซื้อขายได้โดยตรง

Skill bodies เขียนโดย admin เท่านั้นใน v1 และมีการจำกัดขนาดสองชั้น (4,000 ต่อ body ที่ route, 28,000 ต่อ prompt ที่ builder) แม้แต่ body ที่เป็นอันตรายก็ไม่สามารถข้าม layers 2–4 ได้ — เพราะสิ่งเหล่านี้ทำงานอยู่นอก prompt

7. การดำเนินการ — admin API + จังหวะเวลาการเผยแพร่

เรียกทำอะไรหมายเหตุ
GET /api/admin/skillsแสดงรายการทักษะทั้งหมด (พื้นฐาน + กำหนดเอง)อ่านข้อมูลใหม่ ข้ามแคช
POST /api/admin/skillsสร้างทักษะที่กำหนดเองslug [a-z0-9-] ≤48 · body ≤4,000 · prompts ⊆ {light, trader, verifier, planner} · 409 เมื่อซ้ำกัน
PATCH /api/admin/skills/{slug}แก้ไข name/description/body/prompts/markets/priority/enabledทักษะพื้นฐานแก้ไขได้; slug ไม่สามารถเปลี่ยนแปลงได้
POST /api/admin/skills/{slug}/resetคืนค่าเริ่มต้นของแคตตาล็อก + เปิดใช้งานอีกครั้งเฉพาะพื้นฐานเท่านั้น — 400 สำหรับที่กำหนดเอง
DELETE /api/admin/skills/{slug}ลบทักษะที่กำหนดเองพื้นฐาน → 400 "ปิดใช้งานหรือรีเซ็ตแทน"

ทุกการเขียนจะถูกบันทึกไว้ใน admin_audit_log (skill.create / update / reset / delete) และทำให้แคชของกระบวนการ API ใช้งานไม่ได้ทันที worker เป็นกระบวนการแยกต่างหาก: มันจะบรรจบผ่าน TTL 30 วินาทีของ registry — การแก้ไขจะไปถึงรอบการตัดสินใจถัดไปภายใน ~30 s และ fleet ที่กำลังทำงานอยู่จะรับค่านั้นในรอบถัดไป (v1 ตั้งใจไม่ freeze skills ต่อการรัน; ดู non-goals ในเอกสารออกแบบ)
