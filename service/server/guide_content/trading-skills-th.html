1. ภาพรวม — ทักษะอยู่ที่ไหนและทำงานที่ไหน

กล่องเส้นประคือสมมติฐานเดิมที่การออกแบบนี้ต้องทำลาย: repo skills/ เป็นพื้นผิวสำหรับเผยแพร่ให้ external agents และถูกยกเว้นออกจาก Docker image — ดังนั้นเนื้อหาทักษะจึงอยู่ในฐานข้อมูล และแคตตาล็อกพื้นฐานจะมาพร้อมกับโค้ดและสร้างตัวเองโดยอัตโนมัติ

2. ลำดับขั้นตอนการตัดสินใจ — ทักษะเข้ามามีบทบาทในรอบการเทรดจริงตรงไหน

💡 ทำเครื่องหมายจุดแทรกทั้งสี่จุด E1 router prompt ถูกออกแบบให้ไม่ขยายตัวโดยเจตนา — มันมีอยู่เพื่อหลีกเลี่ยงการเรียก 6 ครั้งที่มีค่าใช้จ่ายสูง ดังนั้นมันต้องไม่กลายเป็นการเรียกครั้งที่ 7

3. Selection & budget — วิธีสร้าง block (zero-LLM)

ข้อผิดพลาดของ registry ในขั้นตอนใดก็ตามจะลดระดับลงเป็นบล็อกว่างเปล่า — ตาราง skills ที่เสียหายจะไม่มีวันทำให้รอบการเทรดเสียหายได้

5. วงจรชีวิตของสกิล — พื้นฐานเทียบกับกำหนดเอง

การซิงค์แคตตาล็อก (2026-08-02): เมื่อสกิลพื้นฐานดั้งเดิมในแคตตาล็อกได้รับการอัปเดต ทุกแถวใน prod ที่ยังตรงกับสิ่งที่แคตตาล็อกเขียนไว้ล่าสุดจะอัปเกรดโดยอัตโนมัติในการอ่านรีจิสทรีครั้งถัดไป — ลายนิ้วมือ (catalog_hash) ใช้แยกความแตกต่างระหว่างสองแบบนี้ แถวที่แอดมินแก้ไขแล้วจะหยุดตรงกันและคงการแก้ไขไว้จนกว่าจะมีการรีเซ็ตอย่างชัดเจน ซึ่งจะเปิดใช้การอัปเกรดอัตโนมัติอีกครั้งด้วย การปิดใช้งานสกิลเป็นสถานะของผู้ควบคุมระบบ ไม่ใช่การแก้ไข: สกิลที่ปิดใช้งานและไม่ถูกแก้ไขยังคงได้รับการอัปเกรดเนื้อหา และยังคงปิดอยู่

6. ชั้นความปลอดภัย — เหตุใดข้อความในพรอมต์จึงเข้าถึงคำสั่งซื้อขายโดยตรงไม่ได้

เนื้อหาสกิลถูกเขียนโดยแอดมินเท่านั้นใน v1 และมีการจำกัดขนาดสองชั้น (4,000 ต่อเนื้อหาที่เราต์ 14,000 ต่อพรอมต์ที่ตัวสร้าง) แม้แต่เนื้อหาที่เป็นอันตรายก็ไม่สามารถข้ามชั้นที่ 2–4 ได้ — เพราะมันทำงานอยู่นอกพรอมต์

7. การใช้งานจริง — API สำหรับแอดมิน + จังหวะเวลาการเผยแพร่

การเรียกทำอะไรหมายเหตุ
GET /api/admin/skillsแสดงรายการสกิลทั้งหมด (พื้นฐาน + กำหนดเอง)การอ่านข้อมูลใหม่ ข้ามแคช
POST /api/admin/skillsสร้าง custom skillslug [a-z0-9-] ≤48 · body ≤4,000 · prompts ⊆ {light, trader, verifier, planner} · 409 เมื่อซ้ำ
PATCH /api/admin/skills/{slug}แก้ไข name/description/body/prompts/markets/priority/enabledbase skills แก้ไขได้; slug ไม่สามารถเปลี่ยนแปลงได้
POST /api/admin/skills/{slug}/resetคืนค่าตั้งต้นของแคตตาล็อก + เปิดใช้งานอีกครั้งเฉพาะ base เท่านั้น — 400 สำหรับ custom
DELETE /api/admin/skills/{slug}ลบ custom skillbase → 400 "disable or reset instead"

ทุกการเขียนจะถูกบันทึกไว้ใน admin_audit_log (skill.create / update / reset / delete) และล้างแคชของ API process ทันที worker เป็น process แยกต่างหาก: มันจะ converge ผ่าน 30-second TTL ของ registry — การแก้ไขจะไปถึงรอบการตัดสินใจถัดไปภายในประมาณ ~30 วินาที และ fleet ที่กำลังทำงานอยู่จะรับค่าใหม่ในรอบถัดไป (v1 จงใจไม่ freeze skills ต่อ run; ดู non-goals ในเอกสารออกแบบ)
