自動売買ルールが モデル(simulator) → シャドウ(shadow) → 実運用(live)へとつながる全体の経路： 何を設定すべきか、注文がどの関門を通るか、システムが絶対に何をしないかを一つの文書で説明します。

013つの実行モード / 3つの実行モード

ルール(自動化ページ)の アカウント(account) 設定一つが約定がどこに着地するかを決定します。他のどの設定もこれを変更できません。

モード約定先実際の資金必要条件用途
シミュレーター プラットフォームのモデル元帳のみなしなし (デフォルト) 戦略検証、プラットフォーム学習
シャドウ モデル元帳(基準) + ブローカーサンドボックスへの対照注文なし ゲートウェイ接続(任意 — なければ純粋なモデル) 実際のスリッページ・約定率を無リスクで比較
ライブ 接続されたゲートウェイを通じて 実際のブローカーあり ゲートウェイ接続 + 資格情報 + 実運用約款の同意 実際の自動売買
図1 — 1つのルールがゲートチェーンを通過した後、account_typeに応じて3つの経路のいずれかにルーティングされます。
絶対に起こらないこと: ゲートウェイのないliveルールが黙ってシミュレーションに格下げされること。liveは 明示的な理由とともに拒否され、その理由が実行記録に残ります — 本物のように見える偽の約定が最悪だからです。

STEP 1 — ブローカーで資格情報を準備 / ブローカーの認証情報を準備する

ブローカー必要なものどこで注意
AlpacaAPIキーID + シークレットalpaca.markets → API Keys (paperとliveのキーは別々)取引権限のみ。shadowは自動的にpaperエンドポイントを使用
BinanceAPIキー + シークレットアカウント → API Management出金権限は絶対に付与しないこと。 取引(TRADE)のみチェック。shadowはtestnetを使用
IBKRClient Portal Gateway URL + 口座番号IBKRが配布するClient Portal Gatewayを直接実行・ログインAPIキーはなし — ゲートウェイのセッションがそのまま認証情報になる。 サーバーからアクセス可能なアドレスである必要がある。口座番号が Dで始まる場合は模擬口座(shadowは模擬口座でのみ動作)
BybitAPI Key + Secretbybit.com → API取引権限のみ。shadowはデモトレード環境を使用(デモキーは別)

KrakenAPI Key + Secretkraken.com → Settings → APIサンドボックスなし — shadowはKrakenの検証専用注文(絶対に約定しない)を送信。キーはSooppiy専用に(他アプリと共有禁止)

KuCoinKey + Secret + Passphrasekucoin.com → API Managementv2キー。shadowは注文テストエンドポイントを使用(絶対に約定しない)
地域拡張 (2026-08-01): Bybit・OKX・Kraken・Crypto.com・Upbit・KuCoinが追加され、今すぐ接続できます。すべてshadow優先で運用されます。新規取引所のlive注文は、検証期間が完了しプラットフォームで有効化されるまで明示的なメッセージとともに拒否され(無断でシミュレーションに切り替わることはありません)、新しく開放された取引所には当初、注文あたり$1,000の上限があります(超過時は縮小ではなく拒否)。ブローカーごとの詳細な接続ガイドは、アカウントページでブローカーを選び📖ボタンから見られます。

STEP 2 — 口座ページでゲートウェイを接続 / 口座(Accounts)ページで接続する

  • 口座(Accounts) ページ → 取引ゲートウェイ カードでブローカーを選択。リストはサーバーから読み込まれます(GET /api/execution/brokers).
  • Alpaca/Binance: キー+シークレットを入力。IBKR: ゲートウェイURL + 口座番号を入力(ローカルゲートウェイの自己署名証明書オプションあり)。 OKX/KuCoinはパスフレーズも併せて入力します。
  • キーはサーバー側でAES-GCMで暗号化保存され、ブラウザのlocalStorageには残らず、保存後は入力欄から即座に消去され再表示されません。

STEP 3 — 実取引規約への同意 / ライブトレーディング利用規約に同意する

  • 接続ボタン上のチェックボックスが同意手続きです。同意なしでは接続自体が進みません。
  • 同意はブローカーごとに不変の記録(broker_live_optins)として残ります — Alpacaに同意していても、Binance liveには別途同意が必要です。

STEP 4 — ステータスバナーの確認 / ヘルスバナーを確認する

  • 接続後、口座ページ上部に緑(正常)/赤(不可)のバナーが表示されます(GET /api/execution/health).
  • IBKRはセッション状態(期限切れ/競合)まで表示されます。Alpaca/Binanceにはセッションという概念がないため、資格情報の有無のみを確認します。

STEP 5 — まずshadowで検証 / 影で先に検証する

  • 自動化ページ(エキスパートモード) → ルールのアカウント = shadow + 自動実行 ON。
  • 模擬台帳が基準として維持される一方、同じ注文がブローカーのサンドボックスにも送られ、約定差異がドリフト記録に蓄積されます。実際の資金を使わずにスリッページ・約定率を確認できます。

STEP 6 — liveへの切り替え / ライブに切り替える

  • ルールのアカウント = live。自動実行がオンのliveルールには一覧に赤い実際の資金(REAL MONEY)バッジが付きます。
  • この時点から、ゲートチェーンをすべて通過した決定のみが実際のブローカーへ送られます。ブローカーが承認した後にのみ、プラットフォームの台帳に記録されます。

STEP 7 — モニタリング / 監視

  • 自動化ページの実行記録: 各ティックの決定・約定・スキップ理由。
  • 口座ページのブローカー注文履歴: リクエスト数量 vs ブローカー確認済み約定数量、ステータス別の色分け。
  • ドリフト記録(赤いカード): 台帳とブローカーが食い違った場合 — §5を参照。
  • 通知: 約定(trade_executed)、ゲートウェイダウン(gateway_down)、注文ドリフト(order_drift) — 通知設定のメール/SMSチャネルに従います。

03注文が通過する12の関門 / 12段階のゲートチェーン

自動実行がオンのルールの各ティックごとに、決定(buy/sell)が実際に約定するには以下の関門を順番にすべて通過する必要があります。一つでも止まれば、その理由が実行記録に残り、注文は送信されません。

図2 — 実行ゲートチェーン(evaluate_execution_gates)。⑫ 左列下から→右列上へと続き、すべて通過して初めて約定します。テスト実行(▶)は分析のみを行い、このチェーンを通りません。
順序が重要です:自動実行がオフのルールは「自動実行オフ」として記録され、ゲートウェイエラーとしては記録されません。スキップ理由を読めば、どの関門で止まったのかすぐに分かります。

04liveオーダーのライフサイクル / 注文のライフサイクル

ブローカーが即座に約定を確定しない場合(SUBMITTED) オーダーリコンサイラーが2分ごとにブローカーへ結果を問い合わせ、最終状態を確定します。

図3 — 提出 → (即座に、またはリコンサイラー経由で)確定 → ずれがあれば大きくアラート。要求数量(quantity)とブローカー確認数量(filled_qty)は別カラムのため、差異が常に見えます。
設計原則 — 検出のみ、修正は人が行う: リコンサイラーはポジション・現金には絶対に触れません。バックグラウンド処理が金額計算を修正することは元帳を二重に壊す道となるため、ずれは赤いカードとアラートで大きく表示し、修正はユーザーがブローカー口座を確認した上で自ら行います。

05IBKRセッションkeepalive / IBKR セッションキープアライブ

IBKR Client Portalのセッションは数分の未操作で切断されます。ワーカーが60秒ごとにセッションをtickleし、切断された場合は再認証を試み、復旧不能なら1日1回アラートを出します。

図4 — セッション状態マシン。競合(competing)セッションもdeadとして扱います(別のログインが口座を占有すると注文が拒否されるため)。
shadowセーフガード: IBKRはAlpaca/Binanceと異なり、専用のサンドボックスホストがなく、口座が実資金かどうかを決定します。そのため、shadowモードで口座番号がデモ口座(D 接頭辞)でない場合、アダプターはリクエスト自体を送信せず拒否します。

07システムが絶対に行わないこと / 安全性不変条件（テスト固定）

不変条件理由保証方法
liveを黙って模擬に格下げしない偽の約定が本物のように見えるのが最悪ゲート②で明示的に拒否し、理由を記録
shadow注文が実際の取引所に届かない「模擬実行」が実資金を使ってはならないルールモードがエンドポイントを固定（保存された口座モードを無視）、IBKRは模擬口座を強制
ブローカーが拒否した場合、ポジションを作成しない市場に届かない注文の幽霊ポジションを防止liveはブローカーの受諾後にのみ元帳に記録
リコンサイラーが元帳を修正しないバックグラウンドでの金額計算の修正＝二重損傷のリスク検知・記録・通知のみ、修正は人手
ブローカーキーがクライアントに返されない漏洩面積の最小化AES-GCMで保存、参照APIはメタデータのみ返却
暗号化キー（EXECUTION_ENCRYPTION_KEY）はwrite-once交換時に保存されたすべての認証情報が永久に無効化運用手順＋パスワードマネージャーによるバックアップ
live失敗は沈黙しないデッドゲートウェイは静かな市場と区別不可能gateway_down/order_drift 通知(時間・日単位で重複排除)
上記の不変条件は自動テスト(合計1,386件中、実行スタック約100件)で固定されており、3-エージェントQA(バックエンド敵対的検証・フロントエンドフロー・プロダクション状態)で再検証されています。
