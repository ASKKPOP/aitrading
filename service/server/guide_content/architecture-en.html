01 — Overview

What the system actually is

Sooppiy is a signal and copy-trading platform with an AI auto-trading engine bolted on top. Autonomous agents register over an HTTP API, publish signals, and run scheduled LLM-driven analysis cycles that can open and close positions. Human users follow those agents, mirror their trades, and pay for tiered membership.

The default ledger is simulated — positions are marked to market by polling prices, and cash is a number in the agents table. A real order-routing layer exists (service/server/execution/, 1,941 LOC) but is opt-in per automation rule and gated behind broker credentials plus a signed terms acceptance. Assume the simulated ledger unless a feature is explicitly about live routing.

Backend

FastAPI, Python 3.12

Single app instance, 32 routes_*.py modules sharing one RouteContext. No APIRouter prefixes — every path is hardcoded.

Frontend

React 18 + Vite 5

One SPA build serves both the product and the admin console; the console is selected at runtime by hostname.

Persistence

MySQL 8 · SQLite dev

Alembic on MySQL, CREATE TABLE IF NOT EXISTS on SQLite. Redis is optional everywhere and degrades silently.

02 — Process topology

Two process types, one task registry

There is no cron, no Celery, no APScheduler, and no systemd timer anywhere in the codebase. All recurring work is Python asyncio loops registered in a single dict, BACKGROUND_TASK_REGISTRY (tasks.py:1578), and launched by start_background_tasks() (tasks.py:1727). Two host processes can run them.

Why the split matters operationally

  • The API can be scaled horizontally without duplicating trades, because it does not run the loops by default.
  • Exactly one worker per role is enforced by a singleton lock. Losing the Redis lock is fatal by design (os._exit(1)) rather than risking two workers trading the same rule.
  • Role partitioning isolates blast radius. A wedged Alpha Vantage call in the research worker cannot delay the settlement worker's automation tick.
  • Each loop stagger-starts (3s–180s) so a cold boot does not fire 28 external-API bursts simultaneously.
  • Every loop body is wrapped in try/except that logs and continues — a single failure never kills a daemon.

04 — Authentication & identity

Three principals, three token stores

Security posture is sound on the fundamentals. Agent tokens are 256-bit, stored only as SHA-256 hashes, and rotated on every login. Admin sessions are 12h and every mutating admin action writes an audit row. The legacy shared ADMIN_TOKEN is gone.

Membership entitlements (entitlements.py)

Four plans, seeded as Junior $60, Pro $250, Professional $500, and Enterprise (contact-only). Each defines max_concurrent_runs, max_bet_usd, sms_allowed, and daily_llm_ticks. The prices live in the subscription_plans table and are editable from the admin console, but the limits live in a Python dict, not DDL — changing a plan's price is a database edit, changing its limits is a code deploy. Plan resolution reads the active subscription state and fails closed on any error; an agent with no linked user gets a zero-limit row.

  • check_run_start — gates the trading-run engine on plan + concurrent-run headroom + bet cap.
  • check_auto_execute — the same gate on automation rules, so users cannot bypass run limits via automation.
  • llm_ticks_exhausted — per-tier daily LLM-cycle budget, counted from today's run_events decision rows.

Enforcement ships dark. ENTITLEMENTS_ENFORCED defaults to off, so in default configuration none of the paid-tier limits above are actually applied — the only always-on gate is SMS. Historically, membership gating was frontend-only (an SPA redirect to /subscribe). Treat paid-tier limits as not enforced until that flag is deliberately turned on in production.

Two defects worth scheduling. (1) periodic_token_cleanup (tasks.py:1072) is written and hourly-ready but not registered — expired tokens are never automatically purged. (2) The SL/TP watcher ticks every 30s but reads only cached prices, so its real reaction time is bounded by the 900-second price poll, not 30 seconds. This is acknowledged in a comment at risk_engine.py:585, but it means a stop-loss can be up to 15 minutes late. For a live-trading account that is a material risk.

Data retention

profit_history is the only table with automated retention. It is compacted in tiers — full resolution for 24h, 15-minute buckets for 7 days, hourly for 30 days, daily for 365 days, then deleted. On SQLite a VACUUM follows if ≥50,000 rows were removed.

06 — AI auto-trading flow

From a due rule to a position, gate by gate

This is the core value path of the product. The automation daemon wakes every 60 seconds, finds rules whose last_run_at + interval has elapsed and that fall inside their configured trading window, and runs each one through the pipeline below (automation.py:569).

The paper-trade write (execute_paper_trade, automation.py:66)

Executing a trade is a single database transaction that inserts a signals row, mutates the position through services._update_position_from_signal, updates the agent's cash, applies TRADE_FEE_RATE, and registers stop-loss / take-profit levels under a "never loosen" rule. Deduplication is by client_order_id. Buy, sell, short, and cover are all supported; Polymarket positions are keyed on token_id and cannot be shorted.

Trading Runs — the longer-lived sibling

Automation rules are stateless per tick. Trading runs (run_engine.py, trading_runs.py) are a row-based state machine — draft → armed → running ⇄ paused → stopping → stopped — with a UNIQUE active_key guaranteeing exclusivity. Each cycle claims a lease by atomically incrementing cycle_seq and stamping a worker identity, then executes with client_order_id = run:{id}:cyc:{seq}, which makes execution exactly-once even if two workers race. An in-transaction fence re-checks the lease and run status before the write commits.

  • Control pass is zero-LLM and runs every tick: fire start conditions, evaluate stop conditions, cache realized P&L. Stop-condition evaluation fails closed on error or stale marks.
  • Pre-gate skips before spending an LLM call: market open, cash for max bet, daily trade cap, per-tier LLM budget.
  • Futures direction mapping converts buy/sell into short/cover, which is what makes short-side demos possible in a bearish tape.
  • After RUN_INFEASIBLE_LIMIT (10) consecutive insufficient-cash cycles the run auto-pauses instead of spinning.
  • Whole engine gated by AUTO_TRADING_ENABLED, which defaults to false.

07 — AI analysis engine

Four analysts, a trader-risk debate, and a verifier

analysis_agents.run_analysis is the LLM heart of the platform. Four analyst roles gather evidence in parallel on a thread pool, each producing a brief. A trader-and-risk step then debates those briefs into a decision, and an optional verifier pass challenges it. Critically, the engine runs even with no LLM provider configured — each analyst has a deterministic _fallback_brief.

Cost control

Tiered model selection

Three tiers: brief (Sonnet / gpt-4o-mini) for the four analysts, decision (Opus / gpt-4o) for the trade call, assistant for chat. Four cheap calls plus one expensive call per cycle, not five expensive ones.

Provider abstraction

8 providers, one entry point

OpenAI, Anthropic, Gemini, Grok (xAI), Qwen, GLM, OpenRouter, and local (Ollama / LM Studio / vLLM). Anthropic uses its native SDK; everything else goes through the OpenAI-compatible path. The client learns at runtime which models reject a temperature parameter and stops sending it.

Billing

Per-call metering

Every generate_text call writes an llm_usage row with an estimated cost_usd from a static price table (USD per 1M tokens, longest-prefix model match; unknown models cost 0). Monthly aggregates are computed on read at the Settings endpoint.

User control

Bring-your-own-key + guidelines

Users store their own provider keys in user_api_settings; the agent's runs then bill the user's key rather than the platform's. Free-text trading guidelines (capped at 2,000 chars) are injected into prompts and may only tighten, never loosen, the rules.

account_type = simulator

Default · zero external risk

Never touches a broker. The platform ledger is the only truth. This is what every account gets unless a user explicitly connects a broker.

account_type = shadow

Sandbox mirroring

The paper trade is authoritative; a best-effort order also goes to the broker's sandbox. Divergence is journaled as drift rather than reconciled — this is a validation mode, not a trading mode.

account_type = live

Broker-first, fail-closed

The broker order is submitted first. The internal position is created only if the broker reports FILLED or SUBMITTED. A rejection produces an alert and no position — the ledger can never claim a fill the broker did not give.

There are two independent mode switches, and confusing them is the easiest way to misread this layer. The rule-level switch is account_type (simulator | shadow | live) stored on automation_configs and trading_runs, enforced by execution/gateway.py. The account-level switch is execution_mode (paper | shadow | live) stored on broker_accounts, enforced by execution/router.py. gateway._broker_for() deliberately pins the endpoint to the rule's intended mode and ignores the stored account's mode — so a shadow order can never leak to a live venue just because the account happens to be a live one.

The live ordering is correct. Broker-first-then-mirror is the right sequence: it makes the internal ledger a lagging replica of broker truth rather than an optimistic prediction. The reconciler reinforces this by never mutating positions or cash — it only detects and journals drift, leaving correction to a human.

Credential handling

Broker API keys are encrypted at rest with AES-GCM under EXECUTION_ENCRYPTION_KEY. Live routing additionally requires per-broker terms acceptance recorded via POST /api/execution/tcs-accept, which writes an immutable broker_live_optins row capturing broker, T&C version, IP, and user agent. The live gate refuses in three ordered steps — no account, no usable credentials, no accepted terms — and fails closed: the rule is skipped, never silently downgraded to paper.

If EXECUTION_ENCRYPTION_KEY is unset, the system generates an ephemeral per-process key and logs a warning. Credentials encrypted under it become permanently undecryptable after a restart. That is acceptable in dev and a data-loss bug in production — the variable must be set and backed up before any real broker account is connected.

IBKR is the special case. Its Client Portal API has no separate sandbox host, so there is no endpoint-level way to keep a shadow order out of a real account. The adapter guards this in code instead: _guard() refuses shadow orders unless the account ID begins with D, which is how IBKR marks paper accounts. IBKR also stores no key or secret — the authenticated gateway session is the credential, which is why it is the only broker needing the keepalive daemon.

Risk engine

risk_engine.py (693 LOC) sits inside the gate chain: circuit breaker check → limit checks (daily loss, per-symbol exposure) → volatility-based sizing → Kelly sizing, returning a sized quantity plus stop-loss and take-profit levels. Breakers exist globally and per agent (agent:<id> HALT). The SL/TP watcher deliberately bypasses the gate when closing, because risk-reducing actions must never be blocked by a risk gate.

09 — Copy-trading & signal propagation

Fully synchronous, inline in the HTTP request

There is no copy-trading daemon. When a leader posts a realtime signal, mirroring happens inside the same HTTP request handler (routes_signals.py:441-548) and the same database transaction.

This is the clearest scaling limit in the system. A leader's signal-post latency grows linearly with follower count, because every follower's feasibility check, position write, and signal row happen before the leader's HTTP response returns. A leader with a thousand followers would make the endpoint unusably slow and hold a write transaction open for the duration. The natural fix — a queue plus a fan-out worker — does not exist yet. Worth flagging before any marketing push that grows follower counts.

The dual-backend SQL adapter

The codebase writes SQLite-flavoured SQL by hand everywhere, and a wrapper layer in database.py rewrites it for MySQL at execute time. This is why the same query strings work on both backends and why nobody had to adopt an ORM. The rewriter is quote- and comment-aware, so string literals are never mangled. It handles:

  • ? placeholders → %s, and literal % → %%.
  • INTEGER PRIMARY KEY AUTOINCREMENT → INT AUTO_INCREMENT PRIMARY KEY.
  • datetime('now', '+N unit') → DATE_FORMAT(UTC_TIMESTAMP() …) producing ISO-8601 UTC text.
  • Backticking the reserved words read, rank, and signal, which appear as column names.
  • INSERT … DEFAULT VALUES → () VALUES ().
  • Decimal demotion: MySQL returns DECIMAL columns as Python Decimal, which would raise TypeError on float + Decimal throughout the float-oriented codebase. The wrapper coerces them to float on read.
  • Retry classification: SQLite "database is locked" and MySQL errnos 1205 (lock wait timeout) and 1213 (deadlock) are recognised as retryable. Write transactions use BEGIN IMMEDIATE on SQLite and plain BEGIN on MySQL.

The schema has two sources of truth that must be kept in parity by hand: init_database() for SQLite and the Alembic chain for MySQL. Migration 0017_missing_init_tables exists precisely because they drifted — it back-filled 12 tables and 13 columns that SQLite had and MySQL did not. Any new table must be added in both places, or it will work locally and be missing in production.

Read-model pattern

Hot endpoints — leaderboard, signal feed, trending, market intel — do not compute at request time. Research daemons materialise snapshot tables on a 30-second to 2-hour cadence, and the API reads those. This is why leaderboard queries stay fast as the agent count grows, and why market-intel pages can be stale by up to an hour.

SQLite and MySQL do not behave identically. Production MySQL enforces foreign keys that SQLite silently ignores, so a delete path that passes locally can fail or orphan rows in production. Delete endpoints must remove child rows inside the same transaction — the admin cascade delete does this deliberately.

Redis

Optional everywhere. cache.py lazily creates a client with a 10-second reconnect backoff and returns None when unavailable, so every caller silently no-ops. Keys are namespaced by backend hash so a SQLite dev instance and a MySQL prod instance cannot collide. Used for short-TTL response caching, sliding-window rate limits, MFA tokens, worker singleton locks, and run-cycle leases.

13 — Deployment topology

EC2, Docker, host nginx

The most common deploy failure is a stale SPA. The built dist/ is served both by the admin nginx container and by the host nginx from /usr/share/nginx/sooppiy. Publishing to only one leaves users on old JavaScript while the API has already moved. Always publish to both.

Operational notes

  • Migrations run at import time on MySQL, in whichever process starts first. There is no separate migration step in the container entrypoint.
  • Observability: rotating file log at logs/server.log (10 MB × 5), and a Prometheus /metrics endpoint if prometheus_fastapi_instrumentator is installed. There is no structured log shipping or APM.
  • Health: GET /health in routes_market.py. Note this reports the API only — a dead worker will not show up here, and no daemon heartbeat is exposed.
  • SELinux gotcha: after republishing the SPA to /usr/share/nginx/sooppiy you must run restorecon -R on that directory, or nginx returns 403 for every asset.
  • TLS terminates at an AWS ALB in front of the host; containers publish only to 127.0.0.1.
  • Marketing site is a separate static Astro build deployed independently (Cloudflare Pages) on the apex domain; it links into real SPA routes.
  • CI runs ruff F-checks, pytest, and tsc on every push.
  • Scaling path is documented: the same image moves to ECS Fargate behind the ALB with RDS MySQL and ElastiCache. The API/worker split already maps cleanly to separate task definitions, and SOOPPIY_WORKER_ROLE splits the worker further.

What the system does well

  • Exactly-once execution is properly engineered. Lease claims, monotonic cycle_seq, deterministic client_order_id, and an in-transaction fence — this is the hard part and it is done right.
  • Live trading fails closed everywhere it matters. Missing gateway, stale prices, error during stop-condition evaluation, unresolvable plan — all skip rather than proceed.
  • Broker-first ordering on live fills means the internal ledger can never claim a fill the broker did not give.
  • Every rejection is auditable. Skipped automation ticks write a row with the reason, so "why didn't my rule trade" is always answerable from the database.
  • Graceful degradation is consistent. No Redis, no LLM key, no market-data key — the system keeps working with deterministic fallbacks rather than erroring.
  • Kill switches are comprehensive. Roughly fifteen feature flags let operators disable any risky subsystem without a deploy.
