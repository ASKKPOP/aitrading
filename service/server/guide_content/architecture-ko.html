01 — 개요

이 시스템이 실제로 무엇인가

Sooppiy는 시그널 및 카피 트레이딩 플랫폼으로, 그 위에 AI 자동매매 엔진이 추가되어 있습니다. 자율 에이전트는 HTTP API를 통해 등록하고, 시그널을 발행하며, 예약된 LLM 기반 분석 주기를 실행하여 포지션을 열고 닫을 수 있습니다. 사람 사용자는 이러한 에이전트를 팔로우하고, 그들의 거래를 미러링하며, 등급별 멤버십에 대한 비용을 지불합니다.

기본 원장은 시뮬레이션 방식입니다 — 포지션은 가격을 폴링하여 시가 평가되며, 현금은 agents 테이블 안의 숫자입니다. 실제 주문 라우팅 레이어가 존재합니다 (service/server/execution/, 1,941 LOC)가 존재하지만 자동매매 규칙별 옵트인이며, 브로커 자격증명과 약관 동의 서명이 있어야 열립니다. 기능이 명시적으로 실거래 라우팅에 관한 것이 아닌 한 시뮬레이션 장부를 전제로 보면 됩니다.

FastAPI, Python 3.12

단일 앱 인스턴스, 32개 routes_*.py 모듈이 하나의 RouteContext을(를) 공유합니다. APIRouter 접두사 없음 — 모든 경로는 하드코딩되어 있습니다.

하나의 SPA 빌드가 제품과 관리자 콘솔을 모두 제공하며, 콘솔은 런타임에 호스트명으로 선택됩니다.

MySQL 8 · SQLite dev

MySQL에서는 Alembic, SQLite에서는 CREATE TABLE IF NOT EXISTS을(를) 사용합니다. Redis는 어디서나 선택 사항이며 조용히 성능이 저하됩니다.

02 — 프로세스 토폴로지

두 가지 프로세스 유형, 하나의 작업 레지스트리

코드베이스 어디에도 크론, Celery, APScheduler, systemd 타이머가 전혀 없습니다 어디에도 없습니다. 모든 반복 작업은 Python asyncio 루프로 단일 딕셔너리에 등록되며, BACKGROUND_TASK_REGISTRY (tasks.py:1578), 다음에 의해 실행됩니다 start_background_tasks() (tasks.py:1727). 두 개의 호스트 프로세스가 이를 실행할 수 있습니다.

분할이 운영상 중요한 이유

  • API는 수평적으로 확장할 수 있습니다 거래를 중복시키지 않고도 가능한데, 기본적으로 루프를 실행하지 않기 때문입니다.
  • 역할당 정확히 하나의 워커 만 싱글턴 락에 의해 강제되며, Redis 락을 잃는 것은 설계상 치명적 오류로 처리됩니다 (os._exit(1)) 두 워커가 동일한 규칙을 거래할 위험을 감수하는 대신입니다.
  • 역할 분리는 장애 반경을 격리합니다. 정체된 Alpha Vantage 호출이 research 워커에서 발생해도 settlement 워커의 자동화 틱을 지연시킬 수 없습니다.
  • 각 루프는 스태거 방식으로 시작되어(3s–180s), 콜드 부팅 시 28개의 외부 API 호출이 동시에 발생하지 않도록 합니다.
  • 모든 루프 본문은 try/except 로 감싸져 있어, 로그를 남기고 계속 진행합니다 — 단일 실패가 데몬을 종료시키지 않습니다.

04 — 인증 및 아이덴티티

세 개의 주체, 세 개의 토큰 저장소

보안 태세는 기본적으로 견고합니다. 에이전트 토큰은 256비트이며, SHA-256 해시로만 저장되고, 로그인할 때마다 회전됩니다. 관리자 세션은 12시간이며 모든 변경성 관리자 작업은 감사 행을 기록합니다. 기존의 공유 ADMIN_TOKEN가 사라졌습니다.

멤버십 자격 (entitlements.py)

네 가지 플랜이 Junior $60, Pro $119, Professional $199, Enterprise(문의 전용)로 시딩됩니다. 각 플랜은 max_concurrent_runs, max_bet_usd, sms_allowed와(과) daily_llm_ticks을(를) 정의합니다. 가격은 subscription_plans 테이블에 있으며 관리자 콘솔에서 편집할 수 있지만, 제한은 Python dict이며 DDL이 아닙니다 — 플랜의 가격을 변경하는 것은 데이터베이스 편집이지만, 플랜의 제한을 변경하는 것은 코드 배포입니다. 플랜 해석은 활성 구독 상태를 읽고 실패 시 차단 오류가 발생하면 항상 그렇게 됩니다; 연결된 사용자가 없는 에이전트는 제한이 0인 행을 받습니다.

  • check_run_start — 플랜 + 동시 실행 여유 + 베팅 한도를 기준으로 트레이딩 실행 엔진을 제어합니다.
  • check_auto_execute — 자동화 규칙에도 동일한 제어가 적용되어 사용자가 자동화를 통해 실행 제한을 우회할 수 없습니다.
  • llm_ticks_exhausted — 티어별 일일 LLM 사이클 예산으로, 오늘의 run_events 결정 행을 기준으로 계산됩니다.

적용 기능은 비활성 상태로 배포됩니다. ENTITLEMENTS_ENFORCED은 기본값이 꺼짐(off)이므로, 기본 설정에서는 위의 유료 티어 제한이 실제로 적용되지 않습니다 — 항상 활성화된 유일한 제어는 SMS입니다. 이전에는 멤버십 제어가 프런트엔드에서만 이루어졌습니다(SPA 리디렉션이 /subscribe).적용되지 않음 해당 플래그가 프로덕션에서 의도적으로 활성화되기 전까지는요.

듀얼 백엔드 SQL 어댑터

코드베이스는 어디서나 SQLite 스타일의 SQL을 직접 작성하며, 그 안의 래퍼 레이어가 database.py 이를 실행 시점에 MySQL용으로 다시 작성합니다. 이 덕분에 동일한 쿼리 문자열이 양쪽 백엔드에서 모두 동작하며, 아무도 ORM을 도입할 필요가 없었습니다. 이 재작성기는 따옴표와 주석을 인식하므로 문자열 리터럴이 손상되지 않습니다. 처리하는 항목은 다음과 같습니다:

  • ? 플레이스홀더 → %s, 그리고 리터럴 % → %%.
  • INTEGER PRIMARY KEY AUTOINCREMENT → INT AUTO_INCREMENT PRIMARY KEY.
  • datetime('now', '+N unit') → DATE_FORMAT(UTC_TIMESTAMP() …) ISO-8601 UTC 텍스트를 생성합니다.
  • 예약어를 백틱으로 감싸기 read, rank, 그리고 signal, 이는 컬럼 이름으로 사용됩니다.
  • INSERT … DEFAULT VALUES → () VALUES ().
  • Decimal 강등: MySQL는 반환합니다 DECIMAL 컬럼을 Python Decimal, 이는 발생시킵니다 TypeError 실행 시 float + Decimal float 중심의 코드베이스 전반에서. 래퍼는 이를 float 읽기 시 변환합니다.
  • 재시도 분류: SQLite "database is locked" 및 MySQL 오류 코드 1205(잠금 대기 시간 초과)와 1213(교착 상태)은 재시도 가능한 것으로 인식됩니다. 쓰기 트랜잭션은 BEGIN IMMEDIATE SQLite와 일반 BEGIN MySQL에서.

스키마에는 두 개의 진실 공급원(source of truth)이 있으며 수동으로 동기화 상태를 유지해야 합니다: init_database() SQLite용과 MySQL용 Alembic 체인. 마이그레이션 0017_missing_init_tables 이 둘이 어긋났기 때문에 존재하며, SQLite에는 있지만 MySQL에는 없었던 12개 테이블과 13개 컬럼을 소급 반영했습니다. 새 테이블은 반드시 양쪽 모두에 추가해야 합니다, 그렇지 않으면 로컬에서는 작동하지만 프로덕션에서는 누락됩니다.

Read-model 패턴

핫 엔드포인트 — 리더보드, 시그널 피드, 트렌딩, 마켓 인텔 — 는 요청 시점에 계산되지 않습니다. 리서치 데몬이 30초에서 2시간 주기로 스냅샷 테이블을 생성하고, API는 이를 읽습니다. 이것이 에이전트 수가 늘어나도 리더보드 쿼리가 빠르게 유지되는 이유이며, 마켓 인텔 페이지가 최대 한 시간까지 오래된 데이터일 수 있는 이유입니다.

SQLite와 MySQL은 동일하게 동작하지 않습니다. 프로덕션 MySQL은 SQLite가 조용히 무시하는 외래 키 제약을 강제하므로, 로컬에서는 통과하는 삭제 경로가 프로덕션에서는 실패하거나 고아 행을 남길 수 있습니다. 삭제 엔드포인트는 동일한 트랜잭션 내에서 자식 행을 제거해야 합니다 — 관리자 계단식 삭제는 이를 의도적으로 수행합니다.

Redis

모든 곳에서 선택 사항입니다. cache.py 는 10초 재연결 백오프로 클라이언트를 지연 생성하며, 사용 불가 시 None 를 반환하므로, 모든 호출자는 조용히 아무 동작도 하지 않습니다. 키는 백엔드 해시로 네임스페이스화되어 SQLite 개발 인스턴스와 MySQL 프로덕션 인스턴스가 충돌하지 않습니다. 짧은 TTL 응답 캐싱, 슬라이딩 윈도우 속도 제한, MFA 토큰, 워커 싱글톤 락, 실행 주기 리스에 사용됩니다.

13 — 배포 토폴로지

EC2, Docker, host nginx

가장 흔한 배포 실패 원인은 오래된(stale) SPA입니다. 빌드된 dist/은(는) admin nginx 컨테이너와 host nginx 양쪽에서 /usr/share/nginx/sooppiy을(를) 통해 서빙됩니다. 한쪽에만 배포하면 API는 이미 이동했는데 사용자는 이전 JavaScript를 사용하게 됩니다. 항상 양쪽 모두에 배포하세요.

운영 참고 사항

  • 마이그레이션은 import 시점에 실행됩니다 MySQL에서, 먼저 시작되는 프로세스가 어느 쪽이든 그 안에서 실행됩니다. 컨테이너 엔트리포인트에는 별도의 마이그레이션 단계가 없습니다.
  • 관측성(Observability): 순환 파일 로그가 logs/server.log(10 MB × 5)에 기록되며, /metrics가 설치된 경우 Prometheus prometheus_fastapi_instrumentator 엔드포인트가 제공됩니다. 구조화된 로그 전송이나 APM은 없습니다.
  • 헬스체크: GET /health routes_market.py에서. 이는 API만 보고한다는 점에 유의하세요 — 죽은 worker는 여기에 나타나지 않으며, 데몬 하트비트도 노출되지 않습니다.
  • SELinux 주의사항: SPA를 /usr/share/nginx/sooppiy에 재배포한 후에는 해당 디렉터리에 restorecon -R을(를) 실행해야 합니다. 그렇지 않으면 nginx가 모든 자산에 대해 403을 반환합니다.
  • TLS은(는) host 앞단의 AWS ALB에서 종료되며, 컨테이너는 오직 다음으로만 게시합니다: 127.0.0.1.
  • 마케팅 사이트는 apex 도메인에서 독립적으로 배포되는 별도의 static Astro 빌드입니다(Cloudflare Pages). 이는 실제 SPA 경로로 링크됩니다.
  • CI는 매 푸시마다 ruff F-checks, pytest, tsc을(를) 실행합니다.
  • 확장 경로도 문서화되어 있습니다: 동일한 이미지가 ALB 뒤의 ECS Fargate로 이동하며 RDS MySQL과 ElastiCache를 사용합니다. API/워커 분리는 이미 별도의 태스크 정의로 깔끔하게 매핑되며, SOOPPIY_WORKER_ROLE은(는) 워커를 더 세분화합니다.

시스템이 잘하고 있는 부분

  • 정확히 한 번 실행이 제대로 설계되어 있습니다. Lease 클레임, 단조 증가하는 cycle_seq, 결정론적 client_order_id, 그리고 트랜잭션 내 펜스 — 이것이 어려운 부분이며 제대로 구현되어 있습니다.
  • 라이브 트레이딩은 중요한 모든 지점에서 안전하게 실패합니다. 게이트웨이 누락, 오래된 가격, 정지 조건 평가 중 오류, 해석 불가능한 계획 — 이 모든 경우 진행하지 않고 건너뜁니다.
  • 라이브 체결에서의 브로커 우선 순서 는 내부 원장이 브로커가 제공하지 않은 체결을 절대 주장할 수 없음을 의미합니다.
  • 모든 거부는 감사 가능합니다. 자동화 틱이 건너뛰어질 때 이유와 함께 행이 기록되므로, "왜 내 규칙이 거래되지 않았는가"는 항상 데이터베이스에서 답을 찾을 수 있습니다.
  • 우아한 성능 저하가 일관되게 적용됩니다. Redis가 없거나, LLM 키가 없거나, 시장 데이터 키가 없어도 — 시스템은 오류를 내는 대신 결정론적 폴백으로 계속 작동합니다.
  • 킬 스위치가 포괄적으로 구비되어 있습니다. 약 15개의 기능 플래그를 통해 운영자는 배포 없이도 위험한 하위 시스템을 비활성화할 수 있습니다.
