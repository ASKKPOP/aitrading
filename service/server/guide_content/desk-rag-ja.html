2. 収集 — チャンクの生成方法

収集 — チャンクが生成される経路。3つのソースすべてが、毎トレーディングティックに便乗してスロットル・冪等（SHA）・fail-softで蓄積される。破損したコーパスがトレーディングサイクルを止めることは構造的にあり得ない。

ソース何がチャンクになるか種類重要な理由
ingest_decisions() 各decisionイベントのreport — デスクが述べた根拠 — に加え、その裏にある数値（action, confidence, conviction） decision プラットフォームが生み出す最も価値あるテキストは、一度読まれた後、次の200件のイベントの下に埋もれてしまう
ingest_run_outcomes() 終了したラン（stopped/finished/failed）とその実現結果を結びつけたもの outcome 「この判断」と「それが何を生んだか、あるいは何を失ったか」を結びつけるものは他になく — デスクにはこう問うことすらできなかった「前回このように判断したとき、何が起きたか？」
ingest_reports() モニタリングmarkdown（handoff、daily cycle notes、backlog）を## 見出しごとにチャンク化 — 1日分は粗すぎ、1段落では見出しを失う monitoring 測定された知見（fee hurdle、full-book dumps、ladder churn…）はアカウントのローテーションを乗り越えてデスクに届く

5. スコアリングロジック — 意図的に単純

スコアリング — 意図的にシンプルに。埋め込みサービス・FTS5・MySQL FULLTEXT なし。

  • 純粋な Python の字句スコアラー。 コーパスは小規模（数百から数千チャンク程度）であり、Python スコアラーは 同一に SQLite と MySQL の両方で動作する — 方言の違いはこのコードベースを過去に苦しめてきた（LIKE ESCAPE、日時関数、FK 制約）。
  • 短いストップワードリスト。 積極的なストップリストはドメイン語を除去してしまう — loss, stop, close — それこそがクエリが実際に対象としているものだ。
  • kind=monitoring のみが今日リコール可能。 510件の decision と 31件の outcome チャンクは書き込み専用である 設計上：それらはPhase 3の学習データであり、アトリビューションが存在する前に投入すると、フィードバックループのないノイズを追加するだけになる。
  • サイクルパス上のすべては fail-soft である。 空の、遅い、または壊れたコーパスは "" を返す — サイクルが自身の記憶によって失われることはない。

6. フェーズ・ロードマップ — 学習ループの現在地

ロードマップ — 順序ルールが拘束力を持つ: 回収に 変動(variance)がなければ重みを学習できない。データより先に構築しない。1日1インクリメント、毎日プロドまで。

過学習のリスクは計画書に明記されている：スキルと知見は測定されたエピソードから記述される — それは である 過去に適合させることだ。緩和策として、すべての教訓はエビデンス条項を保持し、重みは意見ではなくエビデンスに基づく。

8. これが意図的にそうでないもの

これが意図的にそうでないもの — よくあるRAGの主張に対する実態。

よくある主張ここ
「膨大なデータを瞬時に処理する」いいえ。 デスクは小さなブリーフを見る。検索が送るのは適切な小さなブリーフであり、より多くのデータではない。
「人間の感情を取り除く」部分的に。 2%未満の値動きでのフルブックのダンプが測定された — 行動的にはパニックと同一。想起機能は、測定された教訓を次の同様の瞬間の前に提示するために存在する。
「自動的に学習する」まだ。 重みには、検索されたものの分散が必要である。その分散を記録する機能は稼働中（#340）；そこから学習することは日次ビルドの周期の役割であり、一度に一つの慎重な増分で行われる。
「ベクトルデータベース」いいえ。 テーブルとPythonのスコアラーは、両方のSQL方言で同一であり、金銭が絡む経路ではフェイルソフトである。意図的に地味である。
