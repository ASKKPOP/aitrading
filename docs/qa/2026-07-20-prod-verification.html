Findings

1 — Production has no true liveness signal RISK
There is no /api/health route anywhere in the codebase, yet GET https://api.sooppiy.com/api/health returns HTTP 200 with <!DOCTYPE html>. The SPA fallback answers it. Any monitor that checks a status code — ALB target group, uptime probe, cron — cannot distinguish a healthy backend from a dead one. A total outage would present as a normally-loading site whose every API call silently returns HTML. Confirmed on both domains (F1, F2).
2 — Documented endpoint prefix /api/claw/* does not exist RISK
The handoff doc's architecture section states agents call /api/claw/*. No such prefix is registered. The real routes are /api/agents/me/*. Because unmatched paths return 200 + HTML, a status-code-only test of /api/claw/agent appears to pass — this produced a false positive in an earlier verification run of this very engagement before body assertions were added.
3 — Paths that silently fall through to HTML RISK
/api/leaderboard, /api/agents, and /api/portfolio all return the SPA rather than JSON (F3). /api/positions is a real route and returns JSON. Any of the first three used as a liveness or smoke check is meaningless.
4 — Concurrent deploys share one unlocked ~/sooppiy/.env RISK
The file changed from 9206 to 9566 bytes mid-session while a parallel session deployed. The deploy runbook mutates it with sed -i and there is no lock. Production moved across four image tags in roughly thirty minutes. Two overlapping deploys can leave backend and worker on different tags, or clobber one session's image pin. A wholesale .env restore from a stale snapshot would have silently dropped the other session's keys.
5 — Everything the account actually touches works PASS
All 15 agent-token endpoints, all 4 user-token endpoints, both market-data endpoints, and all 3 auth-enforcement checks returned correct JSON. Login yields user_id 5 with subscription_status: active; a wrong password issues no token; unauthenticated and garbage-token requests to real routes are correctly refused with JSON 401.

Deploy runbook — executed, not assumed

The runbook in docs/plan/03-session-handoff.md was run end to end against production: built a dated tag, repointed SOOPPIY_IMAGE, recreated backend and worker via compose, republished the SPA, then rolled back. Both directions finished with 0 restarts, 0 tracebacks, and matching bundle hashes.

The exercise was made safe by first proving the backend Python source in the live image was byte-identical to origin/main (SHA-1 of the sorted per-file digest list matched at 6da68d754812546b), making the rebuild a code-level no-op.

Method

39 checks driven by curl against the live public endpoints, authenticating as info@askkpop.com through the documented login → agent-token flow. Read-only apart from login and the idempotent agent-token mint. Each check classifies the response body as JSON, HTML, EMPTY, or OTHER and asserts on that classification rather than the status code.

The suite was run twice; the verdict column was byte-identical across both passes. An earlier draft of the suite reported four false failures caused by two defects in the harness itself — a collision with bash's readonly UID, and use of the non-existent /api/claw/* prefix. Both were fixed before these results were recorded.
