要約(韓国語サマリー)

強制清算(force liquidation)は今 理論ではなく実際のリスクです。プロダクションのオープンポジション5件すべてが2倍または3倍のレバレッジを使用しています。しかし現在の防御手段は _evaluate_stop の中の固定閾値がひとつあるだけで、その閾値は維持証拠金(MMR)・ファンディングレート・マーク価格・クロスマージンを一切計算せず、AIには何も知らせず、実取引のブローカー経路にはマージン状態を読み取る機能自体がありません。本書では、(A) マージン状態オラクル、(B) health = (マーク−清算)/(エントリー−清算) という単一指標とその変化速度、(C) 4段階エスカレーション — T1・T2は AIが判断T3のみを機械的反射とし、(D) 20秒周期のデーモンを設計します。正直な例外を一つ明示します:T3は意図的にルールです。health 0.15でのLLM往復はマージン全体を賭けるギャンブルになるためです。

2. 現在のチェックが清算モデルと言えない理由

コードベースには清算防御が正確に1つだけ存在する。それは _evaluate_stop の内部にあるクッション分岐だ。その構造は、清算までの距離に対する単一の固定割合である。この割合がヘルスの観点で何を意味するか計算してみよう——ショートの場合、クッションが発動するのは mark = entry(1 + c/L) のときであり、清算は entry(1 + 1/L) で発生する。よって

health = (liq − mark) / (liq − entry)
       = (entry(1+1/L) − entry(1+c/L)) / (entry(1+1/L) − entry)
       = (entry(1−c)/L) / (entry/L)
       = 1 − c  =  0.15        (and the long case is symmetric)

つまり今日の清算防御全体は、health = 0.15 における1本の固定ラインに過ぎない。 レバレッジにも銘柄にも依存せず——そして最も重要な点として——ポジションがどれほどの速度で動いているかをまったく考慮していない。さらに具体的な見落としが5つあり、そのうち4つは数式に関するもの、1つは実装（配線）に関するものだ。

#省略された項誤差の方向3倍における大きさ

ステージB — 1つのスカラー値とその微分

long :  health = (mark − liq) / (entry − liq)
short:  health = (liq − mark) / (liq − entry)

velocity = Δhealth / Δt          (least-squares slope over the last N samples)
ttl      = health / max(ε, −velocity)      # time to liquidation at this rate

価格やP&Lで閾値判定するのではなく正規化する理由：health はエントリー時に1.0、清算時に0.0となる。これはすべての銘柄、すべてのレバレッジ、両方向において成り立つため、市場ごとの調整なしに、3倍のMNQと2倍のUSDZARを同じ帯域セットで管理できる。velocity が必須である理由：health 0.40が1分あたり0.15で低下している場合は緊急事態であるが、health 0.22が6時間横ばいの場合はそうではない。 固定閾値ではこの2つを区別できない。これはまさに現在提供している単一の0.15ラインの障害モードである — ポジションが1週間かけて到達しても90秒で到達しても、同じ地点で発火してしまう。

ルールでは、すべての推奨事項がsooppiy.com AIの下す決定として提供されることになっている。T3はこれを破っているが、その理由は哲学的なものではなく、測定可能なものである。決定層のLLM呼び出しはp50で数秒だが、テールが太い――_light_analysisはその呼び出しをむき出しのexceptでラップし、"light cycle: no LLM verdict"にフォールバックする。まさにそのテールが存在するためである（run_engine.py:2094–2096）。3倍レバレッジでは、ヘルス0.15は、マークがエントリーから約5%離れた地点にあることを意味し、これは100%マージンワイプに相当する。そこで不確定な秒数を費やすことは、ネットワークの往復にマージン全体を賭けることになる。

したがって、区分は次の通りである：AIはT2までのすべての決定を担う。T2未満ではデーモンが動作し、AIの仕事はデーモンが行ったことを説明することになる。 各リフレックスはliq_reflexイベントを発生させ、それがそのランの次のサバイバルブリーフに供給される。これにより、デスクは自らのニアミスから学ぶことができ、それらから遮断されることがない。T3が頻繁に発火する場合、それはデスクがT1/T2で失敗している証拠であり、修正すべきはプロンプトであって、T3の定数ではない。

2026-07-30 — 構築後の修正であり、リフレックスは現在プロダクションでARMEDになっている。

1. 上記表のT3のアクションは誤りであり、構築することができない。 「ヘルス0.45を回復するのに十分な削減」は実現不可能である：分離マージンの下では、サイズqのポジションはエントリーEでレバレッジLにおいてq·E/Lを計上し、q·|P−E| = q·E/Lのときに清算される――qは打ち消し合うため、清算価格はサイズに全く依存しない。トリミングは失う可能性のある額を減らすが、得られる距離はゼロである。 LIQ_REFLEX_TARGET_HEALTHとLIQ_REFLEX_FLATTEN_FRACは実装されたことがなく、実装すべきでもない。リフレックスはフラット化するか、何もしないかであり、survival_brief これは今、デスクにそのことを率直に伝える。なぜなら、トリムすれば余裕ができると信じているデスクは、決済ではなくトリムを行ってしまうからだ。

2. 最初の実装は、手のない反射をリリースした。 PR #127はオラクル、ヘルススカラー、分類器、ヒステリシスをリリースしたが、reflex_action() 正しく返したのは"flatten" T3の時点で——out["reflex"] += 1、消費者のいないカウンターだった。ウォッチループは状態を記録し、周期を短縮し、エスカレーションを出力したが、注文は一度も出さなかった。 LIQ_REFLEX=true は何も決済していなかったはずだ。PR #130で修正され、T3をautomation.execute_paper_trade ——SL/TPウォッチャー自身のクローズプリミティブに接続した。これにより、反射的な決済は記録され、実行に帰属付けられ、他の強制決済と同様にアラートされるようになった。そしてこれにより、オーファン (run_id NULL)がそもそも決済可能になった。本番環境で唯一のレバレッジポジションは、まさにそのようなオーファンである。

3. 計画が想定していなかったガード。 価格ポーラーは約900秒周期で動作するが、このループは20秒周期で動作するため、T3の読み取りが15分も古いマークに基づく場合がある——ブリーフでは問題ないが、取り消せないフラット化では致命的だ。エグゼキューターはstale_mark (を超えて LIQ_REFLEX_MAX_STALE、300秒）、 cooldown (LIQ_REFLEX_RETRY、スタンプされた60秒、 前注文を出す（そうすることで、上昇するクローズがラッチを保持し続ける）、 no_owner, flat, no_markおよびmark_age_unknown。すべての拒否はジャーナルに記録される。拒否は興味深い記録である。なぜなら、それはデーモンが拒否している間にポジションがT3にあったことを意味し、その理由こそが、事後に正常に機能しているガードと壊れたエグゼキューターを見分ける唯一の手段だからである。

                           buys distance, keeps full upside
    hold                 - only if you can say what would change your mind

add_marginは独自の注記に値します。これは、reduce: マージンを追加で差し入れることでレバレッジを下げ、清算価格を遠ざける ポジションを何も手放さずに。自身の見立てを信じており、単に踏み上げられているだけのデスクは、ほぼ常にそれを選好するはずである。今日、デスクにはそれを表現する手段が一切ない——動詞が存在せず、レバレッジは実行作成時にティア表によって一度だけ設定され(fleet_planner.py:117)、その後は見直されない。これはAIが所有すべき意思決定であり、現在は名前すらつけられない。

その source:行も重要だ。次のように表示される場合、synthetic その旨をブリーフに明確に記載すべきである — 「この清算価格はレバレッジと想定維持証拠金からモデル化されたものであり、取引所から報告された値ではない」 — なぜなら、モデル化された数値をあたかも事実であるかのように伝えられたデスクは、不当な精度をもって行動することになるからだ。

8. これで解決しないこと

  • ギャップ。 値幅制限による寄り付きや週末の暗号資産の急落は、2回のサンプリングの間にあるすべてのバンドを飛び越えてしまう。どのような監視間隔であっても、不連続性を防ぐことはできない — 唯一の防御策は、エントリー時点の建玉サイズとレバレッジであり、それはfleet_plannerの管轄であって、このデーモンの管轄ではない。デーモンが保証と誤解されないよう、はっきり述べておく価値がある。
  • クロスマージン。 アイソレートとしてモデル化されている。シミュレートされた台帳では正しいが、実際のクロスマージン口座では誤りであり、その誤差は無限大になり得る。オラクルが実際のブローカーからアカウントレベルの状態を読み取れるようになるまで、クロスマージンのライブ口座は中途半端にモデル化するのではなく、拒否すべきである。
  • 初日にはブローカーが存在しない。 broker_accounts は本番環境では空であるため、フェーズ1〜4はすべて合成ソースのみで実行される。デーモンが発する内容はすべて synthetic というラベルが付けられ、そのラベルが実質的な役割を果たしている。
  • 古びたコメント。 fleet_planner.py:57–59 は、他の何よりも先にフェーズ1で修正すべきである。今これを読む者は、レバレッジが1倍で清算が延期されていると結論づけるだろうが、どちらも誤りである。
韓国語の詳細

なぜ必要か: 本番環境のポジション5件すべてが2〜3倍のレバレッジです。しかし清算防御は health = 0.15 という固定ラインが1本あるだけで(計算で証明済み — §2)、維持マージン・ファンディングレート・マーク価格・クロスマージンをすべて無視し、価格フィードが停止すると検査を スキップします。実際のブローカーアダプターにはマージンを読み取る関数自体が存在せず、Binanceアダプターは先物ではなく現物専用です。そしてAIデスクは、自分がレバレッジを使用しているという事実さえ認識していません。

設計: ① マージン状態オラクル(ブローカーAPI優先、なければMMR・ファンディング補正済みの合成値 — どちらであるかをAIにそのまま伝える) ② healthとその 速度 — 閾値だけでは「6時間目の0.22」と「毎分0.15ずつ下落する0.40」を区別できない ③ 4段階エスカレーション:T1・T2はAIが判断し reduce / close / add_margin / holdを直接選び、T3のみ機械的反射 ④ 20秒周期のデーモンで、ポジションテーブル基準のためrun_idのない孤児ポジション2件もカバー。

正直な例外: T3は意図的にルールです。3倍でhealth 0.15はマージン全額消滅までエントリー価格の5%しかありませんが、LLMの往復は秒単位で、裾は厚いです。代わりにT3が作動したら、その事実を次のブリーフィングに入れて、デスクが自分の失敗から学べるようにします。T3が頻繁に鳴るなら、それはT3定数を直す問題ではなく、プロンプトを直す問題です。

防げないもの: ギャップ(不連続なジャンプ)はどの周期でも防げません — エントリー時点のサイズ・レバレッジの問題であり fleet_plannerの仕事です。クロスマージンはアカウント単位の状態を読み取るまで、中途半端にモデリングせず拒否する方が正しいです。
