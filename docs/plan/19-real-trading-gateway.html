The hard part is already built. The execution layer shipped 2026-07-19 and has been hardened since:
  • Broker ABC (execution/base.py) — 4 methods: submit_order, get_order_status, cancel_order, get_broker_positions. A new venue is one subclass.
  • gateway.py — the rule's account_type is the only routing switch. Live is refused (never silently downgraded) without credentials + per-broker T&Cs consent. Endpoint pinning ensures shadow can never reach a real venue.
  • Credential vault — AES-GCM (execution/crypto.py, EXECUTION_ENCRYPTION_KEY), decrypt-tested before any live order routes.
  • Workers — order_reconciler (settles SUBMITTED orders against the venue's answer, journals drift, alerts the owner) and gateway_keepalive (IBKR session).
  • API + UI — routes_execution.py (accounts, mode switch, T&Cs accept, orders, reconciliations, health) and AccountsPage.tsx.
This plan is therefore adapter work plus regional plumbing, not a new execution engine.

Two structural consequences fall out of this table.
  1. Credentials are no longer always key+secret. OKX and KuCoin add a passphrase. The vault already stores an arbitrary encrypted JSON blob (IBKR proved it), but routes_execution.CreateBrokerAccountRequest validates fields per broker — that validator grows a per-broker required-fields map.

4 · Architecture — what changes, what stays

5 · The shadow problem — three strategies, per venue

Shadow mode today assumes every broker has a sandbox. The fact sheet shows that assumption dies with this expansion: Kraken, Upbit, KuCoin and bitFlyer have no usable spot sandbox. Rather than faking one, each adapter declares which of three shadow strategies it supports — and the router records which one produced each reconciliation row.

↓

↓

↓
Venue checks auth, symbol, size, balanceno order is placed, no fill exists
↓

C · Journal-only shadow

No network call at allupbit · bitFlyer — nothing safe to hit
↓
Record intended order + live book pricevia price_fetcher at decision time
↓

Invariant kept from gateway.py: a shadow rule must never reach a real venue with an order that can fill. Strategy B touches the live endpoint but only through the venue's own validate/test call — the request is provably unfillable by construction. Strategy C makes no call at all. Nothing here relaxes the endpoint-pinning rule; it refines it per venue.

6 · Key design decisions

6.1 · One registry, declarative per-broker metadata

AVAILABLE_BROKERS stays the single source of truth (the market-registry lesson: hand-maintained parallel lists rot). It grows from a tuple of names into a small table consumed by both the request validator and the router factory:

BROKER_SPECS = {
  "binance":   Spec(fields=("key","secret"),              shadow="sandbox",  quote="USDT"),
  "bybit":     Spec(fields=("key","secret"),              shadow="sandbox",  quote="USDT"),
  "okx":       Spec(fields=("key","secret","passphrase"), shadow="sandbox",  quote="USDT"),
  "kraken":    Spec(fields=("key","secret"),              shadow="dry_run",  quote="USD"),
  "cryptocom": Spec(fields=("key","secret"),              shadow="sandbox",  quote="USDT"),
  "upbit":     Spec(fields=("key","secret"),              shadow="journal",  quote="KRW"),
  "kucoin":    Spec(fields=("key","secret","passphrase"), shadow="dry_run",  quote="USDT"),
  "alpaca":    Spec(fields=("key","secret"),              shadow="sandbox",  quote="USD"),
  "ibkr":      Spec(fields=("gateway_url","account_id"),  shadow="sandbox",  quote="USD"),
}

6.2 · Symbol normalisation lives in the adapter, canonical form lives in the platform

The platform keeps speaking BTC/USDT-style canonical symbols. Each adapter owns a two-way mapper: BTCUSDT (Binance/Bybit) · BTC-USDT (OKX/KuCoin) · BTC_USDT (Crypto.com) · XBTUSD (Kraken — including the XBT rename) · KRW-BTC (Upbit — quote-first ordering). The mapper is required for get_order_status too: the Binance adapter already proved a lookup with the wrong symbol form reports "order does not exist".

6.3 · Upbit's market-order quirk is a first-class case, not a patch

Upbit market buys are priced in KRW cost (ord_type=price), market sells in asset volume (ord_type=market). The Order dataclass carries quantity; the Upbit adapter converts quantity→cost using the decision-time price for buys, and the reconciler reads back the actual filled volume from the order lookup. This asymmetry is exactly the kind of thing the drift journal exists to catch — the adapter must never pretend the requested and filled quantities are the same number.

6.4 · Non-USD quotes get an explicit FX step

The ledger is USD-denominated. For KRW (and later JPY) venues, the adapter records the fill in venue currency and the FX rate used, on the broker_orders row (two new nullable columns: quote_currency, fx_rate_usd). Conversion happens once, at fill-recording, from a rate captured at that moment — never recomputed later (the NaN-poisoning and drift lessons both say: persist what you used). Reconciler drift compares in venue currency, so FX noise can't masquerade as fill drift.

6.5 · Pre-flight validation against venue trading rules

Every venue enforces min-notional / lot-size / price-precision. Each adapter fetches its venue's instrument rules (exchangeInfo-equivalents), caches them in-process with a daily TTL, and rejects a non-conforming order before submission with an i18n-routed error (per the i18n sweep rule: every user-visible refusal goes through the catalogue). A predictable local rejection beats a venue rejection string the user can't read.

6.6 · Kraken nonces need a per-account monotonic source

Kraken invalidates a key on nonce regression, and prod runs a worker plus an API process. The Kraken adapter takes nonces from a DB-backed monotonic counter per broker account (single UPDATE … RETURNING-style bump), not time.time() — two processes sharing a key would otherwise race and permanently error the key.

6.7 · Region-aware Accounts UI, no geo-blocking

GET /api/execution/brokers grows an optional ?region= parameter returning the matrix in §2 (recommended-first ordering). The frontend shows "recommended for your region" grouping on AccountsPage.tsx; every venue stays connectable regardless of region. Region source: user's existing language/locale setting as a default, user-overridable.

8 · Safety rails for live money

  1. Per-venue live allowlist. LIVE_BROKER_ALLOWLIST (env, default: alpaca,binance,ibkr — today's set). A new adapter can shadow immediately but cannot take live orders until its name is added post-soak. Checked inside live_refusal_reason so refusal messaging is consistent and nothing downgrades silently.
  2. Per-order notional cap for new venues. EXECUTION_MAX_ORDER_USD (default 1,000) applies to any venue in its first 30 allowlisted days. (2026-11-24: per-venue defaults now exist — Webull $1,500 — and EXECUTION_MAX_ORDER_USD_<BROKER> overrides one venue; the platform-wide variable, when set, still overrides every venue's default.) Caps are refusals, not resizes — resizing an order the AI sized is a silent decision change (Plan 17 rails logic).
  3. T&Cs stay per-broker. broker_live_optins is already keyed by broker string — each new venue automatically requires its own explicit "this is real money" acceptance. No change needed; a test asserts a Bybit opt-in does not unlock OKX.
  4. Reconciler coverage is a merge gate. get_order_status is optional in the ABC for historical reasons; for new adapters it is mandatory — an adapter PR without a working status lookup does not merge, because SUBMITTED orders would never settle (§ the order-drift alert path depends on it).
  5. Kill switch. Emptying LIVE_BROKER_ALLOWLIST halts all live routing platform-wide with an explicit refusal — one env var, no deploy.

9 · Testing & verification

  • Signature unit tests — every adapter's signing function verified against the venue's published example vectors (Kraken and OKX both document one), with mocked httpx. Sockets blocked in the suite: the quant-crypto leak taught that try/except-wrapped fetches hide missing mocks.
  • Contract tests shared across adapters — one parametrised suite runs every adapter through: reject-without-credentials, symbol round-trip, status-map completeness (every venue state maps to an OrderStatus), part-fill settlement, error-never-raises.
  • Testnet integration scripts — research/-style manual scripts per sandbox venue, run before each soak starts; not in CI (external, flaky, credentialed).
  • Mutation pass — per repo standard: flip the allowlist check, swap Upbit's ord_type mapping, break a symbol mapper — confirm tests fail before reporting coverage.
  • Soak = monitoring, not a checkbox — the automation-monitoring cadence watches position_reconciliations per venue; the acceptance percentages in §7 are measured there, on prod.

2026-08-01 sandbox-sweep finding — server geography blocks two venues. The per-venue sandbox verification (research/gateway_sandbox_check.py, run from the production server itself) found that Binance and Bybit geo-block the prod server's US AWS IP: Binance answers HTTP 451 / “service unavailable from a restricted location”, Bybit's CDN blocks the country outright — on both their live and test environments. Every other venue (OKX, Kraken, Crypto.com, Upbit, KuCoin, Alpaca) is fully reachable from prod and each adapter's signed request path was verified against the real endpoint (venue auth-rejections surfaced cleanly through the adapter). Consequences: the Binance live path in the legacy allowlist cannot actually execute from this server, and Bybit's P1 sandbox soak cannot run from it either — orders would refuse loudly with the venue's message (no silent failure, no fake fill). Options for the owner: route execution egress through a non-US region (proxy or a small relay in ap-northeast), or drop Binance/Bybit from the recommended matrix for now. Until decided, both venues stay connectable but their soaks are blocked on infrastructure, not code.

11 · 한국어 요약

목표. 현재 3개(alpaca·binance·ibkr)인 실거래 게이트웨이 어댑터를 지역별 수요에 맞춰 9개로 확장합니다 — Bybit, OKX, Kraken, Crypto.com, Upbit, KuCoin 추가(일본 현지 거래소는 P4에서 bitFlyer부터 타당성 평가). Revolut은 공개 트레이딩 API가 없어 제외합니다.

핵심 판단. 실행 엔진(라우터·게이트웨이·AES-GCM 자격증명 금고·정합성 워커)은 이미 완성되어 있으므로, 이 계획은 새 엔진이 아니라 어댑터 추가 + 지역 배관 작업입니다. 거래소별로 인증 방식(HMAC 변형, OKX/KuCoin의 passphrase, Upbit의 JWT), 심볼 표기(BTCUSDT/BTC-USDT/XBTUSD/KRW-BTC), 그리고 샌드박스 유무가 전부 달라 — 어댑터마다 셋 중 하나의 섀도 전략(샌드박스 / 검증전용 dry-run / 기록전용 저널)을 선언합니다.

업비트가 가장 까다롭습니다. 샌드박스·드라이런이 전혀 없고, KRW 호가라 원장(USD)에 FX 환산 단계가 필요하며, 시장가 매수는 수량이 아닌 KRW 금액으로 주문하는 비대칭이 있습니다. 그래서 한국(P2)을 별도 페이즈로 분리하고 저널 소크 기간을 14일로 2배 잡았습니다.

안전장치. ① 거래소별 라이브 허용목록(LIVE_BROKER_ALLOWLIST) — 소크 통과 전에는 새 거래소로 실주문 불가, ② 신규 거래소 첫 30일 주문당 명목금액 상한(축소가 아닌 거부), ③ 거래소별 실거래 약관 동의(기존 구조 그대로), ④ 상태조회(get_order_status) 미구현 어댑터는 머지 불가, ⑤ 허용목록 비우기 = 전체 킬스위치.

일정. P0 배관(~2일) → P1 글로벌 bybit·okx·kraken(~5일+7일 소크) → P2 업비트(~4일+14일 소크) → P3 kucoin·crypto.com(~4일+7일 소크) → P4 일본 평가+지역별 UI(~3일). 소크는 다음 페이즈 개발과 병행 — 달력 기준 약 5주, 실작업 약 18일. 모든 페이즈는 표준 규칙대로 prod(sooppiy.com)까지 배포하되 신규 거래소는 소크 통과 전 라이브 게이트 OFF 상태로 배포합니다.
