5. Skill lifecycle — base vs custom

Catalogue sync (2026-08-02): when the original base skill is updated in the catalogue, every prod row still exactly as the catalogue last wrote it upgrades automatically on the next registry read — a fingerprint (catalog_hash) tells the two apart. A row an admin has edited stops matching and keeps the edit until an explicit reset, which also re-arms auto-upgrade. Disabling a skill is operator state, not an edit: a disabled untouched skill still receives body upgrades and stays off.

6. Safety layers — why prompt text can't reach an order directly

Skill bodies are admin-authored only in v1 and size-capped twice (4,000 per body at the route, 30,000 per prompt at the builder). Even a hostile body cannot bypass layers 2–4 — they run outside the prompt.

DELETE /api/admin/skills/{slug}remove custom skillbase → 400 "disable or reset instead"

Every write is recorded in admin_audit_log (skill.create / update / reset / delete) and invalidates the API process's cache immediately. The worker is a separate process: it converges through the registry's 30-second TTL — an edit reaches the next decision cycle within ~30 s, and a running fleet picks it up on its next cycle (v1 deliberately does not freeze skills per run; see the design doc's non-goals).
