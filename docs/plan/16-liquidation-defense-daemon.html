Plan 16 — Liquidation Defense Daemon

An AI daemon that monitors forced-liquidation risk on leveraged positions and acts on it, using the user's own broker API key. Algorithm, flow, and diagrams.

Written 2026-07-29. Every claim below is anchored to a file/line in the current codebase or to a query run against production MySQL. Ships to prod sooppiy.com per standing rule.

요약 (Korean summary)

강제청산(force liquidation)은 지금 이론이 아니라 실제 리스크입니다. 프로덕션의 열린 포지션 5개 전부가 2배 또는 3배 레버리지를 쓰고 있습니다. 그런데 현재 방어 수단은 _evaluate_stop 안의 고정 임계값 하나뿐이며, 그 임계값은 유지증거금(MMR)·펀딩비·마크가격·크로스마진을 전혀 계산하지 않고, AI에게는 아무것도 알려주지 않으며, 실거래 브로커 경로에는 마진 상태를 읽는 기능 자체가 없습니다. 이 문서는 (A) 마진 상태 오라클, (B) health = (마크−청산)/(진입−청산) 라는 단일 척도와 그 속도, (C) 4단 에스컬레이션 — T1·T2는 AI가 판단하고 T3만 기계 반사, (D) 20초 주기 데몬을 설계합니다. 정직한 예외를 하나 명시합니다: T3는 의도적으로 룰입니다. health 0.15에서 LLM 왕복은 마진 전체를 걸고 하는 도박이기 때문입니다.

2. Why the current check is not a liquidation model

There is exactly one liquidation defence in the codebase: the cushion branch inside _evaluate_stop. Its structure is a single fixed fraction of the distance to liquidation. Work out what that fraction means in health terms — for a short, the cushion fires when mark = entry(1 + c/L) and liquidation is at entry(1 + 1/L), so

health = (liq − mark) / (liq − entry)
       = (entry(1+1/L) − entry(1+c/L)) / (entry(1+1/L) − entry)
       = (entry(1−c)/L) / (entry/L)
       = 1 − c  =  0.15        (and the long case is symmetric)

So today’s entire liquidation defence is one fixed line at health = 0.15. Leverage-independent, instrument-independent, and — the part that matters — it has no idea how fast the position is travelling. It also has five specific omissions, four in the maths and one in the plumbing.

#Omitted termDirection of the errorSize at 3×
1Maintenance margin rate (MMR). Exchanges liquidate when equity falls below maintenance margin, not when it hits zero. Binance USDⓈ-M tiers MMR by notional (0.4%–12.5%).optimistic real liquidation arrives earlier than we model≈ 0.5% of entry
2Funding. A perp pays or receives funding every 8h. Our model has no funding term at all, so margin can erode toward liquidation on a completely flat tape and the model will never see it.optimistic and it grows with holding time0.001–0.01 health/day
3Mark price vs last price. Exchanges liquidate on an index-anchored mark; we compute on positions.current_price, a poll of last trade.both ways diverges most during the wicks that liquidate peopleinstrument-dependent
4Cross-margin coupling. In a real cross-margined account another position’s loss moves this position’s liquidation price. Our model is isolated-per-position by construction.optimistic unbounded in the worst casen/a — not modelled
5Staleness handling is inverted. The whole liquidation block sits inside if has_position and pnl["mark_age_ok"]: (run_engine.py:860). On stale marks the check is skipped. The stale-mark RuntimeError below it (line 893) pauses entries and alerts, but never closes anything.structural a leveraged position with a dead price feed is carried unmonitored, with no exit path—

And the sixth, which is the one that matters most for this project’s premise: the AI is never told any of it. The desk’s prompt (_light_analysis, run_engine.py:2054–2089) contains the symbol, the price, the position quantity, the thesis, ten closes, and — since PR #124/#125 — the position’s P&L trajectory. It contains no leverage, no liquidation price, no margin, no funding. The desk cannot reason about survival because it does not know it is leveraged.

3. The algorithm — five stages

Stage A — Margin State Oracle (new: service/server/liquidation.py)

One function, one shape, two possible sources. Add an optional capability to the Broker ABC, following the exact pattern get_order_status already uses (default returns None = “cannot look up”, never raises for expected errors — execution/base.py:104–118):

async def get_margin_state(self) -> Optional[list[dict]]:

When no broker can answer — which is every case on day one, since broker_accounts is empty in prod — fall back to a synthetic state that fixes omissions 1 and 2 and labels itself honestly:

long :  liq = entry × (1 − 1/L + mmr) + funding_accrued_per_unit
short:  liq = entry × (1 + 1/L − mmr) − funding_accrued_per_unit
        source = "synthetic",  confidence = "modelled"

mmr comes from a per-market table (crypto-perp notional tiers; a SPAN approximation for exchange futures; the broker default for forex), and funding_accrued_per_unit is summed from observed funding events for the holding period. The source field is not decoration — it is passed to the AI verbatim, so the desk knows whether it is being told a fact or an estimate.

Stage B — one scalar, and its derivative

long :  health = (mark − liq) / (entry − liq)
short:  health = (liq − mark) / (liq − entry)

velocity = Δhealth / Δt          (least-squares slope over the last N samples)
ttl      = health / max(ε, −velocity)      # time to liquidation at this rate

Why normalise rather than threshold on price or P&L: health is 1.0 at entry and 0.0 at liquidation for every instrument, every leverage, and both directions, so one set of bands governs MNQ at 3× and USDZAR at 2× without per-market tuning. Why velocity is not optional: health 0.40 falling 0.15/min is an emergency; health 0.22 flat for six hours is not. A fixed threshold cannot distinguish those two, and that is precisely the failure mode of the single 0.15 line we ship today — it will fire at the same place whether the position drifted there over a week or arrived in ninety seconds.

Stage C — four tiers, and an honest exception

T3 is a rail, deliberately — and this is the one place I am arguing against the standing rule.

The rule is that every recommendation ships as a decision the sooppiy.com AI makes. T3 breaks it, for a reason that is measurable rather than philosophical. A decision-tier LLM call is a few seconds at p50 with a fat tail — _light_analysis wraps its call in a bare except and falls back to "light cycle: no LLM verdict" precisely because that tail exists (run_engine.py:2094–2096). At 3× leverage, health 0.15 means the mark is about 5% of entry away from a 100% margin wipe. Spending an uncertain number of seconds there is betting the entire margin on a network round-trip.

So the split is: the AI owns every decision down to T2. Below T2 the daemon acts, and the AI’s job becomes explaining what the daemon did. Every reflex emits a liq_reflex event that is fed into that run’s next survival brief, so the desk learns from its own near-misses instead of being shielded from them. If T3 fires often, that is evidence the desk is failing at T1/T2 and the fix belongs in the prompt — not in T3’s constants.

Stage D — the daemon loop (tasks.py: liquidation_watch_loop)

Same shape as risk_watcher_loop (tasks.py:863–889): an async loop, an _env_int interval, a thread hop for the blocking work, and a bare except so one bad tick cannot kill the worker.

LIQ_WATCH_INTERVAL      = 20s     # tighter than risk_watcher's 30s and the
                                  # ~60s run-control scan: this is the one loop
                                  # whose tail cost is the entire margin
LIQ_WATCH_INTERVAL_HOT  = 5s      # once ANY position is at T2 or worse
LIQ_DEESCALATE_SAMPLES  = 3       # hysteresis: only de-escalate after 3
                                  # consecutive samples one band better

Hysteresis is not a nicety. Without it a single wick flaps the tier, and a flapping tier means the desk is woken out of band repeatedly for the same position — which trains everyone, human and model, to ignore the alert.

Stage E — scope on positions, not runs

Positions 67 (SOLUSDT, 2×) and 69 (USDZAR, 2×) have run_id NULL. _evaluate_stop only ever runs for a position attached to a running run, so neither of those is liquidation-checked by anything today. The daemon must iterate the positions table filtered on leverage > 1, which is the only scope that covers the whole book — attached, orphaned, and manual alike.

6. What the AI is told — the survival brief

This is the part that follows the standing rule, and it is the difference between a daemon that manages liquidation risk for the desk and one that lets the desk manage it. Prepend to the prompt whenever leverage > 1:

MARGIN STATE (source: broker)
  Leverage 3.0x, isolated. Liquidation at 36,719.83; mark 35,900.00.
  Health 0.31  (1.0 = your entry price, 0.0 = margin fully wiped).
  Velocity -0.22 health/hour over the last 3 samples.
  Time to liquidation at this rate: 84 minutes.
  Funding: you PAY 0.011% every 8h on 82,331 notional = $9.05/day,
    which costs 0.033 health per day even if price never moves.
  Recent: 0 reflex actions on this position.

  DEADLINE: reply within 45s or the risk daemon will reduce this
  position for you to health 0.45. Your options:
    reduce  (size_frac)  - shed exposure, keep the thesis alive
    close                - out entirely
    add_margin (to L=n)  - deleverage without reducing exposure;
                           buys distance, keeps full upside
    hold                 - only if you can say what would change your mind

add_margin deserves its own note. It is a genuinely different answer from reduce: it lowers leverage by posting more margin, which moves the liquidation price away without giving up any of the position. A desk that believes its thesis and is merely being squeezed should almost always prefer it. Today the desk cannot express it at all — there is no verb, and leverage is set once by the tier table at run creation (fleet_planner.py:117) and never revisited. That is a decision the AI should own and currently cannot even name.

The source: line matters too. When it reads synthetic the brief should say so plainly — “this liquidation price is modelled from leverage and an assumed maintenance margin, not reported by a venue” — because a desk told a modelled number as though it were a fact will act with unearned precision.

Verification plan

  1. Algebraic: assert health(cushion price) == 1 − RUN_LIQ_CUSHION_FRAC for both directions and a range of L. This pins the new scalar to the shipped behaviour and would catch a sign error immediately.
  2. Replay: reconstruct the health series from the recorded equity telemetry + position rows and confirm the tier classifier never crosses T2 on history. If it does, the bands are wrong and must be re-derived before shipping — not after.
  3. Injection: synthesise a decaying mark on a copy of a real position and assert each band fires once, in order, with hysteresis holding across a wick.
  4. Mutation: break each of the five omissions back in (drop the MMR term, drop funding, restore the mark_age_ok skip) and confirm a test fails for each. Per house rule, a green suite proves nothing until the bugs have been re-injected — and clear __pycache__ inside the runner, or a same-length restore will import the mutated .pyc.
  5. Deadline: stub the LLM to sleep past LIQ_DESK_DEADLINE_S and assert T3 takes over exactly once, with the reflex journalled.

8. What this does not fix

  • Gaps. A limit-down open or a weekend crypto cascade jumps through every band between two samples. No monitoring cadence defends against a discontinuity — the only defence is position size and leverage at entry, which belongs to fleet_planner, not to this daemon. Worth stating plainly so the daemon is not mistaken for a guarantee.
  • Cross-margin. Modelled as isolated. Correct for our simulated ledger, wrong for a real cross-margined account, and the error is unbounded. Until the oracle reads account-level state from a real broker, a cross-margined live account should be refused rather than half-modelled.
  • Day one has no broker. broker_accounts is empty in prod, so phases 1–4 run entirely on the synthetic source. Everything the daemon says will be labelled synthetic, and that label is doing real work.
  • The stale comment. fleet_planner.py:57–59 should be corrected in phase 1 regardless of anything else here. Someone reading it today would conclude leverage is 1× and liquidation is deferred, and would be wrong on both counts.

왜 필요한가: 프로덕션 포지션 5개 전부가 2~3배 레버리지입니다. 그런데 청산 방어는 health = 0.15 고정선 하나뿐이고(계산으로 증명 — §2), 유지증거금·펀딩비·마크가격·크로스마진을 모두 무시하며, 가격 피드가 멈추면 검사를 건너뜁니다. 실거래 브로커 어댑터는 마진을 읽는 함수 자체가 없고 Binance 어댑터는 선물이 아니라 현물 전용입니다. 그리고 AI 데스크는 자기가 레버리지를 쓰고 있다는 사실조차 모릅니다.

설계: ① 마진 상태 오라클(브로커 API 우선, 없으면 MMR·펀딩 보정한 합성값 — 어느 쪽인지 AI에게 그대로 알려줌) ② health와 그 속도 — 임계값만으로는 “여섯 시간째 0.22”와 “분당 0.15씩 떨어지는 0.40”을 구분할 수 없음 ③ 4단 에스컬레이션: T1·T2는 AI가 판단하고 reduce / close / add_margin / hold를 직접 고름, T3만 기계 반사 ④ 20초 주기 데몬, 포지션 테이블 기준이므로 run_id가 없는 고아 포지션 2건도 커버.

정직한 예외: T3는 의도적으로 룰입니다. 3배에서 health 0.15는 마진 전액 소멸까지 진입가의 5%뿐인데, LLM 왕복은 초 단위이고 꼬리가 두껍습니다. 대신 T3가 작동하면 그 사실을 다음 브리핑에 넣어 데스크가 자기 실패로부터 배우게 합니다. T3가 자주 울리면 그건 T3 상수를 고칠 문제가 아니라 프롬프트를 고칠 문제입니다.

못 막는 것: 갭(비연속 점프)은 어떤 주기로도 못 막습니다 — 진입 시점의 사이즈·레버리지 문제이고 fleet_planner의 일입니다. 크로스마진은 계좌 단위 상태를 읽기 전까지 반쯤 모델링하지 말고 거부하는 편이 맞습니다.
