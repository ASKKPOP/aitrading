1 · The request, and how this plan reads it

Owner request (verbatim): “Make plan (report html for me with visualization + flow + dialog) for future when Buying and when selling strategies, each slot, every 1 hours update that and then do 30 min for usa stock, crypto, forex.”

Owner follow-up (mid-planning, verbatim): “each slot keep that plan , sooppiy AI use that strategies after analysis each 30min.” This upgrades the feature from a report to a closed loop: the plan is kept as the slot’s standing strategy, and the desk consumes it in every 30-minute analysis — follow it, revise it, or deviate with a stated reason (§3.6). This also matches the standing AI-FIRST rule: the plan is trading logic the sooppiy AI itself runs, not just a page for humans.

Owner clarification (verbatim): “It's for make positive profit — when it will buy (entry zone/trigger), when it will sell (target, stop reference, time exit).” The feature’s goal is therefore plus net profit, and it is judged in realized-P&L terms — not adoption, not page views, not “the report renders.” §3.7 states exactly which measured loss classes the kept plan attacks and how the profit verdict is made; if plan-following cycles do not add expectancy, the logic is garbage by the standing owner law and the flag comes off.

Reading adopted by this plan — for each fleet slot, the desk AI publishes a forward strategy: under what conditions it will buy (entry zone / trigger) and under what conditions it will sell (target, stop reference, time exit), plus its reasoning. Users see it as a per-slot report with a visualization (levels on price), a flow (how the plan was produced), and the desk’s dialog (its cycle-by-cycle reasoning). Freshness: refreshed at least hourly for every slot, and at least every 30 minutes for us-stock, crypto, and forex.

Ambiguity noted. “every 1 hours … and then do 30 min for usa stock, crypto, forex” has a second possible reading: one hourly full report plus a separate lightweight 30-minute delta for those three markets. The adopted reading (per-market freshness floors: 30 min for the three named markets, 60 min for the rest — today that rest is futures and prediction) is simpler and strictly satisfies both readings’ intent. If the two-artifact reading was meant, only Phase 2 changes — say so and the cadence table in §4 is re-cut.

3 · Feature design

3.1 · The outlook object (what “when to buy / when to sell” means, precisely)

The model’s decision JSON gains one sibling object. It is the slot’s standing plan: kept per slot, read back into the desk’s next analysis (§3.6), and shown to users. It never mechanically touches stop_conditions, order params, or any rail (§5 guards) — its influence flows only through the desk’s own next decision, so the AI remains the author of every order.

"outlook": {
  "bias":        "long" | "short" | "flat",
  "entry":  { "kind": "zone" | "trigger" | "none",
              "low": 2.98, "high": 3.04,            // buy/add zone (px)
              "trigger": "reclaim of 3.10 on volume" },
  "exit":   { "target_px": 3.42,                    // when it will sell (profit)
              "stop_ref_px": 2.86,                  // when it will sell (defense) — the EXISTING stop, echoed
              "time_exit": "2026-08-16T14:00Z" },   // or null
  "invalidation": "daily close below 2.86 kills the long thesis",
  "horizon_hours": 18,
  "narrative": "Two sentences of forward reasoning, in the desk's voice.",
  "basis": {                                        // the LLM ⇄ algorithm discussion record
    "algo": { "entry_low": 2.99, "entry_high": 3.04, "target_px": 3.38,
              "stop_ref_px": 2.86, "time_exit": "2026-08-16T14:00Z" },
    "verdict": "adopted" | "adjusted" | "overridden" | "algo_fallback",
    "discussion": "why the final targets beat (or keep) the algorithmic candidate (≤300)" }
}

The discussion (owner directive): the LLM and the deterministic algorithm must discuss which targets are best — neither is simply trusted. A pure function (algo_candidate) derives a candidate plan from the thesis block: expected-move levels floored at the 2.40% fee hurdle, a pullback entry band, the existing stop echoed, horizon as time exit. That candidate goes into the prompt; the desk must adopt, adjust, or override it with a stated reason, and both sides plus the verdict are stored in basis. If the LLM is unavailable (sweeper fallback), the candidate becomes the plan with verdict algo_fallback — the schedule never slips.

Numeric fields are clamped and NaN-scrubbed at parse (NaN in a persisted JSON column permanently 500s reads — known trap). stop_ref_px is an echo of the live stop for display; the write-once stop rule is untouched.

3.5 · Dialog — the desk’s reasoning, per slot

The dialog view is a chronological read of the slot’s run_events tail — existing decision.report lines interleaved with the new outlook.narrative lines. Nothing new is written for it; it is a read-side composition (same idea as desk_cycles.py). Mock of the UI:

Holding the FIL short. Momentum quality is intact and the bounce stalled under 3.12; no add — book is at size.
Desk · outlook 14:00 forward plan
Sell-side (cover): take profit into 2.80–2.96. Buy-side: no add unless 3.10 rejects again on volume. Invalidation: daily close above 3.47 (stop ref). Horizon ≈ 18 h.
Platform 14:22

Reduce 25% — tape printed a higher low on rising volume; keeping the core short against 3.47. Consistent with the 14:00 standing plan (no add below a 3.10 reclaim).

Desk-authored bubbles are localized via the existing write-time-warm path; platform events render from the fixed-phrase catalogue (desk_i18n_data.py). Close-reason taxonomy stays intact: AI-decided vs platform-forced authorship is visually distinguished (left border + label), matching the two-axis attribution rule.

3.6 · The closed loop — each slot keeps its plan, and the AI uses it every 30-min analysis

Per the owner follow-up, the plan is kept and consumed, not write-and-forget. Three small mechanisms, all copies of existing patterns:

  1. Keep: the slot’s standing plan is the newest outlook event for its bound run (read by ts). No new table: run_events is already the durable, ordered store, and history is the audit trail of every plan revision for free.
  2. Feed back: a new brief line standing_plan in _compose_position_state (run_engine.py:3795-3824 — one (name, line) tuple + one _standing_plan_line() helper) renders the kept plan compactly into every analysis prompt: “Your standing plan (14:00): short bias · cover 2.80–2.96 · no add unless 3.10 reclaims · invalidation daily close > 3.47 · horizon 18h.” The desk therefore sees its own plan on every 30-minute cycle before deciding.
  3. Discipline: a new base trading skill (trading_skills.BASE_SKILLS, trading_skills.py:160, rendered via skills_block :2177) instructing: trade your standing plan; revise it deliberately each cycle; if this cycle’s action contradicts it, say so and why. The decision JSON gains "plan_adherence": "followed" | "revised" | "deviated", stored on the decision event — so every outcome carries its plan-vs-action reason (this is exactly the per-trade-reason discipline the monitoring law demands, and it becomes measurable: adherence vs realized P&L).
Why prompt-feedback and not a mechanical executor: the desk stays the author of every order (handoff §7b). The plan constrains and informs the AI’s next decision; it never bypasses it. A mechanical “execute the plan” engine would recreate the forced-close class of losses the close-reason taxonomy exists to separate — and would violate the write-once stop rule the moment a plan revision implied a wider stop.

3.7 · The profit mechanism — what the kept plan attacks, and how the verdict is made

The goal is plus net profit. Concretely, a pre-committed buy-side and sell-side attacks loss classes that were measured on this platform, not hypothesized:

Measured loss classHow the kept plan attacks it
Full-book dumps on sub-2% ordinary moves — a handful of 100%-of-book exits on small moves carried most of one measured loss window The sell-side is pre-committed (target / stop ref / time exit). “Dump everything now” becomes a deviation from the kept plan that the desk must argue against its own written invalidation — on an ordinary-day move with the invalidation intact, the plan’s answer is reduce or hold, not a full dump.
Chased entries and adds into strength — adds into losers and ungated short adds were each worth a shipped gate (#79, #118) The buy-side exists before the tape moves: entry only in the pre-stated zone or on the pre-stated trigger. An add outside the plan is a recorded deviated with a reason — visible per trade, measurable in aggregate.
Fee-hurdle churn — the flat fee needs ≈2.40% of favorable move to break even A plan whose target sits closer than the fee hurdle is self-refuting on paper, before any order: target−entry distance is checkable at parse time and surfaces in the panel. Today that arithmetic only exists inside build gates; the plan makes it visible per slot, every cycle.
Unexplained exits — the monitoring law demands the reason behind every outcome; free-text report alone made that reconstruction manual plan_adherence (followed / revised / deviated) stamps every decision with plan-vs-action, so outcome analysis becomes a query, not archaeology.
Honesty clause — what the plan cannot fix. When the churn theory was actually measured, ~92% of that loss window was gross price movement — direction was wrong, not execution. A kept plan buys exit discipline and entry selectivity; it does not make the thesis right. Directional quality remains thesis/ranking/research work, and this plan must not be reported as fixing it.

The verdict procedure (profit-or-loss terms first): after 7 trading days live, replay the ledger via pnl_audit (forced flattens included — raw adapt-realized misses them) split by plan_adherence. Pass = expectancy per trade at or above the pre-flag baseline, and plan-following cycles not underperforming deviations. Fail = OUTLOOK_ENABLED=0 (prompt reverts to its pre-plan shape instantly) and the plan logic is revised — a small favorable delta on a large loss is not improvement and will not be reported as one. The same replay also splits by basis.verdict: if algorithmic candidates outperform LLM-adjusted targets — or the reverse — that measured difference, not anyone’s preference, decides which author leads the next iteration. “Which is the best target” is answered in realized P&L.

5 · Risks, guards, and non-goals

Hard boundary — through the desk, never around it. The standing plan reaches trading exclusively as prompt context for the desk’s own next decision (§3.6). No code path executes a plan mechanically: it never writes stop_conditions, never feeds order_params, never widens a stop (write-once at open), and never routes through the execution gateway. The AI remains the final author of every order. Grep-verified in Phase 1 and again at review.
  • Token cost: ~120–180 extra output tokens per cycle. Both desk tiers currently run on local, so marginal cost ≈ 0 today; if a paid tier returns, the 64%-unattributed-spend gap applies to this too — the outlook rides the same LlmContext as the decision call, adding no new attribution hole.
  • Prompt budget: the outlook contract adds one paragraph to the light prompt; the 21-line brief journal is untouched. If the 48k skills budget tightens, the outlook instruction is the first candidate to compress, not the brief.
  • run_events volume: +1 row per cycle per run plus sweeper rows — same order of magnitude as decision; the (event_type, ts) index already covers the read path.
  • Non-goal (this plan): feeding outlooks into the Plan-22 desk-memory RAG corpus. Natural follow-up — the outcome-vs-outlook delta is exactly the “reason behind every trade’s outcome” the monitoring law demands — but it is its own ingestion pass (desk_memory_ingest.py) and ships separately.
  • Non-goal: a standalone exported HTML file per slot. The report surface is the in-app panel + API; build_guide_content.py is a build-time doc generator, not a runtime renderer, and cloning it for per-slot state would be speculative.
