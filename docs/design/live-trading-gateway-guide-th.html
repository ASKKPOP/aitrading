เส้นทางทั้งหมดที่กฎการเทรดอัตโนมัติ จำลอง(simulator) → เงา(shadow) → เทรดจริง(live) เชื่อมต่อกัน: ต้องตั้งค่าอะไรบ้าง คำสั่งซื้อขายผ่านด่านตรวจใดบ้าง และระบบไม่ทำอะไรเด็ดขาด อธิบายไว้ในเอกสารฉบับเดียว

01โหมดการทำงานทั้งสาม / สามโหมดการทำงาน

การตั้งค่า บัญชี(account) เพียงจุดเดียวในกฎ (หน้า Automation) เป็นตัวกำหนดว่าการจับคู่คำสั่งจะไปลงเอยที่ใด ไม่มีการตั้งค่าอื่นใดเปลี่ยนแปลงสิ่งนี้ได้

โหมดตำแหน่งที่จับคู่คำสั่งเงินทุนจริงเงื่อนไขที่ต้องมีวัตถุประสงค์
จำลอง บัญชีจำลองของแพลตฟอร์มเท่านั้นไม่มีไม่มี (ค่าเริ่มต้น) ตรวจสอบกลยุทธ์, เรียนรู้แพลตฟอร์ม
เงา บัญชีจำลอง(อ้างอิง) + คำสั่งเทียบกับโบรกเกอร์ แซนด์บ็อกซ์ไม่มี การเชื่อมต่อเกตเวย์ (ทางเลือก — หากไม่มีจะเป็นจำลองล้วน) เปรียบเทียบ slippage และอัตราการจับคู่คำสั่งจริงโดยไม่มีความเสี่ยง
สด ผ่านเกตเวย์ที่เชื่อมต่อไปยัง โบรกเกอร์จริงมี การเชื่อมต่อเกตเวย์ + ข้อมูลรับรอง + การยอมรับข้อตกลงเทรดจริง เทรดอัตโนมัติในสถานการณ์จริง
ภาพที่ 1 — กฎหนึ่งข้อเมื่อผ่านห่วงโซ่ด่านตรวจแล้ว จะถูกส่งไปยังหนึ่งในสามเส้นทางตาม account_type
สิ่งที่ไม่มีวันเกิดขึ้น: กฎ live ที่ไม่มีเกตเวย์จะถูกลดระดับเป็นจำลองอย่างเงียบๆ live จะถูกปฏิเสธพร้อมเหตุผลที่ชัดเจน และเหตุผลนั้นจะถูกบันทึกไว้ในบันทึกการทำงาน — เพราะการจับคู่คำสั่งปลอมที่ดูเหมือนจริงคือสิ่งที่แย่ที่สุด

STEP 1 — เตรียมข้อมูลรับรองจากโบรกเกอร์ / เตรียมข้อมูลรับรองของโบรกเกอร์

โบรกเกอร์สิ่งที่ต้องมีที่ไหนข้อควรระวัง
Alpacaรหัส API Key ID + Secretalpaca.markets → API Keys (คีย์ paper และ live แยกกัน)สิทธิ์เทรดเท่านั้น shadow จะใช้ปลายทาง paper โดยอัตโนมัติ
BinanceAPI Key + Secretบัญชี → API Managementห้ามให้สิทธิ์ถอนเงินโดยเด็ดขาด ติ๊กเฉพาะ เทรด(TRADE) เท่านั้น shadow จะใช้ testnet
IBKRClient Portal Gateway URL + หมายเลขบัญชีรัน Client Portal Gateway ที่ IBKR แจกจ่ายและล็อกอินด้วยตนเองไม่มี API key — เซสชันของเกตเวย์คือข้อมูลรับรองในตัวเอง ต้องเป็นที่อยู่ที่เซิร์ฟเวอร์เข้าถึงได้ หากหมายเลขบัญชีขึ้นต้นด้วย D แสดงว่าเป็นบัญชีจำลอง (shadow ทำงานได้เฉพาะกับบัญชีจำลองเท่านั้น)
BybitAPI Key + Secretbybit.com → APIสิทธิ์เทรดเท่านั้น shadow ใช้สภาพแวดล้อมเดโม (คีย์เดโมแยกต่างหาก)
OKXKey + Secret + Passphraseokx.com → API keysตั้งพาสเฟรสเองตอนสร้างคีย์ shadow ใช้เดโมเทรดดิง (คีย์เดโมแยก)
KrakenAPI Key + Secretkraken.com → Settings → APIไม่มีแซนด์บ็อกซ์ — shadow ส่งคำสั่งแบบตรวจสอบเท่านั้นของ Kraken (ไม่มีทางจับคู่) ใช้คีย์เฉพาะกับ Sooppiy (ห้ามแชร์กับแอปอื่น)
Crypto.comAPI Key + Secretexchange.crypto.com → API Keysคีย์ของ Exchange shadow ใช้แซนด์บ็อกซ์ UAT (คีย์แยก)
UpbitAccess Key + Secretupbit.com → จัดการ Open APIต้องลงทะเบียน IP เซิร์ฟเวอร์ ตลาด KRW — บันทึกอัตราแลกเปลี่ยนทุกการจับคู่ shadow บันทึกอย่างเดียว ไม่ส่งอะไรไป Upbit
KuCoinKey + Secret + Passphrasekucoin.com → API Managementคีย์ v2 shadow ใช้ endpoint ทดสอบคำสั่ง (ไม่มีทางจับคู่)
การขยายระดับภูมิภาค (2026-08-01): เพิ่ม Bybit, OKX, Kraken, Crypto.com, Upbit และ KuCoin เชื่อมต่อได้แล้ววันนี้ ทั้งหมดรันแบบ shadow ก่อน คำสั่ง live บนกระดานใหม่จะถูกปฏิเสธพร้อมข้อความชัดเจน (ไม่มีการแอบเปลี่ยนเป็นการจำลอง) จนกว่า Sooppiy จะเปิดใช้งานหลังช่วงทดสอบเสร็จ และกระดานที่เพิ่งเปิดมีเพดานคำสั่งละ $1,000 ในช่วงแรก (Webull $1,500) (เกินเพดานถูกปฏิเสธ ไม่ถูกลดขนาด) แต่ละโบรกเกอร์มีคู่มือเชื่อมต่อทีละขั้นในหน้าบัญชี — เลือกโบรกเกอร์แล้วกดปุ่ม 📖

STEP 2 — เชื่อมต่อเกตเวย์ที่หน้าบัญชี / เชื่อมต่อได้ที่หน้า Accounts

  • บัญชี(Accounts) หน้า → เกตเวย์เทรด เลือกโบรกเกอร์จากการ์ด รายการจะถูกโหลดจากเซิร์ฟเวอร์(GET /api/execution/brokers).
  • Alpaca/Binance: ป้อนคีย์+รหัสลับ IBKR: ป้อน URL เกตเวย์ + หมายเลขบัญชี (มีตัวเลือกใบรับรองที่ลงนามด้วยตนเองสำหรับเกตเวย์ภายในเครื่อง) OKX/KuCoin ต้องกรอกพาสเฟรสด้วย
  • คีย์จะถูกเข้ารหัสด้วย AES-GCM และจัดเก็บไว้ที่เซิร์ฟเวอร์โดยจะไม่คงอยู่ใน localStorage ของเบราว์เซอร์ และจะถูกลบออกจากช่องป้อนข้อมูลทันทีหลังบันทึก จะไม่แสดงซ้ำอีก

STEP 3 — ยอมรับข้อตกลงการซื้อขายจริง / ยอมรับข้อกำหนดการเทรดจริง

  • ช่องทำเครื่องหมายเหนือปุ่มเชื่อมต่อคือขั้นตอนการยอมรับ หากไม่ยอมรับ การเชื่อมต่อจะไม่ดำเนินการเลย
  • การยอมรับจะถูกบันทึกเป็นรายการที่แยกตามโบรกเกอร์ และไม่เปลี่ยนแปลง (broker_live_optins) — แม้จะยอมรับ Alpaca แล้ว ก็ยังต้องยอมรับแยกต่างหากสำหรับ Binance live

STEP 4 — ตรวจสอบแบนเนอร์สถานะ / ตรวจสอบแบนเนอร์สถานะ

  • หลังเชื่อมต่อแล้ว จะมีแบนเนอร์สีเขียว (ปกติ)/สีแดง (ใช้งานไม่ได้) แสดงที่ด้านบนของหน้าบัญชี (GET /api/execution/health).
  • IBKR จะแสดงสถานะเซสชันด้วย (หมดอายุ/แย่งใช้งาน) ส่วน Alpaca/Binance ไม่มีแนวคิดเรื่องเซสชัน จึงตรวจสอบเพียงว่ามีข้อมูลรับรองอยู่หรือไม่

STEP 5 — ตรวจสอบด้วย shadow ก่อน / ตรวจสอบความถูกต้องใน shadow ก่อน

  • หน้าอัตโนมัติ (โหมดผู้เชี่ยวชาญ) → ของกฎ account = shadow + เปิดการทำงานอัตโนมัติ ON
  • สมุดบัญชีจำลองยังคงเป็นตัวอ้างอิงหลัก ในขณะที่คำสั่งเดียวกันจะถูกส่งไปยังแซนด์บ็อกซ์ของโบรกเกอร์ด้วย ความแตกต่างของการจับคู่คำสั่งจะถูกสะสมไว้ในบันทึกความคลาดเคลื่อน (drift) คุณจะเห็น slippage และอัตราการจับคู่คำสั่งได้โดยไม่ต้องใช้เงินจริง

STEP 6 — เปลี่ยนเป็น live / สลับไปใช้งานจริง

  • ของกฎ account = live กฎ live ที่เปิดการทำงานอัตโนมัติจะมีป้ายสีแดง เงินจริง (REAL MONEY) ติดอยู่ในรายการ
  • ตั้งแต่จุดนี้เป็นต้นไป มีเพียงการตัดสินใจที่ผ่านห่วงโซ่ประตูตรวจสอบทั้งหมดเท่านั้นที่จะถูกส่งไปยังโบรกเกอร์จริง สมุดบัญชีของแพลตฟอร์มจะบันทึกก็ต่อเมื่อโบรกเกอร์ยอมรับคำสั่งแล้วเท่านั้น

STEP 7 — เฝ้าติดตาม / ตรวจสอบ

  • บันทึกการทำงานในหน้าอัตโนมัติ: การตัดสินใจ การจับคู่คำสั่ง และเหตุผลที่ข้ามในทุกติ๊ก
  • ประวัติคำสั่งโบรกเกอร์ในหน้าบัญชี: จำนวนที่ร้องขอเทียบกับจำนวนที่โบรกเกอร์ยืนยันว่าจับคู่แล้ว พร้อมสีตามสถานะ
  • บันทึกความคลาดเคลื่อน (การ์ดสีแดง): กรณีที่สมุดบัญชีกับโบรกเกอร์ไม่ตรงกัน — ดู §5
  • การแจ้งเตือน: การจับคู่คำสั่งสำเร็จ (trade_executed) เกตเวย์ล่ม (gateway_down) คำสั่งคลาดเคลื่อน (order_drift) — เป็นไปตามช่องทางอีเมล/SMS ที่ตั้งค่าการแจ้งเตือนไว้

03ประตูตรวจสอบ 12 ขั้นที่คำสั่งต้องผ่าน / ห่วงโซ่ประตู 12 ขั้นตอน

ในทุกติ๊กของกฎที่เปิดการทำงานอัตโนมัติ การตัดสินใจ (buy/sell) จะต้องผ่านประตูตรวจสอบด้านล่างนี้ทั้งหมดตามลำดับ จึงจะถูกส่งจริง หากถูกกั้นแม้เพียงจุดเดียว เหตุผลนั้นจะถูกบันทึกไว้ในบันทึกการทำงาน และคำสั่งจะไม่ถูกส่งออกไป

ภาพที่ 2 — ห่วงโซ่ประตูตรวจสอบการทำงาน (evaluate_execution_gates) ⑫ ต่อเนื่องจากคอลัมน์ซ้ายด้านล่างไปยังคอลัมน์ขวาด้านบน ต้องผ่านทั้งหมดจึงจะจับคู่คำสั่งได้ การรันทดสอบ (▶) เป็นเพียงการวิเคราะห์เท่านั้น และไม่ผ่านห่วงโซ่นี้
ลำดับมีความสำคัญ: กฎที่ปิดการทำงานอัตโนมัติจะถูกบันทึกเป็น「ปิดการทำงานอัตโนมัติ」ไม่ใช่บันทึกเป็นข้อผิดพลาดของเกตเวย์ เพียงอ่านเหตุผลที่ข้ามก็จะทราบได้ทันทีว่าติดขัดที่ด่านไหน

04วงจรชีวิตของคำสั่ง live / วงจรชีวิตของคำสั่งซื้อขายที่ใช้งานจริง

หากโบรกเกอร์ไม่ยืนยันการทำรายการทันที(SUBMITTED) ตัวกระทบยอดคำสั่ง (Order Reconciler)จะสอบถามผลลัพธ์จากโบรกเกอร์ทุก 2 นาทีเพื่อยืนยันสถานะสุดท้าย

ภาพที่ 3 — ส่ง → (ยืนยันทันทีหรือผ่านตัวกระทบยอด) → หากมีความคลาดเคลื่อนจะแจ้งเตือนอย่างชัดเจน จำนวนที่ร้องขอ(quantity)กับจำนวนที่โบรกเกอร์ยืนยัน(filled_qty)แยกคอลัมน์กัน จึงเห็นความแตกต่างได้ตลอด
หลักการออกแบบ — ตรวจจับเท่านั้น การแก้ไขให้เป็นหน้าที่ของคน: ตัวกระทบยอดจะไม่แตะต้องตำแหน่งหรือเงินสดเด็ดขาด การให้งานพื้นหลังไปแก้ไขการคำนวณเงินจะยิ่งทำให้บัญชีแยกประเภทเสียหายซ้ำสอง ดังนั้นเมื่อมีความคลาดเคลื่อนจะแสดงเป็นการ์ดสีแดงและแจ้งเตือนอย่างเด่นชัด ส่วนการแก้ไขให้ผู้ใช้ตรวจสอบบัญชีโบรกเกอร์แล้วดำเนินการเอง

05IBKR session keepalive / รักษาสถานะการเชื่อมต่อเซสชัน IBKR

เซสชัน IBKR Client Portal จะขาดการเชื่อมต่อได้แม้ไม่ได้ใช้งานเพียงไม่กี่นาที Worker จะ tickle เซสชันทุก 60 วินาที หากขาดการเชื่อมต่อจะพยายามยืนยันตัวตนใหม่ และหากกู้คืนไม่ได้จะแจ้งเตือนวันละ 1 ครั้ง

รูปที่ 4 — แผนภาพสถานะเซสชัน เซสชันที่แข่งขัน (competing) ก็ถือว่าเป็น dead เช่นกัน (เนื่องจากหากมีการเข้าสู่ระบบอื่นครอบครองบัญชี คำสั่งซื้อขายจะถูกปฏิเสธ)
กลไกความปลอดภัยของ shadow: IBKR แตกต่างจาก Alpaca/Binance ตรงที่ไม่มีโฮสต์แซนด์บ็อกซ์แยกต่างหาก บัญชีเป็นตัวกำหนดว่าเป็นเงินจริงหรือไม่ ดังนั้นในโหมด shadow หากหมายเลขบัญชีไม่ใช่บัญชีทดลอง (คำนำหน้า D ) อะแดปเตอร์จะปฏิเสธโดยไม่ส่งคำขอออกไปเลย

06เหตุผลที่ข้าม → วิธีแก้ไข / เหตุผลที่ข้าม และวิธีแก้ไข

เหตุผลในบันทึกการทำงานความหมายวิธีแก้ไข
ปิดการทำงานอัตโนมัติกฎใช้สำหรับการวิเคราะห์เท่านั้นเปิดใช้งานช่องทำเครื่องหมายการทำงานอัตโนมัติของกฎ
เลือกใช้งานจริง (Live) แล้ว แต่ยังไม่ได้ตั้งค่าเกตเวย์การซื้อขายไม่มีบัญชีโบรกเกอร์ที่เชื่อมต่อเชื่อมต่อเกตเวย์ในหน้าบัญชี (STEP 2)
ไม่มีข้อมูลรับรอง API ที่ใช้งานได้สำหรับเกตเวย์ที่เชื่อมต่อไม่มีคีย์ที่บันทึกไว้ หรือถอดรหัสไม่ได้ (เช่น มีการเปลี่ยนคีย์เซิร์ฟเวอร์)เชื่อมต่อโบรกเกอร์ใหม่
ยังไม่ยอมรับข้อกำหนดการซื้อขายจริงไม่มีประวัติการยอมรับข้อกำหนดสำหรับโบรกเกอร์นั้นยอมรับข้อกำหนดแล้วเชื่อมต่อใหม่ในหน้าบัญชี (STEP 3)
เกตเวย์ปฏิเสธคำสั่งซื้อขาย — …โบรกเกอร์ปฏิเสธคำสั่งซื้อขาย (ระบุเหตุผล เช่น ยอดคงเหลือไม่พอ เซสชันหมดอายุ)ตรวจสอบสาเหตุ — หากเป็น IBKR 401 ให้เข้าสู่ระบบเกตเวย์ใหม่
การตัดสินใจคือ holdAI ตัดสินใจรอดูสถานการณ์ปกติ — ไม่ต้องดำเนินการใด ๆ
ความเชื่อมั่น X — ต่ำกว่าเกณฑ์ Yความมั่นใจไม่เพียงพอรอ (แนะนำ) หรือปรับ min_confidence ลง
ตลาดปิดทำการตลาดสหรัฐฯ ปิดทำการปกติ — ลองใหม่เมื่อตลาดเปิดทำการ
ปฏิเสธการวางคำสั่ง shadow order ในบัญชี IBKR …พยายามทำ shadow ด้วยบัญชีจริงของ IBKRเชื่อมต่อกับบัญชีทดลอง (DU…) หรือใช้ simulator แทน shadow

07สิ่งที่ระบบจะไม่ทำเด็ดขาด / ค่าคงที่ด้านความปลอดภัย (test-pinned)

ค่าคงที่เหตุผลวิธีการรับประกัน
จะไม่ลดระดับ live เป็นโหมดจำลองอย่างเงียบๆการจับคู่คำสั่งปลอมที่ดูเหมือนของจริงคือสิ่งที่แย่ที่สุดปฏิเสธอย่างชัดเจนที่ gate ② พร้อมบันทึกเหตุผล
คำสั่ง shadow จะไม่ถูกส่งไปถึงตลาดจริง"การรันจำลอง" ต้องไม่ใช้เงินจริงโหมดกฎเกณฑ์จะตรึง endpoint ไว้ (ไม่สนใจโหมดบัญชีที่บันทึกไว้) โดย IBKR จะบังคับใช้บัญชีทดลอง
จะไม่มีการสร้างโพซิชันเมื่อโบรกเกอร์ปฏิเสธป้องกันโพซิชันผีจากคำสั่งที่ไม่ถึงตลาดlive จะบันทึกลงบัญชีแยกประเภทหลังจากโบรกเกอร์ยอมรับเท่านั้น
reconciler จะไม่แก้ไขบัญชีแยกประเภทการแก้ไขการคำนวณเงินในเบื้องหลัง = ความเสี่ยงต่อความเสียหายซ้ำซ้อนตรวจจับ บันทึก และแจ้งเตือนเท่านั้น การแก้ไขเป็นหน้าที่ของมนุษย์
คีย์ของโบรกเกอร์จะไม่ถูกส่งกลับไปยังไคลเอนต์ลดพื้นที่การรั่วไหลให้น้อยที่สุดจัดเก็บด้วย AES-GCM โดย API สำหรับเรียกดูจะคืนค่าเฉพาะเมทาดาทาเท่านั้น
คีย์เข้ารหัส (EXECUTION_ENCRYPTION_KEY) เป็นแบบ write-onceเมื่อเปลี่ยนคีย์ ข้อมูลรับรองที่จัดเก็บไว้ทั้งหมดจะเป็นโมฆะอย่างถาวรขั้นตอนการดำเนินงาน + การสำรองข้อมูลด้วยตัวจัดการรหัสผ่าน
ความล้มเหลวของ live จะไม่เงียบหายGateway ที่ตายแล้วแยกไม่ออกจากตลาดที่เงียบการแจ้งเตือน gateway_down/order_drift (ลดข้อมูลซ้ำแบบรายชั่วโมง·รายวัน)
Invariant ข้างต้นถูกตรึงไว้ด้วยการทดสอบอัตโนมัติ (ประมาณ 100 รายการจาก stack การรันทั้งหมด 1,386 รายการ) และได้รับการตรวจสอบซ้ำด้วย 3-agent QA (การตรวจสอบเชิงปฏิปักษ์ฝั่ง backend · โฟลว์ฝั่ง frontend · สถานะโปรดักชัน)

08หมายเหตุการปฏิบัติงาน / บันทึกผู้ปฏิบัติงาน

รายการค่า/ตำแหน่งหมายเหตุ
ตัวแปรสภาพแวดล้อมโปรดักชัน ~/sooppiy/.env ไฟล์เดียว (mode 600)รวมความคิดเห็นแยกตามส่วน คอนเทนเนอร์ต้องสร้างใหม่จึงจะมีผล
รอบ keepaliveGATEWAY_KEEPALIVE_INTERVAL (ค่าเริ่มต้น 60 วินาที)ไม่มีค่าใช้จ่าย no-op หากไม่มีบัญชี IBKR
รอบการกระทบยอด (reconcile)ORDER_RECONCILE_INTERVAL (ค่าเริ่มต้น 120 วินาที)ไม่มีค่าใช้จ่ายหากไม่มีคำสั่ง submitted
Endpoint ของโบรกเกอร์ALPACA_*_BASE_URL, BINANCE_*_BASE_URLไม่มีการฮาร์ดโค้ด — ฉีดค่าจาก .env
การปรับใช้ (deploy)สร้าง tag → ของ .env SOOPPIY_IMAGE แก้ไข → docker compose --profile prod up -dไม่มีค่า literal ในไฟล์ compose เลย
