คู่มือฉบับสมบูรณ์สำหรับเกตเวย์การซื้อขายจริง

2026-07-19 · prod = main@8c2248f (image 20260719-orderui) · เขียนขึ้นหลังการตรวจสอบ QA โดย 3-agent · คำบรรยายภาษาอังกฤษในแต่ละส่วน

เส้นทางทั้งหมดที่กฎการซื้อขายอัตโนมัติดำเนินไปสู่ จำลอง (simulator) → เงา (shadow) → จริง (live)โดยเชื่อมโยงกัน: ต้องตั้งค่าอะไร คำสั่งซื้อขายผ่านด่านใดบ้าง และระบบไม่ทำสิ่งใดโดยเด็ดขาด อธิบายไว้ในเอกสารฉบับเดียว

01โหมดการทำงานทั้งสาม / The three execution modes

การตั้งค่า บัญชี (account) เพียงจุดเดียวในกฎ (หน้าอัตโนมัติ) จะเป็นตัวกำหนดว่าการจับคู่คำสั่งซื้อขายจะไปลงที่ใด ไม่มีการตั้งค่าอื่นใดที่จะเปลี่ยนแปลงสิ่งนี้ได้

โหมดตำแหน่งการจับคู่คำสั่งเงินทุนจริงเงื่อนไขที่จำเป็นการใช้งาน
simulator บันทึกจำลองของแพลตฟอร์มเท่านั้นไม่มีไม่มี (ค่าเริ่มต้น) ตรวจสอบกลยุทธ์ เรียนรู้แพลตฟอร์ม
shadow บันทึกจำลอง (เป็นเกณฑ์อ้างอิง) + คำสั่งเปรียบเทียบกับ แซนด์บ็อกซ์ ของโบรกเกอร์ไม่มี การเชื่อมต่อเกตเวย์ (ทางเลือก — หากไม่มีจะเป็นการจำลองล้วน) เปรียบเทียบสลิปเพจและอัตราการจับคู่คำสั่งจริงโดยไม่มีความเสี่ยง
live ผ่านเกตเวย์ที่เชื่อมต่อไปยัง โบรกเกอร์จริงมี การเชื่อมต่อเกตเวย์ + ข้อมูลรับรอง + ยอมรับข้อตกลงการซื้อขายจริง การซื้อขายอัตโนมัติจริง
ภาพที่ 1 — กฎหนึ่งข้อเมื่อผ่านห่วงโซ่ด่านแล้ว จะถูกส่งไปตามหนึ่งในสามเส้นทางตามค่า account_type
สิ่งที่ไม่มีวันเกิดขึ้น: กฎ live ที่ไม่มีเกตเวย์ จะไม่ถูกลดระดับเป็นโหมดจำลองโดยเงียบๆ live จะ ถูกปฏิเสธพร้อมเหตุผลชัดเจน และเหตุผลนั้นจะถูกบันทึกไว้ในบันทึกการทำงาน — เพราะการจับคู่คำสั่งปลอมที่ดูเหมือนของจริงคือสิ่งที่เลวร้ายที่สุด

027 ขั้นตอนสู่การซื้อขายจริง / Seven steps to live

STEP 3ยอมรับข้อตกลง

STEP 1 — เตรียมข้อมูลรับรองจากโบรกเกอร์ / Prepare broker credentials

โบรกเกอร์สิ่งที่ต้องมีที่ไหนข้อควรระวัง
AlpacaAPI Key ID + Secretalpaca.markets → API Keys (คีย์ paper และ live แยกจากกัน)สิทธิ์การซื้อขายเท่านั้น shadow จะใช้ปลายทาง paper โดยอัตโนมัติ
BinanceAPI Key + Secretบัญชี → API Managementห้ามให้สิทธิ์ถอนเงินโดยเด็ดขาด เลือกเฉพาะการซื้อขาย (TRADE) shadow จะใช้ testnet
IBKRClient Portal Gateway URL + หมายเลขบัญชีให้รันและล็อกอิน Client Portal Gateway ที่ IBKR เผยแพร่ด้วยตนเองไม่มี API key — เซสชันของเกตเวย์คือข้อมูลรับรองนั่นเอง ต้องเป็นที่อยู่ที่เซิร์ฟเวอร์เข้าถึงได้ หากหมายเลขบัญชีขึ้นต้นด้วย D แสดงว่าเป็นบัญชีจำลอง (shadow จะทำงานได้เฉพาะบนบัญชีจำลองเท่านั้น)

STEP 2 — เชื่อมต่อเกตเวย์ที่หน้าบัญชี / Connect on the Accounts page

  • บัญชี (Accounts) หน้า → การ์ด เกตเวย์การซื้อขาย เลือกโบรกเกอร์ รายการจะถูกโหลดจากเซิร์ฟเวอร์(GET /api/execution/brokers).
  • Alpaca/Binance: ป้อนคีย์+รหัสลับ IBKR: ป้อน URL เกตเวย์ + หมายเลขบัญชี (มีตัวเลือกใบรับรองที่ลงนามด้วยตนเองสำหรับเกตเวย์ในเครื่อง)
  • คีย์จะถูกเข้ารหัสด้วย AES-GCM และจัดเก็บไว้ที่เซิร์ฟเวอร์โดยจะไม่ถูกเก็บไว้ใน localStorage ของเบราว์เซอร์ และจะถูกลบออกจากช่องป้อนข้อมูลทันทีหลังจากบันทึก โดยจะไม่แสดงผลอีกต่อไป

STEP 3 — ยอมรับข้อกำหนดการเทรดจริง / ยอมรับข้อกำหนดการเทรดจริง

  • ช่องทำเครื่องหมายเหนือปุ่มเชื่อมต่อคือขั้นตอนการยอมรับ หากไม่ยอมรับ จะไม่สามารถดำเนินการเชื่อมต่อได้
  • การยอมรับ ตามโบรกเกอร์ บันทึกที่ไม่เปลี่ยนแปลง(broker_live_optins)แม้ว่าคุณจะยินยอมกับ Alpaca แล้ว แต่ Binance live ก็ยังต้องได้รับความยินยอมแยกต่างหาก

STEP 4 — ตรวจสอบแบนเนอร์สถานะ / ตรวจสอบแบนเนอร์สถานะ

  • หลังจากเชื่อมต่อแล้ว แบนเนอร์สีเขียว(ปกติ)/สีแดง(ใช้ไม่ได้) จะแสดงที่ด้านบนของหน้าบัญชี(GET /api/execution/health).
  • IBKR จะแสดงสถานะเซสชัน(หมดอายุ/แข่งขันกัน)ด้วย ส่วน Alpaca/Binance ไม่มีแนวคิดเซสชัน จึงตรวจสอบเพียงว่ามีข้อมูลรับรองอยู่หรือไม่

STEP 5 — ตรวจสอบด้วย shadow ก่อน / ตรวจสอบใน shadow ก่อน

  • หน้าอัตโนมัติ(โหมดผู้เชี่ยวชาญ) → ของกฎ บัญชี = shadow + เปิดใช้งานอัตโนมัติ ON.
  • ในขณะที่บัญชีจำลองยังคงเป็นค่าอ้างอิง คำสั่งเดียวกันจะถูกส่งไปยังโบรกเกอร์ แซนด์บ็อกซ์ด้วยเช่นกัน และความแตกต่างในการจับคู่คำสั่งจะ บันทึกดริฟต์ถูกสะสมไว้ที่นี่ คุณจะเห็นค่าสลิปเพจและอัตราการจับคู่คำสั่งโดยไม่ใช้เงินจริง

STEP 6 — การเปลี่ยนเป็น live / Flip to live

  • ของกฎ บัญชี = live. กฎ live ที่เปิดใช้งานการทำงานอัตโนมัติจะมีป้ายสีแดง เงินจริง (REAL MONEY) ติดอยู่ในรายการ
  • ตั้งแต่จุดนี้เป็นต้นไป มีเพียงการตัดสินใจที่ผ่านห่วงโซ่เกตทั้งหมดเท่านั้นที่จะถูกส่งไปยังโบรกเกอร์จริง บัญชีของแพลตฟอร์มจะถูกบันทึกก็ต่อเมื่อโบรกเกอร์ยอมรับคำสั่งแล้วเท่านั้น

STEP 7 — การติดตาม / Monitor

  • บันทึกการทำงานในหน้าอัตโนมัติ: การตัดสินใจ การจับคู่คำสั่ง และเหตุผลในการข้ามของทุกติ๊ก
  • ประวัติคำสั่งโบรกเกอร์ในหน้าบัญชีจำนวนที่ขอ vs จำนวนที่โบรกเกอร์ยืนยันการดำเนินการ, สีตามสถานะ
  • บันทึกการเบี่ยงเบน (การ์ดสีแดง): กรณีที่บัญชีและโบรกเกอร์ไม่ตรงกัน — ดู §5
  • การแจ้งเตือน: การดำเนินการ (trade_executed), เกตเวย์ล่ม (gateway_down), การเบี่ยงเบนของคำสั่ง (order_drift) — เป็นไปตามช่องทางอีเมล/SMS ในการตั้งค่าการแจ้งเตือน

0312 ประตูที่คำสั่งต้องผ่าน / ห่วงโซ่ประตู 12 ขั้นตอน

ในทุกติ๊กของกฎที่เปิดใช้การดำเนินการอัตโนมัติ เพื่อให้การตัดสินใจ (buy/sell) ดำเนินการจริง จะต้องผ่านประตูด้านล่าง ทั้งหมดตามลำดับ ต้องผ่านทั้งหมด หากถูกบล็อกแม้เพียงข้อเดียว เหตุผลจะถูกบันทึกในบันทึกการดำเนินการและคำสั่งจะไม่ถูกส่งออกไป

รูปที่ 2 — ห่วงโซ่เกตการดำเนินการ (evaluate_execution_gates) ⑫ ไล่จากด้านล่างของคอลัมน์ซ้าย→ขึ้นไปด้านบนของคอลัมน์ขวา ต้องผ่านทั้งหมดจึงจะส่งคำสั่งได้ การรันทดสอบ (▶) เป็นเพียงการวิเคราะห์เท่านั้น ไม่ผ่านห่วงโซ่นี้
ลำดับมีความสำคัญ: กฎที่ปิดการทำงานอัตโนมัติจะถูกบันทึกเป็น 「ปิดการทำงานอัตโนมัติ」 ไม่ใช่บันทึกเป็นข้อผิดพลาดของเกตเวย์ หากอ่านเหตุผลที่ถูกข้าม จะทราบได้ทันทีว่าติดขัดที่ด่านใด

04วงจรชีวิตของคำสั่งซื้อ live / Life of a live order

หากโบรกเกอร์ไม่ยืนยันการดำเนินการทันที (SUBMITTED) ตัวปรับกระทบยอดคำสั่งซื้อจะสอบถามผลลัพธ์จากโบรกเกอร์ทุก 2 นาทีเพื่อยืนยันสถานะสุดท้าย

ภาพที่ 3 — ส่ง → (ยืนยันทันทีหรือผ่านตัวปรับกระทบยอด) → หากไม่ตรงกันจะแจ้งเตือนดังชัดเจน จำนวนที่ร้องขอ (quantity) และจำนวนที่โบรกเกอร์ยืนยัน (filled_qty) อยู่คนละคอลัมน์ จึงมองเห็นความแตกต่างได้ตลอด
หลักการออกแบบ — ตรวจจับเท่านั้น การแก้ไขต้องเป็นคน: ตัวปรับกระทบยอดจะไม่แตะต้องโพซิชันหรือเงินสดเด็ดขาด การให้งานพื้นหลังไปแก้ไขการคำนวณเงินมีแต่จะทำให้บัญชีแยกประเภทเสียหายซ้ำสอง ดังนั้นเมื่อพบความคลาดเคลื่อนจะแสดงเป็นการ์ดสีแดงและแจ้งเตือนอย่างชัดเจน ส่วนการแก้ไขให้ผู้ใช้ตรวจสอบบัญชีโบรกเกอร์แล้วดำเนินการเอง

05IBKR session keepalive / IBKR session keepalive

เซสชัน IBKR Client Portal จะขาดการเชื่อมต่อแม้ว่างเพียงไม่กี่นาที เวิร์กเกอร์จะ tickle เซสชันทุก 60 วินาที หากขาดการเชื่อมต่อจะพยายามยืนยันตัวตนใหม่ และหากกู้คืนไม่ได้จะแจ้งเตือนวันละ 1 ครั้ง

ภาพที่ 4 — สถานะเครื่องจักรของเซสชัน แม้แต่เซสชันที่แข่งขันกัน (competing) ก็ถือว่าเป็น dead เช่นกัน (เพราะหากมีการล็อกอินอื่นครองบัญชีอยู่ คำสั่งซื้อจะถูกปฏิเสธ)
ระบบป้องกัน shadow: IBKR ต่างจาก Alpaca/Binance ตรงที่ไม่มีโฮสต์แซนด์บ็อกซ์แยกต่างหาก บัญชี เป็นตัวกำหนดว่าใช้เงินจริงหรือไม่ ดังนั้นในโหมด shadow หากหมายเลขบัญชีไม่ใช่บัญชีทดลอง (ขึ้นต้นด้วย D ) อะแดปเตอร์จะปฏิเสธโดยไม่ส่งคำขอออกไปเลย

06เหตุผลที่ถูกข้าม → วิธีแก้ไข / Skip reasons and fixes

เหตุผลในบันทึกการดำเนินการความหมายวิธีแก้ไข
ปิดการทำงานอัตโนมัติกฎใช้สำหรับวิเคราะห์เท่านั้นเปิดใช้งานช่องทำเครื่องหมายการทำงานอัตโนมัติของกฎ
เลือก live แล้วแต่ยังไม่ได้ตั้งค่าเกตเวย์การซื้อขายไม่มีบัญชีโบรกเกอร์ที่เชื่อมต่อเชื่อมต่อเกตเวย์ในหน้าบัญชี (STEP 2)
ไม่มีข้อมูลรับรอง API ที่ใช้งานได้สำหรับเกตเวย์ที่เชื่อมต่อไม่มีคีย์ที่บันทึกไว้ หรือถอดรหัสไม่ได้ (เช่น มีการเปลี่ยนคีย์เซิร์ฟเวอร์)เชื่อมต่อโบรกเกอร์ใหม่
ยังไม่ได้ยอมรับข้อตกลงการซื้อขายจริงไม่มีบันทึกการยอมรับสำหรับโบรกเกอร์นั้นยอมรับข้อตกลงแล้วเชื่อมต่อใหม่ในหน้าบัญชี (STEP 3)
เกตเวย์ปฏิเสธคำสั่งซื้อ — …โบรกเกอร์ปฏิเสธคำสั่งซื้อ (พร้อมระบุเหตุผล เช่น ยอดเงินไม่พอ เซสชันหมดอายุ)ตรวจสอบเหตุผล — หากเป็น IBKR 401 ให้เข้าสู่ระบบเกตเวย์ใหม่
การตัดสินใจคือ holdAI ตัดสินใจรอดูสถานการณ์ปกติ — ไม่ต้องดำเนินการใด ๆ
ความเชื่อมั่น X — ต่ำกว่าเกณฑ์ Yความเชื่อมั่นไม่เพียงพอรอ (แนะนำ) หรือปรับ min_confidence ให้ต่ำลง
ตลาดปิดตลาดสหรัฐฯ ปิดทำการปกติ — ลองใหม่เมื่อตลาดเปิด
ปฏิเสธการวางคำสั่ง shadow ในบัญชี IBKR …พยายามทำ shadow กับบัญชีจริงของ IBKRเชื่อมต่อกับบัญชีทดลอง (DU…) หรือใช้ simulator แทน shadow

07สิ่งที่ระบบจะไม่ทำเด็ดขาด / ค่าคงที่ด้านความปลอดภัย (ยึดตามการทดสอบ)

ค่าคงที่เหตุผลวิธีการรับประกัน
ไม่ลดระดับ live ให้กลายเป็นโหมดจำลองอย่างเงียบๆการจับคู่คำสั่งปลอมที่ดูเหมือนจริงคือสิ่งที่แย่ที่สุดปฏิเสธอย่างชัดเจนที่เกท ② พร้อมบันทึกเหตุผล
คำสั่ง shadow จะไม่ไปถึงตลาดจริง"การทำงานแบบจำลอง" ต้องไม่ใช้เงินจริงโหมดกฎเกณฑ์จะล็อกเอนด์พอยต์ (ไม่สนใจโหมดบัญชีที่บันทึกไว้) IBKR จะบังคับใช้บัญชีทดลอง
ไม่มีการสร้างโพซิชันเมื่อโบรกเกอร์ปฏิเสธป้องกันโพซิชันผีจากคำสั่งที่ไม่ถึงตลาดlive จะบันทึกลงบัญชีแยกประเภทหลังจากโบรกเกอร์ยอมรับเท่านั้น
ตัวกระทบยอด (reconciler) จะไม่แก้ไขบัญชีแยกประเภทการแก้ไขการคำนวณเงินในพื้นหลัง = ความเสี่ยงที่จะเสียหายซ้ำสองตรวจจับ บันทึก แจ้งเตือนเท่านั้น การแก้ไขให้เป็นหน้าที่ของมนุษย์
คีย์ของโบรกเกอร์จะไม่ถูกส่งกลับไปยังไคลเอนต์ลดพื้นที่การรั่วไหลให้น้อยที่สุดจัดเก็บด้วย AES-GCM, API สำหรับดึงข้อมูลจะคืนค่าเฉพาะเมทาดาทาเท่านั้น
คีย์เข้ารหัส (EXECUTION_ENCRYPTION_KEY) เป็นแบบ write-onceเมื่อเปลี่ยนคีย์ ข้อมูลรับรองที่จัดเก็บไว้ทั้งหมดจะใช้ไม่ได้อย่างถาวรขั้นตอนการปฏิบัติงาน + สำรองข้อมูลด้วยตัวจัดการรหัสผ่าน
ความล้มเหลวของ live จะไม่เงียบหายDead gateway ไม่สามารถแยกแยะได้จากตลาดที่เงียบสงบการแจ้งเตือน gateway_down/order_drift (ลดการซ้ำซ้อนตามหน่วยชั่วโมง/วัน)
ค่าคงที่ (invariants) ข้างต้นถูกยึดไว้ด้วยการทดสอบอัตโนมัติ (จากทั้งหมด 1,386 รายการ มีสแต็กการทำงานจริงประมาณ 100 รายการ) และได้รับการตรวจสอบซ้ำโดย 3-agent QA (การตรวจสอบเชิงปฏิปักษ์ฝั่ง backend · โฟลว์ฝั่ง frontend · สถานะโปรดักชัน)

รายการค่า/ตำแหน่งหมายเหตุ
ตัวแปรสภาพแวดล้อมโปรดักชัน ~/sooppiy/.env ไฟล์เดียว (mode 600)มีคอมเมนต์แยกตามส่วน คอนเทนเนอร์ต้องสร้างใหม่จึงจะมีผล
รอบ keepaliveGATEWAY_KEEPALIVE_INTERVAL (ค่าเริ่มต้น 60 วินาที)หากไม่มีบัญชี IBKR จะไม่มีค่าใช้จ่าย no-op
รอบการ reconcileORDER_RECONCILE_INTERVAL (ค่าเริ่มต้น 120 วินาที)หากไม่มีคำสั่ง submitted จะไม่มีค่าใช้จ่าย
เอนด์พอยต์โบรกเกอร์ALPACA_*_BASE_URL, BINANCE_*_BASE_URLไม่มีการฝังค่าตายตัว — ฉีดค่าจาก .env
การปรับใช้สร้างบิลด์แท็ก → ของ .env SOOPPIY_IMAGE แก้ไข → docker compose --profile prod up -dไม่มีค่า literal ในไฟล์ compose เลย
คอนเทนเนอร์ APISOOPPIY_API_BACKGROUND_TASKS=falseลูปนี้สำหรับ worker เท่านั้น — หากเป็น true จะรันซ้ำซ้อนทั้งหมด
