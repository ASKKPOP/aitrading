실거래 게이트웨이 완전 가이드

2026-07-19 · prod = main@8c2248f (image 20260719-orderui) · 3-agent QA 검증 후 작성 · English subtitles per section

자동매매 규칙이 모의(simulator) → 그림자(shadow) → 실거래(live)로 이어지는 전체 경로: 무엇을 설정해야 하고, 주문이 어떤 관문을 지나며, 시스템이 무엇을 절대 하지 않는지를 한 문서로 설명합니다.

01세 가지 실행 모드 / The three execution modes

규칙(자동화 페이지)의 계정(account) 설정 하나가 체결이 어디에 착지하는지를 결정합니다. 다른 어떤 설정도 이를 바꾸지 못합니다.

모드체결 위치실제 자금필요 조건용도
simulator 플랫폼 모의 원장만없음없음 (기본값) 전략 검증, 플랫폼 학습
shadow 모의 원장(기준) + 브로커 샌드박스에 대조 주문없음 게이트웨이 연결(선택 — 없으면 순수 모의) 실제 슬리피지·체결률을 무위험으로 비교
live 연결된 게이트웨이를 통해 실제 브로커있음 게이트웨이 연결 + 자격증명 + 실거래 약관 동의 실전 자동매매
그림 1 — 규칙 하나가 게이트 체인을 통과한 뒤 account_type에 따라 세 경로 중 하나로 라우팅됩니다.
절대 일어나지 않는 것: 게이트웨이가 없는 live 규칙이 조용히 모의로 강등되는 일. live는 명시적 사유와 함께 거부되며 그 사유가 실행 기록에 남습니다 — 진짜처럼 보이는 가짜 체결이 최악이기 때문입니다.

STEP 1 — 브로커에서 자격증명 준비 / Prepare broker credentials

브로커필요한 것어디서주의
AlpacaAPI Key ID + Secretalpaca.markets → API Keys (paper와 live 키는 별개)거래 권한만. shadow는 자동으로 paper 엔드포인트 사용
BinanceAPI Key + Secret계정 → API Management출금 권한 절대 금지. 거래(TRADE)만 체크. shadow는 testnet 사용
IBKRClient Portal Gateway URL + 계좌번호IBKR이 배포하는 Client Portal Gateway를 직접 실행·로그인API 키가 없음 — 게이트웨이 세션이 곧 자격증명. 서버가 접근 가능한 주소여야 함. 계좌번호가 D로 시작하면 모의계좌(shadow는 모의계좌에서만 동작)
BybitAPI Key + Secretbybit.com → API거래 권한만. shadow는 데모 트레이딩 환경 사용(데모 키 별도)
OKXKey + Secret + Passphraseokx.com → API keys패스프레이즈는 키 생성 시 직접 설정. shadow는 데모 트레이딩 사용(데모 키 별도)
KrakenAPI Key + Secretkraken.com → Settings → API샌드박스 없음 — shadow는 크라켄의 검증 전용 주문(절대 체결 불가)을 보냄. 키는 Sooppiy 전용으로(다른 앱과 공유 금지)
Crypto.comAPI Key + Secretexchange.crypto.com → API Keys거래소(Exchange) 키. shadow는 UAT 샌드박스 사용(키 별도)
UpbitAccess Key + Secretupbit.com → Open API 관리서버 IP 등록 필수. KRW 마켓 — 환율은 체결 시점에 기록. shadow는 기록만 하고 업비트에 아무것도 전송하지 않음
KuCoinKey + Secret + Passphrasekucoin.com → API Managementv2 키. shadow는 주문 테스트 엔드포인트 사용(절대 체결 불가)
지역 확장 (2026-08-01): Bybit·OKX·Kraken·Crypto.com·Upbit·KuCoin이 추가되어 지금 연결할 수 있으며, 모두 shadow 우선으로 운영됩니다. 신규 거래소의 live 주문은 검증 기간이 끝나 플랫폼에서 활성화될 때까지 명시적 메시지와 함께 거부되고(몰래 시뮬레이션으로 바뀌지 않음), 새로 열린 거래소는 초기 주문당 $1,000 한도가 적용됩니다(Webull은 $1,500)(초과 시 축소가 아니라 거부). 브로커별 상세 연결 가이드는 계정 페이지에서 브로커 선택 후 📖 버튼으로 볼 수 있습니다.

STEP 2 — 계좌 페이지에서 게이트웨이 연결 / Connect on the Accounts page

  • 계좌(Accounts) 페이지 → 거래 게이트웨이 카드에서 브로커 선택. 목록은 서버에서 불러옵니다(GET /api/execution/brokers).
  • Alpaca/Binance: 키+시크릿 입력. IBKR: 게이트웨이 URL + 계좌번호 입력(로컬 게이트웨이의 자체서명 인증서 옵션 있음). OKX/KuCoin은 패스프레이즈도 함께 입력합니다.
  • 키는 서버에서 AES-GCM으로 암호화 저장되며, 브라우저 localStorage에 남지 않고 저장 즉시 입력창에서 지워지며 다시 표시되지 않습니다.

STEP 3 — 실거래 약관 동의 / Accept the live-trading terms

  • 연결 버튼 위의 체크박스가 동의 절차입니다. 동의 없이는 연결 자체가 진행되지 않습니다.
  • 동의는 브로커별 불변 기록(broker_live_optins)으로 남습니다 — Alpaca에 동의했어도 Binance live에는 별도 동의가 필요합니다.

STEP 4 — 상태 배너 확인 / Check the health banner

  • 연결 후 계좌 페이지 상단에 초록(정상)/빨강(불가) 배너가 뜹니다(GET /api/execution/health).
  • IBKR은 세션 상태(만료/경합)까지 표시됩니다. Alpaca/Binance는 세션 개념이 없어 자격증명 존재 여부만 확인합니다.

STEP 5 — shadow로 먼저 검증 / Validate in shadow first

  • 자동화 페이지(전문가 모드) → 규칙의 계정 = shadow + 자동 실행 ON.
  • 모의 원장이 기준으로 유지되면서, 같은 주문이 브로커 샌드박스에도 나가 체결 차이가 드리프트 기록에 쌓입니다. 실제 자금 없이 슬리피지·체결률을 봅니다.

STEP 6 — live 전환 / Flip to live

  • 규칙의 계정 = live. 자동 실행이 켜진 live 규칙에는 목록에 빨간 실제 자금(REAL MONEY) 배지가 붙습니다.
  • 이때부터 게이트 체인을 전부 통과한 결정만 실제 브로커로 나갑니다. 브로커가 수락한 뒤에만 플랫폼 원장이 기록됩니다.

STEP 7 — 모니터링 / Monitor

  • 자동화 페이지 실행 기록: 매 틱의 결정·체결·스킵 사유.
  • 계좌 페이지 브로커 주문 내역: 요청 수량 vs 브로커 확인 체결 수량, 상태별 색상.
  • 드리프트 기록(빨간 카드): 원장과 브로커가 어긋난 경우 — §5 참고.
  • 알림: 체결(trade_executed), 게이트웨이 다운(gateway_down), 주문 드리프트(order_drift) — 알림 설정의 이메일/SMS 채널을 따릅니다.

03주문이 지나는 12개의 관문 / The 12-step gate chain

자동 실행이 켜진 규칙의 매 틱마다, 결정(buy/sell)이 실제로 체결되려면 아래 관문을 순서대로 전부 통과해야 합니다. 하나라도 막히면 그 사유가 실행 기록에 남고 주문은 나가지 않습니다.

그림 2 — 실행 게이트 체인(evaluate_execution_gates). ⑫ 왼쪽 열 아래→오른쪽 열 위로 이어지며, 전부 통과해야 체결됩니다. 테스트 실행(▶)은 분석만 하며 이 체인을 거치지 않습니다.
순서가 중요합니다: 자동 실행이 꺼진 규칙은 「자동 실행 꺼짐」으로 기록되지 게이트웨이 오류로 기록되지 않습니다. 스킵 사유를 읽으면 몇 번 관문에서 멈췄는지 바로 알 수 있습니다.

04live 주문의 수명주기 / Life of a live order

브로커가 즉시 체결을 확정하지 않으면(SUBMITTED) 주문 리컨실러가 2분마다 브로커에 결과를 물어 최종 상태를 확정합니다.

그림 3 — 제출 → (즉시 또는 리컨실러 경유) 확정 → 어긋나면 시끄럽게 알림. 요청 수량(quantity)과 브로커 확인 수량(filled_qty)은 별도 컬럼이라 차이가 계속 보입니다.
설계 원칙 — 탐지만, 수정은 사람: 리컨실러는 포지션·현금을 절대 건드리지 않습니다. 백그라운드 작업이 돈 계산을 고치는 것은 원장을 두 번 망가뜨리는 길이라, 어긋남은 빨간 카드와 알림으로 크게 표시하고 정정은 사용자가 브로커 계좌를 확인한 뒤 직접 합니다.

05IBKR 세션 keepalive / IBKR session keepalive

IBKR Client Portal 세션은 몇 분만 유휴해도 끊깁니다. 워커가 60초마다 세션을 tickle하고, 끊기면 재인증을 시도하며, 복구 불가면 하루 1회 알립니다.

그림 4 — 세션 상태 머신. 경합(competing) 세션도 dead로 취급합니다(다른 로그인이 계좌를 점유하면 주문이 거부되므로).
shadow 안전장치: IBKR은 Alpaca/Binance와 달리 샌드박스 호스트가 따로 없고 계좌가 실자금 여부를 결정합니다. 그래서 shadow 모드에서 계좌번호가 모의계좌(D 접두사)가 아니면 어댑터가 요청 자체를 전송하지 않고 거부합니다.

07시스템이 절대 하지 않는 것 / Safety invariants (test-pinned)

불변식이유보장 방법
live를 조용히 모의로 강등하지 않음가짜 체결이 진짜처럼 보이면 최악게이트 ②에서 명시적 거부 + 사유 기록
shadow 주문이 실제 거래소에 닿지 않음"모의 실행"이 실자금을 쓰면 안 됨규칙 모드가 엔드포인트를 고정(저장된 계정 모드 무시), IBKR은 모의계좌 강제
브로커 거부 시 포지션 생성 없음시장에 닿지 않은 주문의 유령 포지션 방지live는 브로커 수락 후에만 원장 기록
리컨실러가 원장을 수정하지 않음백그라운드 돈 계산 수정 = 이중 손상 위험탐지·기록·알림만, 정정은 사람
브로커 키가 클라이언트로 돌아가지 않음유출 면적 최소화AES-GCM 저장, 조회 API는 메타데이터만 반환
암호화 키(EXECUTION_ENCRYPTION_KEY)는 write-once교체 시 저장된 모든 자격증명 영구 무효운영 절차 + 비밀번호 관리자 백업
live 실패는 침묵하지 않음죽은 게이트웨이는 조용한 시장과 구분 불가gateway_down/order_drift 알림 (시간·일 단위 중복 제거)
위 불변식들은 자동 테스트(총 1,386개 중 실행 스택 ~100개)로 고정되어 있으며, 3-에이전트 QA(백엔드 적대 검증 · 프런트엔드 플로우 · 프로덕션 상태)로 재검증되었습니다.
