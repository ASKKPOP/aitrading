Part A — Apple Developer portal

A파트: 애플 개발자 포털에서 직접 하셔야 하는 작업

Prerequisites. A paid Apple Developer Program membership (US$99/year) — a free Apple ID cannot enable Sign in with Apple. You must be signed in as Account Holder or Admin. Sooppiy already serves https://sooppiy.com, which satisfies Apple's HTTPS requirement.

유료 Apple Developer Program 멤버십(연 $99) 필요 — 무료 계정으로는 불가. 역할은 Account Holder 또는 Admin. HTTPS 도메인은 이미 충족.

Step 1 · App ID (primary identifier)

앱 ID 생성 — 웹 전용이어도 반드시 먼저 필요합니다

  1. Go to Certificates, Identifiers & Profiles → Identifiers → + → App IDs → App.
  2. Description: Sooppiy. Bundle ID: Explicit, e.g. com.sooppiy.app.
  3. Under Capabilities, tick Sign in with Apple. Register.

Even though we only need web login, the Services ID and the signing key both have to point at a primary App ID. This one exists purely to be that anchor.

Step 2 · Services ID — this becomes APPLE_CLIENT_ID

서비스 ID — 웹 로그인의 client_id가 되는 값 (앱 ID와 반드시 달라야 합니다)

  1. Identifiers → + → Services IDs.
  2. Description: Sooppiy Web. Identifier: com.sooppiy.web — must differ from the App ID above.
  3. Register, then click it again to configure. Tick Sign in with Apple → Configure. Set Primary App ID to the one from Step 1. The domain and return URL are not on this screen — they live behind the ⊕ next to “Website URLs”, which Step 3 walks through.
The return URL is NOT the same shape as Google's. Our Google return URL is https://sooppiy.com/auth/google/callback — an SPA route that reads the query string and then calls the API. Apple POSTs a form body to its return URL, and a static SPA route cannot read a POST body. So Apple's return URL must hit the backend directly, under /api/ (nginx proxies /api/ → the backend; everything else falls through to index.html).

애플 리턴 URL은 구글과 형태가 다릅니다. 애플은 POST로 폼을 보내므로 SPA 라우트가 받을 수 없습니다. 반드시 /api/ 아래 백엔드 경로여야 합니다.

Rules Apple enforces on this field: HTTPS only, exact match (no wildcards, no trailing-slash mismatch), and localhost / raw IPs are rejected. That last one is why Apple login cannot be tested on a local dev server the way Google can — see §6.

Step 3 · Verify the domain the step people get stuck on

도메인 소유 확인 — 별도 메뉴가 아니라 서비스 ID 안에 있습니다

There is no “Domain Verification” menu. That is why it is hard to find: verification lives inside the Services ID you made in Step 2, behind its Configure button. If you are hunting through the sidebar for it, you will not find it there.

사이드바에 “도메인 확인” 메뉴는 없습니다. Step 2에서 만든 서비스 ID → Configure 안에 있습니다.

3a · Get to the right screen

  1. developer.apple.com/account → Certificates, Identifiers & Profiles → Identifiers (left sidebar).
  2. Change the filter in the top-right dropdown from “App IDs” to “Services IDs”. This is the single most common place to get lost — your Services ID is invisible while the list is filtered to App IDs, and it looks like it was never created.
  3. Click your Services ID (com.sooppiy.web).
  4. Tick the Sign In with Apple checkbox. The Configure button beside it only becomes clickable once that box is ticked.
  5. Click Configure → the Web Authentication Configuration dialog opens. Everything below happens here.

3b · Inside the dialog — the ⊕ is the whole trick

The Download button is not on this screen, and that is not a bug. The Web Authentication Configuration dialog opens with only a Primary App ID picker and an empty Website URLs section holding a Search box. There is nothing to download yet because no website URL group exists. The blue ⊕ next to “Website URLs” is what creates one — and that is where the domain field, the return-URL field, and the association file all live.

이 화면에는 Download 버튼이 없습니다 — 아직 등록된 웹사이트 URL 그룹이 없기 때문입니다. “Website URLs” 옆의 파란 ⊕를 누르면 도메인·리턴 URL 입력과 파일 다운로드가 나옵니다.

What to type in the ⊕ sheet
FieldValueWhy
Domains and Subdomainssooppiy.comDomain only. Apple rejects a scheme or a path — https://sooppiy.com and sooppiy.com/ both fail.
Return URLshttps://sooppiy.com/api/auth/apple/callbackHere the https:// is required — the dialog says so explicitly. Must be character-identical to APPLE_REDIRECT_URI, and must be under /api/ so it reaches the backend (Apple POSTs; an SPA route cannot read that).

Then Next. Apple immediately tries to fetch the association file from the domain — it will fail, because we have not deployed it yet. That failure is expected and it is exactly what surfaces the Download button.

도메인은 스킴 없이, 리턴 URL은 https:// 포함. Next를 누르면 애플이 즉시 확인을 시도하고 실패합니다 — 그 실패 화면에서 Download 버튼이 나타납니다.

Finishing the dialog is a four-click tail, and stopping early loses the work. Apple spells it out in the dialog text: register the URLs → confirm the list → Done → Continue → Save. If you close after Done, the Services ID keeps the old configuration and the login will fail with a redirect-URI mismatch that points at nothing obvious.

Done → Continue → Save까지 눌러야 저장됩니다. 중간에 닫으면 설정이 반영되지 않습니다.

3c · The file, and where it has to live

Download gives you apple-developer-domain-association.txt — a small text file containing a JSON token. It is not a secret: it is a public proof-of-control token, which is why it is safe to send to me or commit to the repo. It must answer at exactly: 
https://sooppiy.com/.well-known/apple-developer-domain-association.txt
Note the leading dot in .well-known.
Do not scp it onto the server. The SPA root /usr/share/nginx/sooppiy is replaced on every deploy (scripts/deploy.sh publishes all three static roots), so a hand-placed file disappears the next time we ship — and Apple silently un-verifies the domain, which kills Apple login for everyone with no error anywhere in our logs.

Correct placement — commit it so every deploy republishes it: 
service/frontend/public/.well-known/apple-developer-domain-association.txt
Vite copies public/ verbatim into dist/, and nginx's try_files $uri /index.html serves a real file before falling back to the SPA. Verified on prod: /guide.html and /logo.svg both ship this way and answer 200.

서버에 직접 올리면 다음 배포에 지워지고, 애플이 조용히 인증을 해제합니다. 반드시 service/frontend/public/.well-known/에 커밋해서 빌드에 포함시키세요.

3d · Check it yourself BEFORE pressing Verify

Checking the status code will lie to you. nginx falls back with try_files $uri /index.html, so a missing file still answers 200 — with the SPA's HTML. Confirmed live: /definitely-not-a-file.txt returns 200. You must look at the body. 
# Right — shows the actual bytes Apple will read
curl -s https://sooppiy.com/.well-known/apple-developer-domain-association.txt

# ✅ good   → a short JSON token, something like {"webcredentials":{"apps":[...]}}
# ❌ bad    → <!doctype html>  ... that is index.html; the file is NOT deployed

# Also confirm no redirect is in the way (Apple does not chase them):
curl -sI https://sooppiy.com/.well-known/apple-developer-domain-association.txt | head -3
# want: HTTP/1.1 200 · content-type: text/plain — not 301/302

상태 코드는 거짓말을 합니다 — 파일이 없어도 SPA 폴백 때문에 200이 나옵니다. 반드시 본문을 확인하세요.

3e · Press Verify, and what each failure means

Only once the curl above prints the token: go back to the dialog and press Verify. Apple fetches the URL server-side, right then. Success turns the row green / shows the domain as verified; then Save / Continue to persist the configuration.
What Apple saysWhat it actually means
“Domain verification failed” / “couldn't verify”Apple fetched the URL and did not get the expected bytes — nine times out of ten it got index.html because the file was never deployed. Re-run the curl.
Verification passes but login still fails laterThe domain is fine; the mismatch is the Return URL. It must be character-identical to APPLE_REDIRECT_URI — no trailing slash, no www drift, HTTPS.
Was verified, now broken with no change from usA deploy overwrote the file. That is exactly the failure 3c prevents — check the curl first, then confirm the file is still in public/.well-known/.
“Please enter a valid domain”You typed a scheme or a path. Domain only.
There is a second, different domain screen — do not confuse them. Services → Sign in with Apple for Email Communication also asks for a domain and its own association file. That one is for sending mail to relay addresses (Step 6), not for login. Verifying one does not verify the other; you will eventually need both.

도메인을 요구하는 화면이 두 곳입니다. 이메일 릴레이용(Step 6)과 로그인용은 별개이며, 하나를 인증해도 다른 하나는 인증되지 않습니다.

Step 4 · Private key (.p8) — downloadable exactly once

개인 키 발급 — 다운로드는 단 한 번만 가능합니다

  1. Keys → +.
  2. Key Name: Sooppiy Sign in with Apple. Tick Sign in with Apple → Configure → pick the primary App ID from Step 1.
  3. Register → Download. You get AuthKey_XXXXXXXXXX.p8.
  4. Record the Key ID (the 10 characters in the filename) — that is APPLE_KEY_ID.
The .p8 downloads once and can never be downloaded again. Lose it and the only path is revoking the key and issuing a new one. Apple also caps how many Sign in with Apple keys can exist at a time (2) — if the portal refuses a new key, revoke a stale one first. Store the file in your password manager, not in the repo.

.p8는 재다운로드 불가 — 분실 시 폐기 후 재발급뿐입니다. 저장소에 커밋하지 말고 비밀번호 관리자에 보관하세요.

Step 5 · Team ID

팀 ID 확인

Membership details → Team ID, a 10-character string. That is APPLE_TEAM_ID, and also the iss claim of the client secret.

Shortcut: it is already on screen in the Web Authentication Configuration dialog — the Primary App ID renders as <TeamID>.<bundle>, e.g. Y2WV2C335B.com.sooppiy.app → Team ID Y2WV2C335B.

Primary App ID 앞부분이 곧 Team ID입니다.

Step 6 · Hide My Email relay optional now, required for email delivery

이메일 가리기(릴레이) 설정 — 안 하면 애플 사용자에게 메일이 안 갑니다

Apple users can choose Hide My Email, which hands us a relay address like a1b2c3d4e5@privaterelay.appleid.com instead of their real one. Apple drops mail sent to a relay address from an unregistered sender. Sooppiy sends welcome mail, alerts, password resets and reports — all of that silently disappears for those users unless you register the sender.

  1. Certificates, Identifiers & Profiles → Services → Sign in with Apple for Email Communication → Configure.
  2. Register the sending domain we already use with SendGrid, plus the exact From addresses.
  3. Confirm the SPF record Apple asks for is present on that domain.

가입 환영 메일·알림·비밀번호 재설정이 전부 이 경로를 탑니다. 등록하지 않으면 조용히 전달 실패합니다.

Part B — what to set, and what has to be built

5 env vars

환경변수 5개 — .env.example에 문서화되어 있습니다

Env varValueFrom
APPLE_TEAM_ID10 chars, e.g. A1B2C3D4E5Step 5
APPLE_CLIENT_IDThe Services ID, e.g. com.sooppiy.web — not the App IDStep 2
APPLE_KEY_ID10 chars from the .p8 filenameStep 4
APPLE_REDIRECT_URIhttps://sooppiy.com/api/auth/apple/callback — must equal the Return URL registered in Step 2Step 2
APPLE_PRIVATE_KEYContents of the .p8 file (or APPLE_PRIVATE_KEY_B64)Step 4

The .p8 is multi-line, and .env is not. Pasting it raw breaks the file. Two workable forms — pick one and make the backend match:

# A. single line with escaped newlines (quote it)
APPLE_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\nMIGTAgEA...\n-----END PRIVATE KEY-----"

# B. base64, decoded at load time (no escaping to get wrong)
APPLE_PRIVATE_KEY_B64=LS0tLS1CRUdJTiBQUklWQVRFIEtFWS0tLS0t...

.p8는 여러 줄이라 .env에 그대로 붙이면 깨집니다. 개행을 \n으로 이스케이프하거나 base64로 넣으세요.

Where to put them: straight into the prod .env over SSH (/home/ec2-user/sooppiy/.env), never into the repo. Then re-run scripts/deploy.sh so the containers pick them up — the deploy script re-checks the image guard, so editing .env by hand and restarting outside the script defeats the drift protection.

값은 SSH로 prod .env에만. 저장소에 커밋 금지. 반영은 scripts/deploy.sh로.

5. Why Apple is not a copy-paste of the Google flow

애플은 구글 흐름을 복사해서 되지 않습니다 — 반드시 다른 7가지

#DifferenceWhat it means for the implementation
1The client secret is a JWT you sign, not a string Apple gives you ES256, signed with the .p8. Header {alg: ES256, kid: APPLE_KEY_ID}; claims iss=Team ID, sub=Services ID, aud=https://appleid.apple.com, iat, exp (max 6 months). Generate on demand and cache until just before exp. cryptography is already a dependency; PyJWT is not — either add it to service/requirements.txt or sign with cryptography directly.
2The callback is a POST With scope=name email Apple requires response_mode=form_post and sends application/x-www-form-urlencoded. Google's handler is @app.get; Apple's must be @app.post reading form fields, then 302 the browser back into the SPA carrying the session token.
3Name and email arrive only on the FIRST authorization They come in a user form field as JSON, once, ever. Every later sign-in returns only code and id_token. If the first response is not persisted, the name is gone permanently — the only recovery is the user removing the app under Apple ID settings and re-authorizing. Write it inside the same transaction that creates the user.
4Identity comes from the id_token, not a userinfo endpoint There is no /userinfo. Verify the id_token against Apple's JWKS (https://appleid.apple.com/auth/keys, cache it), check iss=https://appleid.apple.com, aud=Services ID, and exp. The sub claim is the stable per-team user identity → that is the provider_user_id for oauth_identities.
5Emails may be relay addresses @privaterelay.appleid.com. Treat as a real address, but do not assume it is unique-forever or that the user recognises it. Account-linking by email (the Google flow's case 2) still works, but the relay address will never match an existing password account — those users get a new account, which is correct behaviour.
6State cannot ride in a cookie A cross-site POST does not carry a SameSite=Lax cookie. Our existing design already avoids this — _store_state keeps the nonce in Redis/in-proc and it returns in the POST body. Reuse _store_state/_consume_state as-is.
7No localhost testing Apple rejects localhost return URLs, so the flow cannot be exercised the way the Google one can. Either register a second Services ID against a staging HTTPS host, or accept that the first real test happens on prod — in which case ship it behind the provider flag so a failure only shows a disabled button.

6. Verification checklist

검증 체크리스트 — 순서대로 확인

  1. curl https://sooppiy.com/.well-known/apple-developer-domain-association.txt → check the body, not the status code. nginx's SPA fallback is try_files $uri /index.html, so a missing file still answers 200 — with index.html. Verified live: /definitely-not-a-file.txt → 200. So curl -s … | head -1 must show the Apple payload, not <!doctype html>. Re-check after the next deploy too.
  2. Apple portal shows the domain as Verified.
  3. curl https://sooppiy.com/api/auth/providers → "apple": true.
  4. Sign in on a real device with a real Apple ID → lands back in the SPA logged in.
  5. Row appears: SELECT * FROM oauth_identities WHERE provider='apple'.
  6. Sign out, sign in again → same user_id, no duplicate user created.
  7. Repeat once with Hide My Email selected, then confirm a welcome email actually arrives at the relay address.
  8. Existing password account with the same real email → gets linked, not duplicated.

7. Maintenance — the 6-month cliff

유지보수 — 6개월 만료가 조용한 장애를 만듭니다

Resolved by the implementation — there is nothing to rotate. Apple caps the client secret JWT at 6 months, and a long-lived one pasted into .env would expire silently: login just starts failing one day with no deploy to blame. So _apple_client_secret() mints a fresh JWT on every token exchange with a 5-minute expiry. Nothing is stored, nothing expires on a calendar. The .p8 key itself never expires — keep it safe and this stays hands-off. (A test asserts the lifetime stays short, so a future change back to a long-lived secret fails CI.)

구현으로 해결됨 — 회전할 것이 없습니다. 시크릿 JWT를 매 요청마다 5분짜리로 생성합니다. .p8 키 자체는 만료되지 않습니다.

Order of operations

  1. You: Part A steps 1–5 in the Apple portal. Keep the .p8 in your password manager.
  2. You → me: the apple-developer-domain-association.txt file only (it is a public verification token, not a secret). I commit it to service/frontend/public/.well-known/ and deploy, so the URL survives every future deploy.
  3. You: press Verify in the portal.
  4. You: put the 5 values into the prod .env over SSH — they go from Apple to the server and nowhere else.
  5. Me: deploy, then walk the §6 checklist with you. The button switches itself on.
  6. You: Part A step 6 (email relay) before real users arrive, or Hide-My-Email members silently stop receiving mail.

순서: A파트(1–5) → 도메인 확인 파일만 전달(비밀 아님) → 포털에서 Verify → prod .env에 값 5개 입력 → 배포·검증 → 이메일 릴레이 등록.
