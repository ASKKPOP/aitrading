The state rule that makes the keys matter

키가 중요한 이유 — 활성화는 오직 웹훅으로만 일어납니다

Checkout endpoints never activate a plan. They only return a redirect URL. Activation, renewal, plan change and cancellation are applied by billing_sync when a signed webhook arrives. So a working secret key with a broken webhook secret produces the worst failure mode there is: the customer is charged and gets nothing. Set both, and verify both.

체크아웃 엔드포인트는 결제를 활성화하지 않습니다. 활성화·갱신·변경·해지는 전부 서명 검증된 웹훅이 처리합니다. 시크릿 키만 맞고 웹훅 시크릿이 틀리면 돈은 빠져나가고 구독은 안 열리는 최악의 상태가 됩니다.

1. Stripe — step by step

스트라이프 설정 순서

1.0 Answering "What does your business do?" onboarding

Stripe underwrites trading-adjacent platforms carefully. The description below is accurate to what the code actually does — describe it this way, not more modestly. An account activated on a vague description and later found to be trading-related gets frozen with a balance in it.

스트라이프는 트레이딩 관련 플랫폼을 엄격히 심사합니다. 아래 문구는 코드가 실제로 하는 일 그대로입니다. 모호하게 적어 승인받았다가 나중에 발각되면 잔액이 묶인 채 계정이 정지됩니다.

Business description — full

Sooppiy is a subscription software (SaaS) platform for market research and
trading-strategy automation. Customers pay a recurring monthly fee (USD 60 /
250 / 500) for access to the web application.

The software aggregates public market data, news and sentiment, publishes
research and signals, and lets customers build, back-test and run automated
trading rules. By default every strategy runs against a simulated $100,000
paper-trading ledger — no real money is involved. Optionally, a customer may
connect their own brokerage or exchange account (e.g. Alpaca, Binance,
Interactive Brokers) using their own API credentials, so the software can
place orders on that account on their behalf.

Sooppiy is not a broker-dealer, exchange, money transmitter or investment
adviser. It never takes custody of customer funds or securities, and no
customer trading capital passes through Sooppiy or through Stripe. Stripe is
used solely to collect the monthly software subscription fee.

Short version for length-limited fields

Monthly SaaS subscription for market-research and trading-strategy automation
software. Strategies run on a simulated paper-trading ledger by default;
customers may optionally connect their own brokerage account. Sooppiy holds no
customer funds — Stripe collects only the software subscription fee.

One line

Points in your favour — say them, they are all verifiable on the live site:
  • Paper trading is the default; the marketing page states "$100,000 of paper money. Zero real risk."
  • Live trading is opt-in, off by default, and runs on the customer's own broker account after they accept that broker's terms.
  • The site already carries an explicit disclaimer: "Nothing on this site is investment advice."
  • No performance or guaranteed-return claims anywhere in the marketing copy — Stripe's restricted-business list bars exactly those.
Three things to fix before you submit — a reviewer opens the site and reads these:
  1. Terms & Conditions §8 says the opposite of what you're applying for. marketing/src/pages/termsconditions.astro currently reads "The Service is currently free to use… Sooppiy may introduce paid features or subscriptions in the future." Applying to charge subscriptions while your published terms say the product is free is a direct contradiction on the linked page.
  2. No refund / cancellation policy is published. Stripe requires one to be reachable from the site. State the actual policy: monthly term, cancel any time, access runs to expires_at, no partial-month refunds — whatever you decide, but it must be written down.
  3. Pricing is behind the login wall. /subscribe only renders for a signed-in user (App.tsx membership gate), so a reviewer cannot see the $60 / $250 / $500 tiers. Put a public pricing section on the marketing page or a public /pricing route.

① 이용약관 8조가 "현재 무료"라고 되어 있어 유료 구독 신청과 정면으로 모순됩니다. ② 환불·해지 정책이 공개되어 있지 않습니다(스트라이프 필수). ③ 가격이 로그인 뒤에 있어 심사자가 볼 수 없습니다.

This is descriptive guidance, not legal advice, and Stripe's classification decision is theirs alone.

1.1 Activate the account dashboard

Sign in at dashboard.stripe.com and complete business verification until the account shows Live mode available. Until then only sk_test_… keys exist.

사업자 인증을 끝내야 라이브 모드가 열립니다. 그 전에는 테스트 키만 발급됩니다.

1.2 Create one recurring Price per paid plan Product catalog

Products → Add product. For each tier create a product with a recurring, monthly price in USD:

Sooppiy plan codeNamePriceBilling periodNeeds a Stripe price?
juniorJunior$60.00MonthlyYes
proPro$250.00MonthlyYes
professionalProfessional$500.00MonthlyYes
enterpriseEnterprise——No — contact-only

Copy each Price ID (price_…, not the product prod_…). You need all three in step 4.

플랜별로 월 정기 가격을 만들고 price_… ID를 복사하세요. prod_…가 아닙니다. Enterprise는 문의 전용이라 가격이 필요 없습니다.

1.3 Copy the secret key Developers → API keys

Switch the dashboard to Live mode, then Developers → API keys → Secret key → Reveal. It starts with sk_live_ and is shown once.

The publishable key is not used — Sooppiy uses hosted Checkout, so no Stripe key ever reaches the browser.

Optional hardening: a restricted key works if you grant write on Customers, Checkout Sessions and Billing Portal Sessions. Nothing else is called.

라이브 모드에서 시크릿 키(sk_live_)를 복사합니다. 한 번만 표시됩니다. 퍼블리셔블 키는 쓰지 않습니다(호스티드 체크아웃이라 브라우저로 키가 나가지 않음). 제한 키를 쓸 경우 Customers·Checkout Sessions·Billing Portal Sessions 쓰기 권한이면 충분합니다.

1.4 Create the webhook endpoint Developers → Webhooks

Add endpoint → URL:

https://sooppiy.com/api/webhooks/stripe

Select exactly these four events — the handler ignores everything else, and a missing one silently breaks that transition:

EventWhat it drives in Sooppiy
checkout.session.completedFirst activation — links the subscription to the user
invoice.paidEvery renewal — pushes expires_at to period end + 3-day grace
customer.subscription.updatedPlan switch, and cancel_at_period_end
customer.subscription.deletedSubscription ended

After saving, open the endpoint and copy the Signing secret (whsec_…).

위 네 개 이벤트만 선택하면 됩니다. 하나라도 빠지면 해당 전환(최초 활성화·갱신·플랜 변경·종료)이 조용히 멈춥니다. 저장 후 서명 시크릿(whsec_…)을 복사하세요.

API version: leave the endpoint on your account default. The handler reads both the old invoice.subscription and the 2025-03-31 basil shape invoice.parent.subscription_details.subscription, so either version keeps renewals working.

API 버전은 계정 기본값 그대로 두세요. 구·신 두 가지 응답 형태를 모두 처리하므로 갱신이 끊기지 않습니다.

1.5 Configure the Customer Portal Settings → Billing → Customer portal

POST /api/subscriptions/stripe/portal hands subscribers straight to this page, so whatever you don't enable here, they can't do. Turn on:

  • Update payment method — otherwise an expiring card silently ends the subscription.
  • Cancel subscription → at end of billing period (not immediately — Sooppiy's model keeps access until expires_at).
  • Switch plans, listing the three prices from 1.2. Upgrade = immediate + prorated; downgrade = at period end. No proration code on our side.

구독자 관리 화면은 전적으로 이 설정에 따릅니다. 결제수단 변경, 기간 말 해지, 세 플랜 간 전환을 켜세요.

1.6 Enable Apple Pay / Google Pay Settings → Payment method domains

Add and verify sooppiy.com. Stripe hosts the verification file itself for Checkout, so no repo change is needed. Skip this and the wallet buttons just don't render — cards still work.

도메인 인증만 하면 지갑 결제가 열립니다. 건너뛰어도 카드 결제는 정상 동작합니다.

2. PayPal — step by step

페이팔 설정 순서

Sooppiy uses the Subscriptions API (/v1/billing), not the old one-time Orders flow. A PayPal "plan" (P-…) is a real object you must create — it is not the same thing as a Sooppiy plan row.

일회성 주문이 아니라 구독 API를 씁니다. PayPal 플랜(P-…)은 별도로 생성해야 하는 실제 객체입니다.

2.1 Create the Live app developer.paypal.com

Apps & Credentials → toggle to Live → Create App (type: Merchant). Copy the Client ID and Secret.

Do the whole flow in Sandbox first if you want a rehearsal — the steps are identical, only the toggle and the API host change.

Live로 전환한 뒤 Merchant 앱을 만들고 Client ID·Secret을 복사합니다. 먼저 Sandbox에서 그대로 연습해도 됩니다 — 호스트만 다릅니다.

2.2 Get an access token

curl -s -X POST https://api-m.paypal.com/v1/oauth2/token \
  -u "<CLIENT_ID>:<CLIENT_SECRET>" \
  -d "grant_type=client_credentials"

Sandbox host: https://api-m.sandbox.paypal.com. Take access_token from the response.

2.3 Create one Product, then one Plan per tier

# 1) product (once)
curl -s -X POST https://api-m.paypal.com/v1/catalogs/products \
  -H "Authorization: Bearer <ACCESS_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"name":"Sooppiy Subscription","type":"SERVICE","category":"SOFTWARE"}'

Copy the returned id (PROD-…), then create one plan per tier — repeat with 250 and 500:

# 2) plan (repeat per tier: Junior 60 / Pro 250 / Professional 500)
curl -s -X POST https://api-m.paypal.com/v1/billing/plans \
  -H "Authorization: Bearer <ACCESS_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{
    "product_id": "<PROD-…>",
    "name": "Sooppiy Junior Monthly",
    "status": "ACTIVE",
    "billing_cycles": [{
      "frequency": {"interval_unit": "MONTH", "interval_count": 1},
      "tenure_type": "REGULAR", "sequence": 1, "total_cycles": 0,
      "pricing_scheme": {"fixed_price": {"value": "60", "currency_code": "USD"}}
    }],
    "payment_preferences": {"auto_bill_outstanding": true}
  }'

"total_cycles": 0 means bill forever — that is what makes it auto-renew. Copy each P-… plan id.

total_cycles: 0이 무기한 갱신을 뜻합니다. 각 P-… 플랜 ID를 복사하세요.

Junior needs a trial cycle — and it cannot be added later. Under the service rules (service-rules.html §1) Junior carries a 7-day free trial. On PayPal that is a second billing_cycles entry, and a plan created without it must be deleted and recreated — there is no way to add a trial to a live plan. Create Junior like this instead: 
"billing_cycles": [
  { "tenure_type": "TRIAL",   "sequence": 1, "total_cycles": 1,
    "frequency": {"interval_unit": "DAY", "interval_count": 7},
    "pricing_scheme": {"fixed_price": {"value": "0", "currency_code": "USD"}} },
  { "tenure_type": "REGULAR", "sequence": 2, "total_cycles": 0,
    "frequency": {"interval_unit": "MONTH", "interval_count": 1},
    "pricing_scheme": {"fixed_price": {"value": "60", "currency_code": "USD"}} }
]
Pro and Professional keep the single REGULAR cycle shown above — no trial. On Stripe the equivalent is subscription_data.trial_period_days = 7 passed on the Junior Checkout Session only, which is changeable later, so Stripe is not blocked by this.

주니어에는 체험 주기가 필요하고, 나중에 추가할 수 없습니다. PayPal은 체험을 billing_cycles의 두 번째 항목으로 정의하며, 체험 없이 만든 플랜은 삭제 후 재생성해야 합니다. Pro·Professional은 위의 단일 REGULAR 주기 그대로 둡니다. Stripe는 trial_period_days를 나중에 넣을 수 있어 제약이 없습니다.

2.4 Create the webhook app page → Webhooks → Add

https://sooppiy.com/api/webhooks/paypal

Subscribe to these six events:

EventWhat it drives
BILLING.SUBSCRIPTION.ACTIVATEDFirst activation (user id read from custom_id)
PAYMENT.SALE.COMPLETEDEvery renewal payment — extends access
BILLING.SUBSCRIPTION.UPDATEDPlan change applied
BILLING.SUBSCRIPTION.CANCELLEDMarked cancelled; access runs to expires_at
BILLING.SUBSCRIPTION.SUSPENDEDSame treatment as cancelled
BILLING.SUBSCRIPTION.EXPIREDSubscription ended

Save, then copy the Webhook ID (WH-…) shown on the webhook. That ID is what the server sends to PayPal's verify-webhook-signature API — a wrong one rejects every event with 400.

저장 후 Webhook ID(WH-…)를 복사하세요. 서버가 서명 검증 API에 이 값을 보내므로, 값이 틀리면 모든 이벤트가 400으로 거부됩니다.

3. Put the keys on prod

운영 서버에 키 반영

SSH in, edit the env file the containers read (docker-compose.yml loads env_file: .env for both backend and worker):

ssh -i ~/shell/sierrabiolab/sierrabiolab-aws.pem ec2-user@52.9.147.202
cd /home/ec2-user/sooppiy
cp .env .env.bak.$(date +%F)      # keep a rollback copy
vi .env

Append — no quotes, no trailing spaces:

STRIPE_SECRET_KEY=sk_live_…
STRIPE_WEBHOOK_SECRET=whsec_…
PAYPAL_CLIENT_ID=…
PAYPAL_CLIENT_SECRET=…
PAYPAL_WEBHOOK_ID=WH-…
PAYPAL_API_BASE=https://api-m.paypal.com
PAYPAL_UI_ENABLED=true

Recreate both services — the worker shares the same env file:

docker compose --profile prod up -d backend worker
# if the containers come back "up-to-date" instead of recreated:
docker compose --profile prod up -d --force-recreate backend worker
The two easiest ways to get this wrong:
  1. Leaving PAYPAL_API_BASE unset. It defaults to the sandbox host, so live credentials fail authentication and every PayPal call 502s.
  2. Restarting only backend. The worker reads the same .env; leave it stale and the two processes disagree about what is configured.

① PAYPAL_API_BASE를 비워두면 기본값이 샌드박스라 라이브 인증이 실패합니다. ② backend만 재시작하면 worker가 옛 설정을 들고 있게 됩니다.

4. Seed the plan IDs into the database

플랜 ID를 DB에 등록 — 이 단계를 빠뜨리면 결제 버튼이 503을 냅니다

There is no admin-console screen for this yet. The IDs live in subscription_plans.stripe_price_id and subscription_plans.paypal_plan_id (added by migration 0041_billing_autorenew) and must be set with SQL. Without them, checkout returns 503 "This plan is not configured for card payments" — even with perfect keys.

현재 관리자 콘솔에 입력 화면이 없어 SQL로 직접 넣어야 합니다. 키가 완벽해도 이 값이 없으면 503이 납니다.

-- prod MySQL
UPDATE subscription_plans SET stripe_price_id='price_…', paypal_plan_id='P-…' WHERE code='junior';
UPDATE subscription_plans SET stripe_price_id='price_…', paypal_plan_id='P-…' WHERE code='pro';
UPDATE subscription_plans SET stripe_price_id='price_…', paypal_plan_id='P-…' WHERE code='professional';
-- enterprise stays NULL — contact-only, no checkout

SELECT code, price_usd, stripe_price_id, paypal_plan_id FROM subscription_plans ORDER BY sort_order;

Check the SELECT output before moving on: the price you typed into Stripe must match price_usd, and every id must sit on the row it belongs to. A swapped pair charges the wrong amount for the right plan, and no code path catches that.

이동 전에 SELECT 결과를 확인하세요. Stripe에 입력한 금액과 price_usd가 일치해야 하고, ID가 엉뚱한 행에 들어가면 다른 금액이 청구됩니다. 이건 코드가 못 잡습니다.

5. Verify — in this order

검증 순서

5.1 Configuration is visible

curl -s https://sooppiy.com/api/subscriptions/plans | jq '{stripe_available, paypal_available}'

Both must be true. stripe_available reflects only STRIPE_SECRET_KEY; paypal_available needs client id + secret and PAYPAL_UI_ENABLED=true. Neither tells you anything about the webhook secrets — that is 5.2.

5.2 Webhooks are actually accepted the step people skip

In the Stripe dashboard, on the endpoint, use Send test webhook → checkout.session.completed. Expect 200. A 400 means the signing secret is wrong; 503 means STRIPE_WEBHOOK_SECRET is unset in the running container.

In PayPal, use the webhook simulator for BILLING.SUBSCRIPTION.ACTIVATED. Expect 200; 400 = wrong PAYPAL_WEBHOOK_ID.

Then confirm the row landed — duplicates are ignored by design, so this table is the receipt:

SELECT provider, event_id, type, processed_at FROM billing_events ORDER BY id DESC LIMIT 5;

5.3 One real end-to-end purchase

Buy junior once with a real card and once with a real PayPal account, then refund. Confirm:

  • user_subscriptions row with auto_renew=1, the correct external_id, and a future expires_at;
  • the account leaves /subscribe and the platform unlocks;
  • "Manage subscription" opens the Stripe portal / shows the PayPal controls.

실제 카드·PayPal로 junior를 각각 1건 결제한 뒤 환불하세요. 자동갱신 플래그, expires_at, 잠금 해제, 관리 화면까지 확인합니다.

6. Rehearsing in test mode first

라이브 전에 테스트 모드로 예행 — 권장

Same env var names, test values: sk_test_…, and for PayPal PAYPAL_API_BASE=https://api-m.sandbox.paypal.com with sandbox app credentials. Stripe's CLI forwards live-looking events at a local backend and prints its own signing secret:

stripe login
stripe listen --forward-to localhost:8001/api/webhooks/stripe
# prints whsec_… → use THAT as STRIPE_WEBHOOK_SECRET locally
stripe trigger checkout.session.completed

Test-mode price ids differ from live ones. When you switch to live, the DB values from step 4 must be re-seeded with the live price_… / P-… ids.

테스트 모드의 가격 ID는 라이브와 다릅니다. 라이브 전환 시 4단계 값을 라이브 ID로 다시 넣어야 합니다.

7. Rotating or revoking a key

키 교체·폐기

KeyHow to rotateImpact while rotating
STRIPE_SECRET_KEYCreate a new key, update .env, restart, then delete the old one in the dashboardNone if you delete last — existing subscriptions are unaffected
STRIPE_WEBHOOK_SECRETRoll the secret on the endpoint; Stripe keeps the old one valid for a grace windowUpdate .env inside that window or events start 400-ing
PAYPAL_CLIENT_SECRETGenerate a second secret on the app, deploy, then remove the firstTwo secrets can coexist — rotate with no downtime
PAYPAL_WEBHOOK_IDOnly changes if you delete and recreate the webhookEvery event 400s until the new ID is deployed

Failed webhooks are retried by both providers, so a short mismatch is recoverable — events land once the secret is correct, and billing_events keeps replays idempotent. A long one is not: providers stop retrying eventually.

양쪽 모두 실패한 웹훅을 재시도하므로 짧은 불일치는 복구됩니다(중복은 billing_events가 걸러냄). 다만 재시도에는 한계가 있어 오래 방치하면 유실됩니다.
