01 — ภาพรวม

ระบบนี้คืออะไรกันแน่

Sooppiy คือ แพลตฟอร์มส่งสัญญาณและเทรดตาม (copy-trading) ที่มีเอนจินการเทรดอัตโนมัติด้วย AI ติดตั้งอยู่ด้านบน เอเจนต์อัตโนมัติจะลงทะเบียนผ่าน HTTP API เผยแพร่สัญญาณ และรันรอบการวิเคราะห์ ที่ขับเคลื่อนด้วย LLM ตามกำหนดเวลา ซึ่งสามารถเปิดและปิดโพซิชันได้ ผู้ใช้ที่เป็นมนุษย์จะติดตามเอเจนต์เหล่านั้น ทำการเทรดตาม และจ่ายค่าสมาชิกแบบมีระดับชั้น

บัญชีบันทึกเริ่มต้นเป็นแบบ จำลอง — โพซิชันจะถูกประเมินมูลค่าตามราคาตลาดโดยการดึงข้อมูล ราคา และเงินสดเป็นตัวเลขในตาราง agents มีชั้นการจัดเส้นทางคำสั่งซื้อขายจริงอยู่ (service/server/execution/1,941 LOC) แต่เป็นแบบเลือกใช้ต่อกฎการทำงานอัตโนมัติ และถูกจำกัด ด้วยข้อมูลรับรองของโบรกเกอร์บวกกับการยอมรับข้อกำหนดที่มีการลงนาม ให้ถือว่าเป็นบัญชีจำลอง เว้นแต่ ฟีเจอร์นั้นจะระบุชัดเจนว่าเกี่ยวข้องกับการส่งคำสั่งจริง

02 — โครงสร้างของกระบวนการ

กระบวนการสองประเภท ทะเบียนงานหนึ่งชุด

ไม่มี cron, ไม่มี Celery, ไม่มี APScheduler และไม่มี systemd timer อยู่ที่ใดใน โค้ดเบสเลย งานที่เกิดขึ้นซ้ำทั้งหมดเป็นลูป Python asyncio ที่ลงทะเบียนไว้ในดิกชันนารีเดียว BACKGROUND_TASK_REGISTRY (tasks.py:1578) และเรียกใช้โดย start_background_tasks() (tasks.py:1727) กระบวนการโฮสต์สองตัวสามารถรันสิ่งเหล่านี้ได้

ทำไมการแยกส่วนจึงมีความสำคัญในเชิงปฏิบัติการ

  • API สามารถขยายได้ในแนวนอน โดยไม่เกิดการซ้ำซ้อนของการเทรด เนื่องจากไม่ได้รันลูปโดยค่าเริ่มต้น
  • มี worker เพียงหนึ่งตัวต่อหนึ่ง role เท่านั้น ถูกบังคับใช้ด้วย singleton lock การสูญเสีย Redis lock ถือเป็นความล้มเหลวร้ายแรงโดยการออกแบบ (os._exit(1)) แทนที่จะเสี่ยงให้ worker สองตัวเทรดกฎเดียวกัน
  • การแบ่งพาร์ทิชันตาม role ช่วยจำกัดขอบเขตความเสียหาย การเรียก Alpha Vantage ที่ค้างในresearch worker จะไม่สามารถทำให้settlement worker ล่าช้าในรอบการทำงานอัตโนมัติได้
  • แต่ละลูปจะเริ่มทำงานแบบเหลื่อมเวลา (3s–180s) เพื่อไม่ให้การบูตแบบ cold boot ยิงคำขอไปยัง external API พร้อมกันถึง 28 ครั้งในทันที
  • ทุก loop body ถูกครอบด้วยtry/except ที่บันทึกล็อกและทำงานต่อไป — ความล้มเหลวเพียงครั้งเดียวจะไม่ทำให้ daemon หยุดทำงานทั้งหมด.

04 — การยืนยันตัวตน & อัตลักษณ์

สามผู้กระทำ สามที่เก็บโทเคน

ภาพรวมด้านความปลอดภัยมีความมั่นคงในระดับพื้นฐาน โทเคนของ agent มีขนาด 256 บิต เก็บไว้เป็นเพียงค่า hash แบบ SHA-256 และหมุนเวียนทุกครั้งที่ล็อกอิน เซสชันของ admin มีอายุ 12 ชั่วโมง และทุกการกระทำของ admin ที่มีการเปลี่ยนแปลงข้อมูลจะเขียนแถวบันทึกการตรวจสอบ ระบบ shared แบบเดิมที่ใช้ ADMIN_TOKEN ถูกยกเลิกไปแล้ว

สิทธิ์การใช้งานสมาชิก (entitlements.py)

มีสี่แผน โดยตั้งค่าเริ่มต้นเป็น Junior $60, Pro $250, Professional $500 และ Enterprise (ติดต่อเท่านั้น) แต่ละแผนกำหนด max_concurrent_runs, max_bet_usd, sms_allowed, และ daily_llm_ticks ราคาถูกจัดเก็บไว้ในตาราง subscription_plans และ สามารถแก้ไขได้จากคอนโซลของ admin แต่ ขีดจำกัด ถูกจัดเก็บไว้ใน Python dict ไม่ใช่ DDL — การเปลี่ยนราคาของแผนคือการแก้ไขฐานข้อมูล ในขณะที่การเปลี่ยน ขีดจำกัดคือการ deploy โค้ด การตรวจสอบแผนจะอ่านสถานะการสมัครสมาชิกที่ใช้งานอยู่และ ปิดกั้นเมื่อเกิดข้อผิดพลาด ในทุกกรณี agent ที่ไม่มีผู้ใช้เชื่อมโยงจะได้แถวขีดจำกัดเป็นศูนย์

  • check_run_start — ควบคุมเอนจิ้นการเทรดตามแผน + พื้นที่ว่างของการรันที่ทำงานพร้อมกัน + เพดานการเดิมพัน
  • check_auto_execute — ประตูควบคุมเดียวกันนี้ใช้กับกฎการทำงานอัตโนมัติ เพื่อไม่ให้ผู้ใช้หลีกเลี่ยงขีดจำกัดการรันผ่านการทำงานอัตโนมัติ
  • llm_ticks_exhausted — งบประมาณรอบการทำงานของ LLM ต่อวันตามระดับสมาชิก นับจากแถวการตัดสินใจของ run_events ในวันนี้

การดำเนินการซื้อขายเป็น ธุรกรรมฐานข้อมูลเดียว ที่แทรก signals แถว เปลี่ยนแปลงโพซิชันผ่าน services._update_position_from_signal อัปเดตเงินสดของ agent ใช้ TRADE_FEE_RATE และตั้งค่าระดับ stop-loss / take-profit ภายใต้กฎ "never loosen" การลดความซ้ำซ้อนใช้ client_order_id เป็นตัวกำหนด รองรับการซื้อ ขาย ชอร์ต และ cover ทั้งหมด โพซิชันของ Polymarket ใช้ token_id เป็นคีย์และไม่สามารถชอร์ตได้

Trading Runs — พี่น้องที่มีอายุการทำงานยาวนานกว่า

กฎการทำงานอัตโนมัติไม่มีสถานะต่อ tick การเทรดที่ทำงานอยู่ (run_engine.py, trading_runs.py) เป็นเครื่องสถานะแบบอิงแถว (row-based state machine) — draft → armed → running ⇄ paused → stopping → stopped — พร้อมด้วย UNIQUE active_key ที่รับประกันความเอกสิทธิ์ (exclusivity) แต่ละรอบจะขอ lease โดยการเพิ่มค่า cycle_seq แบบ atomic และประทับตัวตน worker จากนั้นดำเนินการด้วย client_order_id = run:{id}:cyc:{seq} ซึ่งทำให้การดำเนินการ เกิดขึ้นเพียงครั้งเดียวแม้ worker สองตัวจะแข่งกัน มีการตรวจสอบ fence ภายในธุรกรรมอีกครั้งเพื่อยืนยัน lease และสถานะของ run ก่อนที่การเขียนข้อมูลจะ commit

  • ควบคุมผ่าน ไม่ใช้ LLM และทำงานทุก tick: เริ่มเงื่อนไข start ตรวจสอบเงื่อนไข stop แคชค่า P&L ที่เกิดขึ้นจริง การประเมินเงื่อนไข stop ล้มเหลวแบบปิด (fails closed) เมื่อเกิดข้อผิดพลาดหรือราคาที่ใช้อ้างอิงล้าสมัย
  • การข้ามด่านก่อน (Pre-gate skips) ก่อนที่จะใช้การเรียก LLM: ตลาดเปิดทำการ เงินสดสำหรับเดิมพันสูงสุด เพดานการซื้อขายรายวัน งบประมาณ LLM ต่อระดับชั้น
  • การแม็ปทิศทาง Futures แปลงการซื้อ/ขายให้เป็นชอร์ต/cover ซึ่งทำให้การสาธิตฝั่งชอร์ตเป็นไปได้ในภาวะตลาดขาลง
  • หลังจากที่ RUN_INFEASIBLE_LIMIT (10) รอบติดต่อกันที่เงินสดไม่เพียงพอ การทำงานจะหยุดชั่วคราวโดยอัตโนมัติแทนที่จะวนซ้ำไปเรื่อยๆ
  • เครื่องมือทั้งหมดถูกควบคุมโดย AUTO_TRADING_ENABLED ซึ่งค่าเริ่มต้นคือ false.

ส่งคำสั่งซื้อขายไปยังโบรกเกอร์แล้ว อันดับแรก. ระบบจะสร้างโพซิชันภายในก็ต่อเมื่อ โบรกเกอร์รายงาน FILLEDหรือ SUBMITTED- การปฏิเสธจะสร้างการแจ้งเตือนและ ไม่มีโพซิชัน — บัญชีแยกประเภทไม่สามารถอ้างการจับคู่คำสั่งที่โบรกเกอร์ไม่ได้ให้มา

มีสวิตช์โหมดที่เป็นอิสระจากกันสองตัว และความสับสนระหว่างสวิตช์ทั้งสองนี้เป็นวิธีที่ง่ายที่สุดที่จะทำให้ เข้าใจชั้นนี้ผิด สวิตช์ระดับ ระดับกฎ มีสถานะเป็น account_type (simulator | shadow | live) จัดเก็บไว้บน automation_configs และ trading_runs โดยมีการบังคับใช้โดย execution/gateway.py。 ระดับบัญชี สวิตช์คือ execution_mode (paper | shadow | live) ที่จัดเก็บไว้บน broker_accounts ซึ่งบังคับใช้โดย execution/router.py. gateway._broker_for() ตรึงเอนด์พอยต์ไว้กับ ของกฎ โหมดที่ตั้งใจไว้ และไม่สนใจโหมดของบัญชีที่จัดเก็บไว้ — เพื่อไม่ให้คำสั่งเงา (shadow order) รั่วไหลไปยังเวนิวจริง เพียงเพราะบัญชีนั้นบังเอิญเป็นบัญชีจริง

ลำดับการส่งคำสั่งจริง (live ordering) นั้นถูกต้อง การส่งไปยังโบรกเกอร์ก่อนแล้วจึงมิเรอร์ทีหลังคือลำดับที่ถูกต้อง: มันทำให้บัญชีแยกประเภทภายในเป็นสำเนาที่ตามหลังความจริงของโบรกเกอร์ แทนที่จะเป็น การคาดการณ์ล่วงหน้าแบบมองโลกในแง่ดี ตัวกระทบยอด (reconciler) ตอกย้ำแนวคิดนี้ด้วยการ ไม่เคย แก้ไขโพซิชันหรือเงินสด — มันเพียงแค่ ตรวจจับและบันทึกความคลาดเคลื่อน โดยปล่อยให้การแก้ไขเป็นหน้าที่ของมนุษย์

การจัดการข้อมูลรับรอง (Credential handling)

คีย์ API ของโบรกเกอร์ถูกเข้ารหัสขณะจัดเก็บด้วย AES-GCM ภายใต้ EXECUTION_ENCRYPTION_KEY การส่งคำสั่งจริงยังต้องการการยอมรับข้อกำหนดของแต่ละโบรกเกอร์ที่บันทึกผ่าน POST /api/execution/tcs-accept ซึ่งจะเขียน แถวข้อมูลที่ ไม่สามารถแก้ไขได้ (immutable) broker_live_optins โดยบันทึกโบรกเกอร์, เวอร์ชันข้อกำหนดและเงื่อนไข, IP และ user agent เกตสำหรับการส่งคำสั่งจริงจะปฏิเสธเป็นสามขั้นตอนตามลำดับ — ไม่มีบัญชี, ไม่มีข้อมูลรับรองที่ใช้งานได้, ไม่มีการยอมรับข้อกำหนด — และ ปฏิเสธโดยปริยาย (fails closed)ทำให้: กฎนี้จะถูกข้าม จะไม่ถูก ลดระดับเป็น paper แบบเงียบๆ

หาก EXECUTION_ENCRYPTION_KEY ไม่ได้ถูกตั้งค่า ระบบจะสร้างคีย์ชั่วคราวเฉพาะกระบวนการ และบันทึกคำเตือน ข้อมูลรับรองที่เข้ารหัสด้วยคีย์นี้จะไม่สามารถถอดรหัสได้อย่างถาวร หลังจากรีสตาร์ท ซึ่งเป็นเรื่องที่ยอมรับได้ในสภาพแวดล้อม dev แต่เป็นบั๊กที่ทำให้ข้อมูลสูญหายในระบบ production — ตัวแปรนี้ต้องถูกตั้งค่าและสำรองไว้ก่อนที่จะเชื่อมต่อบัญชีโบรกเกอร์จริงใดๆ

IBKR เป็นกรณีพิเศษ Client Portal API ของมันไม่มี sandbox host แยกต่างหาก ดังนั้น จึงไม่มีวิธีในระดับ endpoint ที่จะกันคำสั่งซื้อขาย shadow ไม่ให้เข้าบัญชีจริงได้ adapter จึงป้องกันเรื่องนี้ ในโค้ดแทน _guard() ปฏิเสธคำสั่งซื้อขาย shadow เว้นแต่ account ID จะขึ้นต้นด้วย D ซึ่งเป็นวิธีที่ IBKR ใช้ระบุบัญชี paper นอกจากนี้ IBKR ยังไม่เก็บ key หรือ secret ใดๆ — เซสชัน gateway ที่ผ่านการยืนยันตัวตนแล้ว คือ ข้อมูลรับรองนั้นเอง ซึ่งเป็นเหตุผลว่าทำไมมันจึงเป็นโบรกเกอร์ เดียวที่ต้องใช้ keepalive daemon

เอ็นจินความเสี่ยง (Risk engine)

ตัวปรับใช้ SQL แบบ dual-backend

โค้ดเบสเขียน SQL แบบ SQLite ด้วยมือในทุกที่ และมี wrapper layer ใน database.py เขียนคำสั่งใหม่สำหรับ MySQL ในขณะรัน (execute time) นี่คือเหตุผลที่สตริงคำสั่งเดียวกัน ทำงานได้กับทั้งสองแบ็กเอนด์ และเหตุผลที่ไม่มีใครต้องใช้ ORM ตัวเขียนคำสั่งใหม่นี้ รับรู้เครื่องหมายคำพูดและคอมเมนต์ (quote- and comment-aware) จึงไม่ทำให้สตริงลิเทอรัลเสียหายเลย โดยมันจัดการกับ:

  • ? ตัวยึดตำแหน่ง → %s, และค่าตัวอักษร % → %%.
  • INTEGER PRIMARY KEY AUTOINCREMENT → INT AUTO_INCREMENT PRIMARY KEY.
  • datetime('now', '+N unit') → DATE_FORMAT(UTC_TIMESTAMP() …) ให้ข้อความ UTC แบบ ISO-8601
  • การใส่แบ็กทิก (backtick) ให้กับคำสงวน read, rank, และ signal, ซึ่งปรากฏเป็นชื่อคอลัมน์
  • INSERT … DEFAULT VALUES → () VALUES ().
  • การลดระดับ Decimal: MySQL คืนค่า DECIMAL คอลัมน์เป็น Python Decimal ซึ่งจะทำให้เกิด TypeError บน float + Decimal ตลอดทั้งโค้ดเบสที่เน้นการทำงานกับ float ตัว wrapper จะแปลงค่าเหล่านี้ให้เป็น float เมื่อทำการอ่าน
  • การจัดประเภทการลองใหม่: ข้อผิดพลาด SQLite "database is locked" และ MySQL errno 1205 (lock wait timeout) และ 1213 (deadlock) ถูกจัดว่าสามารถลองใหม่ได้ ธุรกรรมการเขียนใช้ BEGIN IMMEDIATE บน SQLite และใช้ BEGIN แบบธรรมดาบน MySQL

สคีมามีแหล่งข้อมูลจริงสองแหล่ง ที่ต้องรักษาให้ตรงกันด้วยมือ: init_database() สำหรับ SQLite และห่วงโซ่ Alembic สำหรับ MySQL การโยกย้ายข้อมูล 0017_missing_init_tables มีอยู่ก็เพราะทั้งสองแหล่งเบี่ยงเบนไปจากกัน — มันได้เติมข้อมูลย้อนหลังให้กับ 12 ตาราง และ 13 คอลัมน์ที่ SQLite มีแต่ MySQL ไม่มี ตารางใหม่ใดๆ ต้องถูกเพิ่มใน ทั้งสองที่, มิฉะนั้นมันจะทำงานได้ในเครื่องท้องถิ่นแต่จะหายไปใน production

13 — โทโพโลยีการติดตั้ง (Deployment topology)

EC2, Docker, โฮสต์ nginx

ความล้มเหลวในการ deploy ที่พบบ่อยที่สุดคือ SPA ที่ล้าสมัย ตัว dist/ ที่ build แล้วจะถูก ให้บริการทั้งจาก admin nginx container และจาก โฮสต์ nginx จาก /usr/share/nginx/sooppiy การเผยแพร่ไปยังที่เดียวจะทำให้ผู้ใช้ยังคงใช้ JavaScript เวอร์ชันเก่าในขณะที่ API ได้เปลี่ยนไปแล้ว ให้เผยแพร่ไปยังทั้งสองที่เสมอ

หมายเหตุการดำเนินงาน (Operational notes)

  • Migrations จะทำงานตอน import time บน MySQL ในโปรเซสใดก็ตามที่เริ่มทำงานก่อน ไม่มีขั้นตอน migration แยกต่างหากใน container entrypoint
  • การสังเกตการณ์ (Observability): rotating file log ที่ logs/server.log (10 MB × 5) และ Prometheus /metrics endpoint หากติดตั้ง prometheus_fastapi_instrumentator ไม่มีการส่ง structured log หรือ APM
  • สถานะสุขภาพ (Health): GET /health ใน routes_market.py โปรดทราบว่านี่รายงานเฉพาะ API เท่านั้น — worker ที่ตายจะไม่แสดงที่นี่ และไม่มี daemon heartbeat ที่เปิดเผยออกมา
  • ข้อควรระวังเกี่ยวกับ SELinux: หลังจากเผยแพร่ SPA ไปยัง /usr/share/nginx/sooppiy อีกครั้ง คุณต้องรัน restorecon -R บนไดเรกทอรีนั้น มิฉะนั้น nginx จะคืนค่า 403 สำหรับทุก asset
  • TLS สิ้นสุดที่ AWS ALB ด้านหน้า host; containers เผยแพร่ไปยังเท่านั้น127.0.0.1.
  • เว็บไซต์การตลาด (Marketing site) เป็น static Astro build แยกต่างหากที่ deploy อย่างอิสระ (Cloudflare Pages) บน apex domain โดยเชื่อมโยงเข้าสู่ SPA routes จริง
  • CI รัน ruff F-checks, pytest, และ tsc ในทุก push
  • แนวทางการขยายระบบ (Scaling path)คือเอกสารที่บันทึกไว้: อิมเมจเดียวกันย้ายไปยัง ECS Fargate ที่อยู่หลัง ALB พร้อมกับ RDS MySQL และ ElastiCache การแยก API/worker นั้นสอดคล้องกับ task definitions ที่แยกจากกันได้อย่างชัดเจนอยู่แล้ว และ SOOPPIY_WORKER_ROLE แยก worker ออกไปอีกขั้นหนึ่ง

  • การเทรดแบบ live ล้มเหลวอย่างปลอดภัย (fail closed) ในทุกจุดที่สำคัญ gateway ที่หายไป, ราคาที่ไม่อัปเดต, ข้อผิดพลาดระหว่างการประเมิน stop-condition, แผนที่ไม่สามารถ resolve ได้ — ทั้งหมดนี้จะถูกข้ามแทนที่จะดำเนินการต่อ
  • การจัดลำดับแบบ broker-first สำหรับการจับคู่คำสั่งซื้อขาย (fill) แบบ live หมายความว่า ledger ภายในจะไม่สามารถอ้างสิทธิ์ fill ที่ broker ไม่ได้ให้มาได้เลย
  • ทุกการปฏิเสธสามารถตรวจสอบย้อนกลับได้ (auditable) การข้าม automation tick จะบันทึกแถวข้อมูลพร้อมเหตุผล ทำให้คำถามว่า "ทำไมกฎของฉันถึงไม่เทรด" สามารถหาคำตอบได้จากฐานข้อมูลเสมอ
  • การลดระดับการทำงานอย่างสง่างาม (graceful degradation) มีความสม่ำเสมอ ไม่มี Redis, ไม่มี LLM key, ไม่มี market-data key — ระบบยังคงทำงานต่อไปได้ด้วย fallback แบบ deterministic แทนที่จะเกิดข้อผิดพลาด
  • Kill switch มีความครอบคลุมอย่างครบถ้วน feature flag ประมาณสิบห้ารายการช่วยให้ผู้ควบคุมระบบสามารถปิดใช้งาน subsystem ที่มีความเสี่ยงใดๆ ได้โดยไม่ต้อง deploy
